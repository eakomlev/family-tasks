# Family Tasks

[![CI](https://github.com/eakomlev/family-tasks/actions/workflows/ci.yml/badge.svg)](https://github.com/eakomlev/family-tasks/actions/workflows/ci.yml)

PWA для семьи: общие задания, расписание уроков и тренировок детей, дни рождения и уведомления. React + Vite (`web/`), Node + Fastify (`server/`), PostgreSQL, всё упаковано в Docker.

## Что умеет

- **Семья без паролей.** Вход по email и коду из письма, приглашение по ссылке на 7 дней, роли «мама», «папа», «ребёнок».
- **Задания** себе и другим членам семьи: срок, время, повторы (каждый день, по дням недели, раз в месяц), отметка выполнения отдельно за каждый день, уведомления.
- **Расписание уроков** (Пн–Сб) и **тренировок** (Пн–Вс): ребёнок ведёт своё, родители видят и меняют; порядок перетаскиванием.
- **«Мой день»:** задания на сегодня, ближайшие уроки и тренировки (родителю сводка по детям).
- **Профиль:** имя, фото, дата рождения; светлая и тёмная темы.
- **Чат:** общий чат семьи и личный чат с каждым участником, сверху те, где недавно писали; число непрочитанных на значке «Чат» и push-уведомления о новых сообщениях. У своих сообщений галочки: одна «отправлено», две «прочитано» (в общем чате, когда прочитали все). Пока только текст.
- **Живые обновления:** когда кто-то из семьи меняет задание, расписание или профиль, открытые у остальных страницы обновляются сами (WebSocket, `/api/ws`; по нему приходит только сигнал, данные страница запрашивает обычным запросом).
- **Push-уведомления:** дни рождения, уроки на завтра, тренировка за 2 часа, новые и выполненные задания.
- **Устанавливается на телефон** как приложение (PWA).

Устройство проекта и соглашения для разработчиков описаны в [CLAUDE.md](CLAUDE.md).

## Запуск в Docker на своём компьютере

Это проверка «как в проде», но без HTTPS и доменов. Развёртывание на сервере описано ниже, в разделе «Деплой на сервер».

```bash
cp .env.example .env   # поменяйте пароль
docker compose up --build
```

Приложение: http://localhost:8080. Nginx отдаёт фронтенд и проксирует `/api` на сервер.

Письма с кодами входа в dev уходят в Mailpit (профиль `dev-mail` из `.env.example`), читать их можно на http://localhost:8025. В проде уберите `COMPOSE_PROFILES` и задайте `SMTP_*` в `.env`.

## Локальная разработка

Одна команда поднимает всё, фронтенд обновляется в браузере при каждом сохранении файла (HMR), сервер перезапускается сам:

```bash
npm run setup   # один раз: зависимости корня, server/ и web/
npm run dev
```

Команда запускает в Docker только БД и Mailpit, затем сервер (http://localhost:3000) и Vite. Адрес приложения напечатает Vite (обычно http://localhost:5173), `/api` проксируется на сервер, письма с кодами видны на http://localhost:8025. Если `.env` нет, он создаётся из `.env.example`. Остановка: Ctrl+C, а БД и Mailpit выключает `npm run dev:stop`.

Демо-данные (нужна запущенная БД: `npm run dev` или `npm run dev:infra`): `npm run seed` создаёт семью (мама Лена, папа Игорь, дети Миша и Аня) с расписанием уроков, тренировками и заданиями; войти можно по почте (`lena@demo.test`, `misha@demo.test`, `igor@demo.test`, `anya@demo.test`, код приходит в Mailpit) или, без почты, кодом из `npm run seed -- --snippet Миша` в консоли браузера. Скрипт работает только на локальной БД.

Service worker в dev выключен, PWA проверяйте на сборке (`docker compose up --build` или `npm run build && npm run preview` в `web/`). Если в браузере остался service worker от старых запусков, удалите его в DevTools → Application → Service Workers.

### Все команды

| Команда | Что делает |
|---|---|
| `npm run setup` | один раз: ставит зависимости корня, `server/` и `web/` |
| `npm run dev` | БД и Mailpit в Docker, сервер и фронтенд с автообновлением |
| `npm run dev:infra` / `npm run dev:stop` | только БД и Mailpit: запустить / остановить |
| `npm run seed` | демо-семья (подробнее выше), режимы `-- --snippet Миша`, `-- --json` |
| `npm test` | все тесты: сервер (нужна БД) и фронтенд; по отдельности `npm run test:server`, `npm run test:web` |
| `cd server && npm run typecheck` | типы приложения и тестов |
| `cd server && npm run notify:tick -- 10:05 --reset` | принудительный проход планировщика уведомлений (см. раздел про push) |
| `cd server && npm run vapid` | создать ключи VAPID для push |
| `cd server && npm run migrate:create -- имя` | новая миграция БД |
| `cd web && npx tsc -b && npm run lint && npm test && npm run build` | проверки, тесты и сборка фронтенда |
| `./update.sh` | обновление на сервере (раздел про деплой) |

## Тесты

Тесты сервера (Vitest) идут на настоящем Postgres, но в отдельной базе `family_tasks_test`, которую создают сами, ваши данные не затрагиваются. БД должна быть запущена:

```bash
npm run dev:infra   # если ещё не запущена
npm test            # сервер и фронтенд, около 5 секунд
```

Тесты фронтенда (`web/tests`, Vitest + Testing Library) БД не требуют: `npm run test:web`.

На GitHub те же проверки запускаются сами при каждом пуше в `main` и в каждом pull request (`.github/workflows/ci.yml`): тесты и типы сервера на настоящем Postgres, типы, линтер, тесты и сборка фронтенда, проверка конфигурации Docker Compose, `Caddyfile` и `update.sh`. Результат виден на вкладке Actions репозитория и в бейдже выше.

Состав: проверки чистой логики (`server/tests/unit`) и проверки API без сети (`server/tests/api`: вход, профиль, приглашения, расписания, задания, push, планировщик уведомлений). Почта и отправка push подменяются. Типы тестов: `cd server && npm run typecheck`. Тесты фронтенда проверяют логику (даты, повторы заданий, выбор дня на «Моём дне», расписания, тема), клиент API, отметку выполнения с откатом и ключевые компоненты (`TaskItem`, `CodeStep`, форма задания).

## Миграции БД

SQL-файлы лежат в `server/migrations/` (формат `-- Up Migration` / `-- Down Migration`), используется [node-pg-migrate](https://github.com/salsita/node-pg-migrate). Сервер применяет новые миграции сам при старте. Вручную (нужен `DATABASE_URL` из `.env`):

```bash
cd server
npm run migrate:create -- add-tasks   # новый файл миграции
npm run migrate:up
npm run migrate:down                  # откат последней
```

## Как устроен вход

- Регистрация и вход идут через email и одноразовый код из письма (6 цифр, 10 минут, 5 попыток, повторная отправка не чаще раза в минуту).
- Создатель семьи (мама/папа) указывает роль, имя и email, подтверждает email кодом и получает код семьи и первое приглашение на 7 дней.
- Присоединяются по ссылке `/join?code=...` (мама/папа/ребёнок) с тем же подтверждением email. Имя и email в семье уникальны, один email может состоять в нескольких семьях (ребёнок может указать почту родителя).
- Вход на другом устройстве: `/login`, email и код. Если email есть в нескольких семьях, предлагается выбрать. У каждого устройства своя сессия, «Выйти» отзывает только её.
- Владелец на странице семьи видит действующее приглашение и может выпустить новое (старое сразу перестаёт работать).
- Если на устройстве уже есть вход, перед заменой показывается подтверждение.
- На устройстве в IndexedDB хранятся код семьи, роль, имя и токен сессии. В БД лежит только SHA-256 хэш токена; токен отправляется как `Authorization: Bearer`.
- Сервер отвечает одинаково на запрос кода для известного и неизвестного email, чтобы адреса нельзя было перебирать.

## Роли и права

- **Создатель семьи** (мама или папа) создаёт и перевыпускает приглашения; присоединиться по приглашению может любая роль.
- **Профиль:** каждый меняет своё имя, фото и дату рождения; email и роль не меняются.
- **Задания:** создаёт любой, себе или другому; **менять и удалять** может только автор, **отмечать выполненным** и снимать отметку может любой член семьи.
- **Расписания уроков и тренировок:** есть только у детей; ребёнок ведёт своё, мама и папа видят и меняют расписание любого ребёнка своей семьи, другие дети его не видят.
- **Видимость:** задания, имена, фото, роли и даты рождения видны всей семье; email виден только его владельцу; чужая семья ничего не видит.

### Ограничения запросов

Общий лимит 120 запросов в минуту с одного IP, для отправки кодов, создания семьи, входа и приглашений — 10 в минуту. Сервер доверяет заголовку `X-Forwarded-For`, поэтому он должен быть доступен только через nginx.

## Push-уведомления

Приложение шлёт Web Push: о дне рождения участника семьи (в 10:00), об уроках на следующий учебный день (в 17:00, только детям) и о тренировке за 2 часа до начала (только детям, у тренировки должно быть указано время начала). Время считается по часовому поясу устройства, на которое включены уведомления. Кроме того, сразу приходят уведомления о новых сообщениях в чатах и о заданиях: исполнителю о новом и изменённом, автору о выполненном (себе ничего не шлётся).

- **Ключи VAPID.** Создайте один раз и положите в `.env` (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT=mailto:ваш@адрес`):

  ```bash
  cd server && npm run vapid
  ```

  Менять ключи после запуска нельзя: все подписки перестанут работать. Без ключей уведомления выключены, сервер предупредит об этом при старте.
- **Включение.** «Настройки» → «Уведомления» → «Включить уведомления» (браузер спросит разрешение), там же кнопка «Проверить уведомление». Работает в собранной версии (`docker compose up --build`): в режиме `npm run dev` service worker выключен.
- **Условия.** Нужен HTTPS (на `localhost` не нужен). На iPhone и iPad уведомления есть только у приложения, добавленного на экран «Домой» (iOS 16.4+).

### Как проверить, не дожидаясь 10:00 и 17:00

1. Запустите собранную версию и откройте её в обычном Chrome: `docker compose up --build -d`, затем http://localhost:8080. Войдите, в «Настройках» включите уведомления и нажмите «Проверить уведомление».
2. Для плановых уведомлений поднимите БД с открытым портом и запустите проход планировщика с нужным временем (по вашему часовому поясу):

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d db
   cd server
   npm run notify:tick -- 10:05 --reset   # дни рождения (окно 10:00–12:00)
   npm run notify:tick -- 17:05 --reset   # уроки ребёнку на следующий учебный день (окно 17:00–19:00)
   npm run notify:tick -- 16:05 --reset   # тренировка в 18:00 (напоминание в 16:00–16:15)
   ```

   Для дня рождения в профиле должна быть указана сегодняшняя дата (год любой, в прошлом), для уроков нужен ребёнок с расписанием на следующий учебный день. `--reset` очищает журнал, иначе повторный запуск ничего не отправит.

## Деплой на сервер (DigitalOcean и др.) с HTTPS

Схема: Caddy принимает HTTPS (сам получает и продлевает сертификат Let's Encrypt) → nginx с фронтендом → Node → Postgres. Всё запускается в Docker одной командой. Нужно: сервер с Ubuntu (хватит самого маленького дроплета), **домен** и **почтовый сервис** для писем с кодами входа.

### Что подготовить заранее

1. **Домен.** В DNS добавьте A-запись домена (например, `family.example.com`) на IP сервера. Сертификат выдаётся на домен, на голый IP нормальный не получить. Без покупки домена для адреса приложения подойдут бесплатные `ваш-ip-через-дефисы.sslip.io` (для 203.0.113.10 это `203-0-113-10.sslip.io`, общие лимиты Let's Encrypt могут помешать) или постоянное имя на DuckDNS (`имя.duckdns.org`). Проверка, что запись заработала: `getent hosts family.example.com` должен показать IP сервера (изменения DNS доходят от нескольких минут до часа).
2. **Почтовый сервис.** Вход и регистрация только по коду из письма, без рабочей почты никто не войдёт. Нужны данные SMTP: хост, порт, логин, пароль и адрес отправителя. DigitalOcean может блокировать исходящий SMTP на портах 25, 465 и 587, поэтому берите сервис, у которого есть порт 2525 (Mailgun, Postmark, Brevo, SendGrid, SendPulse и др.). **Адрес отправителя (`SMTP_FROM`) должен быть на вашем домене, подтверждённом в этом сервисе через записи DKIM и SPF в DNS:** сервисы не разрешают отправлять «от имени» `@gmail.com` и подобных адресов (защита DMARC). Поэтому для почты нужен собственный домен, где можно добавлять любые DNS-записи; на бесплатных поддоменах вроде DuckDNS это невозможно.
3. **Доступ к репозиторию** с сервера: если репозиторий приватный, добавьте на сервере ключ доступа (deploy key) или используйте токен.

### Первый запуск, по шагам

Подключитесь к серверу: `ssh root@IP-СЕРВЕРА`.

```bash
# 1. Docker (в комплекте идёт Compose, нужна версия 2.24 или новее)
curl -fsSL https://get.docker.com | sh
docker compose version

# 2. Брандмауэр: открыты только SSH, HTTP и HTTPS
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow 443/udp
ufw --force enable

# 3. Код
git clone АДРЕС-РЕПОЗИТОРИЯ family-tasks
cd family-tasks

# 4. Настройки
cp .env.example .env
nano .env
```

В `.env` заполните (остальное оставьте как есть):

```bash
COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml   # продакшен-режим с Caddy: после этого команды ниже короткие
COMPOSE_PROFILES=                                         # пусто: Mailpit (локальная почта) в продакшене не нужен
DOMAIN=family.example.com

POSTGRES_PASSWORD=...        # длинный пароль; без знаков / + = @ : (они ломают подключение), лучше hex: openssl rand -hex 24

SMTP_HOST=smtp.example.com
SMTP_PORT=2525
SMTP_USER=...
SMTP_PASS=...
SMTP_FROM="Семейные задачи <noreply@family.example.com>"

VAPID_PUBLIC_KEY=...         # ключи для push-уведомлений, создайте командой ниже и больше не меняйте
VAPID_PRIVATE_KEY=...
VAPID_SUBJECT=mailto:вы@example.com   # ваш настоящий адрес
```

Пароль БД и ключи VAPID можно не вписывать руками, а создать и подставить в `.env` командами (выполняйте один раз; ключи потом менять нельзя):

```bash
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=$(openssl rand -hex 24)|" .env
```

```bash
docker run --rm node:22-alpine npx --yes web-push generate-vapid-keys --json > /tmp/vapid.json && PUB=$(python3 -c "import json;print(json.load(open('/tmp/vapid.json'))['publicKey'])") && PRIV=$(python3 -c "import json;print(json.load(open('/tmp/vapid.json'))['privateKey'])") && sed -i "s|^VAPID_PUBLIC_KEY=.*|VAPID_PUBLIC_KEY=$PUB|; s|^VAPID_PRIVATE_KEY=.*|VAPID_PRIVATE_KEY=$PRIV|" .env && rm /tmp/vapid.json
```

Запуск:

```bash
docker compose up -d --build
docker compose ps                  # все сервисы должны быть Up
docker compose logs -f caddy       # видно, как выпускается сертификат (Ctrl+C, чтобы выйти)
```

Через минуту приложение открывается по `https://ВАШ-ДОМЕН`. Проверьте вход: введите email, письмо с кодом должно прийти. Миграции БД применяются сами при старте сервера. Если сборка обрывается словом `Killed`, серверу не хватает памяти: создайте файл подкачки (`fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile`) и повторите запуск.

### Обновление

На сервере одна команда:

```bash
cd family-tasks
./update.sh
```

Скрипт по порядку:
1. забирает свежий код (`git pull` без слияний; если на сервере менялись файлы проекта, остановится и скажет об этом);
2. делает резервную копию БД в `backups/` (хранятся последние 14; нужно, потому что миграции при откате кода сами не откатываются);
3. пересобирает и перезапускает контейнеры (миграции БД применяются сами при старте сервера);
4. проверяет, что сервер и база отвечают, и (если задан `DOMAIN`) что сайт открывается по HTTPS;
5. удаляет устаревшие образы Docker.

Если после обновления сервер не поднялся, скрипт покажет последние строки лога и готовую команду отката на предыдущую версию. Он также предупредит, если в обновлении изменился шаблон `.env.example` (нужно добавить новые переменные в свой `.env`, затем снова `./update.sh`) или появились миграции. Сначала на сервере должны быть выполнены шаги из «Первого запуска». Если на сервере ещё нет самого `update.sh` (код склонирован до его появления), один раз выполните `git pull`.

Параметры: `./update.sh --no-backup` (без копии БД, быстрее), `./update.sh --help`.

Чтобы выкатить изменения с вашего компьютера: сначала `git push origin main`, затем на сервере `./update.sh`.

### Повседневные команды

```bash
docker compose ps                         # состояние
docker compose logs -f server             # логи приложения (ошибки отправки писем и уведомлений тут)
docker compose logs -f caddy              # логи HTTPS и сертификатов
docker compose restart server             # перезапустить один сервис
docker compose down                       # остановить всё (данные сохраняются)
docker compose up -d                      # запустить снова
```

**Не используйте `docker compose down -v`**: флаг `-v` удаляет тома, то есть всю базу (`pgdata`) и сертификаты (`caddy_data`).

### Резервная копия и восстановление БД

`./update.sh` сам делает копию БД перед каждым обновлением и кладёт в `backups/` (файлы `db-ДАТА.sql.gz`, последние 14). Копию можно снять и вручную:

```bash
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' | gzip > backup-$(date +%F).sql.gz
```

Храните копии и вне сервера (например, скачивайте на свой компьютер через `scp`): при потере сервера копии рядом с ним пропадут вместе с ним.

**Восстановление** заменяет всё, что сейчас есть в базе. Сервер приложения на это время останавливается (иначе он держит соединения с базой):

```bash
docker compose stop server
docker compose exec -T db sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
gunzip -c backups/db-ДАТА.sql.gz | docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -q -v ON_ERROR_STOP=1' > /dev/null
docker compose start server
```

Порядок проверен: после потери данных и восстановления возвращаются те же участники, задания и семьи, сервер запускается без ошибок.

### Если что-то не работает

- **Нет сертификата, браузер ругается.** `docker compose logs caddy`. Чаще всего домен ещё не указывает на сервер (`getent hosts ДОМЕН` должен показать IP сервера) или закрыт порт 80 или 443 (помимо `ufw` на сервере в панели DigitalOcean может быть подключён Cloud Firewall: Networking → Firewalls, там тоже должны быть открыты 80 и 443). Исправьте и перезапустите: `docker compose restart caddy`.
- **Письма с кодом не приходят.** `docker compose logs server | grep -i "email"`: там будет причина (неверный пароль SMTP, заблокированный порт). Проверьте `SMTP_*` в `.env`, после правки `docker compose up -d`.
- **Не работают уведомления.** Нужен HTTPS, заполненные `VAPID_*` и включение в «Настройки» → «Уведомления». На iPhone приложение должно быть добавлено на экран «Домой». Подробнее в разделе про push выше.
- **Сервер не стартует после смены пароля БД.** Пароль применяется только при создании базы. Для уже созданной БД смените его в самом Postgres или (если данных нет) пересоздайте том.

Лимиты запросов считаются по IP посетителя: nginx берёт его из заголовка `X-Forwarded-For`, но только от прокси внутри Docker, поэтому подделать адрес заголовком нельзя.
