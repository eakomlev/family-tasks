# План: фото в чатах и сервис `media/`

Статус: **план**, ничего не сделано. Решения владельца записаны в конце, открытые вопросы там же.

## Зачем и что именно делаем

Отправка фото в общий и личные чаты: выбрать из галереи или снять камерой, увидеть превью в ленте, открыть на весь экран. Только фото (jpeg), без видео и файлов. Сообщение это либо текст, либо фото, либо фото с подписью.

Закладываем рост числа семей, поэтому файлы живут в **отдельном сервисе `media/` и S3-совместимом хранилище** с самого начала (тот же подход, что у `notifier/` и `scheduler/`: свой каталог, пакет, образ).

## Архитектура

```
браузер ── POST фото ──► server ── внутренний API ──► media ──► S3 (бакет)
   ▲                       │ доступ, квота, строка media в БД      │
   └────── GET /media/…?exp&sig (nginx → media) ◄──────────────────┘
```

| Кто | За что отвечает |
| --- | --- |
| `server` | Кто что может: доступ к чату, квота семьи, строка `media` в БД, связь с сообщением, подпись ссылок. |
| `media/` (новый) | Только байты: принять, проверить, перекодировать (`sharp`: убирает EXIF, защищает от подложенных файлов), сделать превью, положить в S3, отдать. Базы данных нет. |
| S3 | Хранение. В dev и на своём сервере контейнер, в проде можно внешний сервис: меняются только переменные `.env`. |

- **База у `media/` отсутствует.** Размер, ширину и высоту он возвращает при загрузке, а запись о файле хранит `server` (таблица `media`). Нет схемы, которую надо согласовывать с миграциями, и нет чтения чужих таблиц.
- **Раздача.** `media/` сам проверяет подписанную ссылку (HMAC, секрет общий с `server`, срок кратен суткам, поэтому адрес стабилен в течение дня и браузер кэширует). Токен пользователя и БД ему не нужны. Браузер ходит на `/media/…`, nginx проксирует на `media`; позже можно поставить CDN. Без верной подписи ответ 404.
- **Загрузка.** Клиент шлёт фото на `server`, тот проверяет доступ и квоту и стримит файл во внутренний API `media/` (общий секрет в заголовке, наружу не открыт). Для 300 КБ это не нагрузка, зато нет тикетов и второй схемы авторизации. Прямую загрузку по подписанному тикету можно добавить позже.
- **Контракт** `server` ↔ `media` описан общим файлом-образцом в `contracts/` (как у очереди), его проверяют тесты обоих пакетов; типы дублируются, код друг друга пакеты не импортируют.
- **Если `media/` не запущен:** текст в чатах работает, фото не отправляются и не показываются (в ленте заглушка). `update.sh` ждёт его healthcheck.

### Какое S3

Клиент в `media/`: `@aws-sdk/client-s3` с настраиваемыми `endpoint`, `region`, `bucket`, ключами и `forcePathStyle`, поэтому подойдёт любое S3-совместимое хранилище. Для контейнера кандидаты:
- **SeaweedFS** (`weed server -s3`): один контейнер, S3 API включается флагом, ключи из файла настроек. Предварительно мой выбор для dev и тестов.
- **Garage**: очень лёгкий, но требует разовой настройки схемы кластера (`garage layout …`), что усложняет автозапуск.
- **MinIO**: у бесплатной версии в 2025 году изменилась модель распространения (насколько мне известно), на долгий срок не выбираю.
- **Внешний S3** (Yandex Object Storage и подобные): для прода, если не хочется держать хранилище самим.

Окончательный выбор делаем в начале фазы 0 коротким опытом: поднять кандидата в Docker, пройти полный цикл `put/get/delete` из `media/`, убедиться, что образ доступен и стартует без ручных шагов. Тесты `media/` идут на настоящем S3 в контейнере (по аналогии с БД в тестах), поэтому CI тоже поднимает сервис.

## Размеры и обработка

- **Клиент** уменьшает фото до длинной стороны 1600 px (JPEG ~0,8, 150–400 КБ) и делает превью 480 px через canvas, как уже сделано для аватаров (`lib/image.ts`); это экономит трафик. HEIC с iPhone Safari декодирует сам.
- **`media/`** не доверяет клиенту: принимает `image/jpeg` до 3 МБ, проверяет сигнатуру и размеры, перекодирует в JPEG (убирает EXIF с геопозицией, поворачивает по ориентации), строит превью 480 px и полноразмерный вариант до 1600 px сам. Клиентское превью нужно только для мгновенного показа до ответа.
- **Лимиты:** файл до 3 МБ, на семью, например, 2 ГБ суммарно (`413 media_quota`), загрузка под строгим лимитом запросов.

## Модель данных (server)

Миграция в `server/migrations`:
- `media (id uuid, family_id, uploader_id, mime, size, width, height, created_at, attached_at null)`; ключи объектов в S3 выводятся из `id` (`<family>/<id>/full.jpg` и `thumb.jpg`), в БД не хранятся.
- `messages.media_id uuid null references media`, а ограничение на текст меняется на «текст 1–2000 знаков **или** `media_id` не пуст».
- Совместимость со старым клиентом: сообщение с фото без подписи приходит с `text = '📷 Фото'` (заглушка), и старая версия не покажет пустой пузырь.

## Поток отправки (два шага)

1. `POST /api/chats/:chat/media` (сырой `image/jpeg`): `server` проверяет доступ к чату и квоту, передаёт байты в `media/`, получает `{width, height, size}`, пишет `media` (`attached_at null`), возвращает `{mediaId}`.
2. `POST /api/chats/:chat/messages` с `{text?, mediaId}`: в одной транзакции проверяет, что медиа загрузил этот участник в этой семье и оно ещё не прикреплено, ставит `attached_at`, пишет сообщение. Дальше как у текста: сигнал сокета `chat`, уведомление.

**Сироты** (загружено, но не прикреплено более суток) убирает ночная уборка в `server` (рядом с очисткой сессий): удаляет строку и просит `media/` удалить объекты. Файлы удалённых семей чистит та же уборка (ищет объекты без строки).

## Остальные места

- **Push и превью списка чатов:** «📷 Фото» (с подписью: «📷 подпись»), тексты в `chat.ts`.
- **Реакции и монеты** работают на сообщении с фото как на обычном; долгое нажатие остаётся, обычное нажатие на фото открывает просмотр.
- **Просмотр на весь экран:** затемнение, `contain`, закрытие нажатием или Escape, кнопка «Сохранить».
- **Лента:** размеры известны заранее (`width`/`height`), лента не прыгает; ленивая загрузка.
- **Права:** отправлять фото могут все, кто может писать в чат.
- **Резервные копии:** `update.sh` копирует только БД, а фото лежат в S3. Для контейнерного S3 копия тома (`tar`, последние N), для внешнего S3 версионирование бакета у провайдера. Без этого фото пропадают вместе с диском.
- **Конфигурация:** `.env`: `MEDIA_SECRET` (подпись ссылок), `MEDIA_INTERNAL_TOKEN` (вызовы `server` → `media`), `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION`. В compose `media` и S3 без публикации портов; наружу только `/media/` через nginx. Новый `location` с `add_header` подключает `security-headers.conf`; CSP не меняется (`img-src 'self'`). Для загрузки поднять `client_max_body_size` у маршрута `/api/chats/*/media`.

## Риски

- **Приватность фото детей.** Подписанные ссылки, срок, нет листинга файлов, `Cache-Control: private`. Утёкшая ссылка работает до конца окна подписи; сокращаем срок, если это важно. S3 не публикует порты наружу и не разрешает анонимный доступ.
- **Больше движущихся частей:** `media/`, хранилище, секреты, копии. Поэтому отдельная фаза эксплуатации и healthcheck в `update.sh`.
- **Выбор S3-контейнера** нужно подтвердить опытом (фаза 0): образ доступен, стартует без ручных шагов, ведёт себя как S3 по тестам.
- **Песочница агента:** сборка образа падает на `npm ci` из-за TLS-прокси (приём с временным Dockerfile описан в `CLAUDE.md`); у `sharp` ещё и нативный бинарник, проверим на Alpine (musl).
- **Расхождение версий при выкладке:** заглушка «📷 Фото» в `text` и порядок «сначала клиент, потом сервер».
- **iOS и камера:** `<input type="file" accept="image/*">` без `capture` даёт «Снять фото / Медиатека»; на реальном iPhone не проверялось.

## Что не входит

- Видео, голосовые, произвольные файлы, несколько фото в одном сообщении.
- Удаление и редактирование сообщений (когда появятся, удаление должно убирать и объекты в S3).
- Модерация изображений.

## Решения владельца

1. Отдельный сервис `media/` с самого начала.
2. Хранилище S3-совместимое с самого начала.

3. **Одно фото** в сообщении на первой версии?
4. **Подпись к фото** нужна (текст вместе с фото)? Рекомендую да.
