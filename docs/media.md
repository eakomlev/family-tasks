# Медиа (`media/`)

> Обработка и выдача фото, файлов и видео, внешнее S3-хранилище. Общая карта проекта и правила: [CLAUDE.md](../CLAUDE.md). Ссылки «раздел ниже» в тексте относятся к этому файлу или к соседним файлам в `docs/`.


Фазы 0–3 плана `docs/chat-photos-plan.md`: отдельный пакет и контейнер для фото из чатов (в `server` подключён, см. «Фото в чатах» в разделе про сервер; клиент см. «Фото в чатах» в разделе про клиент). Принимает JPEG от `server`, перекодирует, хранит в S3-совместимом хранилище и отдаёт по подписанным ссылкам. Базы данных нет: записи о файлах ведёт `server`. Код пакетов друг друга не импортирует, контракт описан образцом `contracts/media-v1.json` (контрольный пример подписи; его проверяют тесты `media` и `server`).

- **Внутренний API** (заголовок `x-internal-token` = `MEDIA_INTERNAL_TOKEN`, наружу nginx его не проксирует): `PUT /internal/media/:family/:id` (тело `image/jpeg`, ответ `{width, height, size, thumbSize}`; не JPEG или битый файл 422 `invalid_image`, слишком большой 413, другой тип 415), `DELETE /internal/media/:family/:id` (204, повтор безопасен), `GET /internal/media/:family` (`{items:[{id,size}]}` для уборки сирот), `DELETE /internal/families/:family`. Идентификаторы только uuid (иначе 400): в ключ не попадает произвольный путь.
- **Обработка** (`src/image.ts`): принимается только JPEG (сигнатура), перекодируется через `sharp`: ориентация применяется к пикселям, EXIF (геопозиция) пропадает, полный вариант до 1600 px (качество 82), превью до 480 px (75), без увеличения; защита от огромных картинок (50 Мпикс). Ключи в хранилище `<семья>/<файл>/full.jpg` и `thumb.jpg`.
- **Раздача** `GET /media/:family/:id/(full|thumb)?exp=&sig=`: `sig` это hex HMAC-SHA256 от `семья/файл/срок` секретом `MEDIA_SECRET` (`src/sign.ts`), срок в секундах Unix не в прошлом и не дальше 3 суток. Любая ошибка (подпись, срок, чужая семья, нет файла, неизвестный вариант) даёт один и тот же 404, по ответу ничего не узнать. `Cache-Control: private, max-age` до конца подписи (не больше суток), `ETag` и `304`. nginx проксирует только `/media/` (`web/nginx.conf`, `$media_upstream`).
- **Хранилище** (`src/store.ts`, интерфейс `BlobStore`: `put/get/delete/list/ping`): клиент `@aws-sdk/client-s3`, настройки `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION`, `S3_FORCE_PATH_STYLE`; значения без запасных в compose, без них `media` не стартует. У разработки отдельный бакет (локальный `.env`), у сервера свой. Бакет создаётся в кабинете рег.ру вручную; `media` при старте проверяет его и повторяет попытки (до двух минут), healthcheck (`GET /health`) проверяет бакет, `update.sh` ждёт `media` до трёх минут. Перенос с прежнего контейнера SeaweedFS сделан `rclone copy` (разово).
- **Настройки:** `MEDIA_SECRET` (подпись ссылок, после смены старые ссылки не открываются), `MEDIA_INTERNAL_TOKEN`, `MEDIA_MAX_UPLOAD_BYTES` (3 МБ), `PORT`. Без обязательных переменных сервис не стартует. В `.env.example` значения `change-me-…` для разработки, в проде задайте свои (`openssl rand -hex 32`).
- **Тесты** (`media/tests/`, Vitest): нужен S3: по умолчанию SeaweedFS на `localhost:8333` (одноразовая команда `docker run` в README, раздел про фото; контейнера в compose нет, адрес и ключи по умолчанию в `tests/s3.ts`, свой бакет `media-test`) или любой бакет через `S3_TEST_ENDPOINT`, `S3_TEST_ACCESS_KEY`, `S3_TEST_SECRET_KEY`, файлы идут по очереди; `unit/` подпись и обработка, `api/` хранилище и API на настоящем S3. Запуск: `npm run test:media` из корня или `npm test` в `media/`, типы `npm run typecheck`. CI: задание `media` (S3 поднимается `docker run` перед тестами: сервисы GitHub Actions не позволяют задать команду контейнера).
- **Копии и состояние** (фаза 3): `update.sh` фото не копирует (хранилище внешнее, копии бакета настраивайте у провайдера или `rclone`; прежнее копирование тома `s3` удалено). Копии БД и фото берите парой. `GET /api/admin/media` (`MediaStats`: `configured`, `alive` по `MediaClient.health()` = `GET /health` сервиса, `photos`, `bytes`, `unattached`, `quotaBytes`, `busiestFamilyBytes`; не администратору 404, без токена 401) и блок «Фото в чатах» на `/profile/service` (`useGetMediaStatsQuery`, опрос раз в 30 секунд, `mediaAlerts`: фото не настроены → пояснение, сервис не отвечает → ошибка, семья от 80% квоты → предупреждение, от 100% → ошибка; `formatBytes`). В тестах `server` таблица `media` общая: проверяйте нижние границы.
- **Проверка:** сервис проверен в Docker (образ на Alpine, `sharp` работает, `media` ждёт хранилище и становится healthy) и через nginx (фото открывается по верной подписи, при плохой 404, `/internal/` снаружи недоступен).
- **Ресурсы** (26 октября 2026). В `docker-compose.yml` у контейнеров есть потолок памяти (`mem_limit`: `db` 2 ГБ, `server` и `media` по 1 ГБ, `notifier`, `realtime`, `scheduler` по 256 МБ, `web` и `caddy` по 128 МБ), у `media` ещё `cpus: 2`. Замер сжатия в контейнере (Docker Desktop, свой тестовый ролик): 1080p, 60 секунд, 62 МБ: ffmpeg работает около 10 секунд; 4K, 12 секунд, 99 МБ: около 5 секунд; без ограничения потоков пик памяти 370 МБ и 670 МБ, при 512 МБ ffmpeg убивался; с `-threads 2` около 190 МБ на 1080p. Остальное время загрузки видео это отправка результата в S3 (на домашней сети около полутора минут, на сервере быстрее). У ffmpeg `-threads` и `-filter_threads` из `MEDIA_FFMPEG_THREADS` (по умолчанию 2) и предел времени `MEDIA_FFMPEG_TIMEOUT_SECONDS` (240). Если ffmpeg убит сигналом (нехватка памяти) или остановлен по времени, `media` отвечает 422 `video_failed` (а не `invalid_video`), `server` отдаёт клиенту 400 `video_failed` («Не удалось обработать это видео. Попробуйте более короткое.»). Проверить такое сжатие можно так: собрать образ (`docker build -t ft-media-test media`), запустить с `--memory 1g --cpus 2` и положить ролик `PUT /internal/videos/<семья>/<id>` с заголовком `x-internal-token` (скрипты замера лежат во временных файлах, не в репозитории).
