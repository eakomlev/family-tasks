# План: логирование и журнал на странице «Сервис»

Статус: **план**, ничего не сделано. Обновляйте таблицу фаз по мере выполнения. Открытые вопросы в конце ждут решения владельца.

## Зачем

1. История логов переживает выкладки.
2. Её можно смотреть и скачивать на странице «Сервис» (только администратору, `ADMIN_EMAILS`).
3. В журнале то, что нужно для разбора: ошибки сервера и клиента и важные события, а не каждый запрос.

## Как сейчас (на 13 октября 2026)

- Сервер пишет JSON-строки (pino) только в стандартный вывод контейнера. Каждый запрос даёт две строки уровня info (`incoming request`, `request completed`); предупреждений и ошибок за сутки на боевом сервере не было.
- Драйвер Docker `json-file` у всех контейнеров **без ротации** (`LogConfig: {Type: json-file, Config: {}}`). Файлы пока маленькие (40–70 КБ), но диск 9,8 ГБ, и размер не ограничен.
- **История теряется при каждой выкладке:** `update.sh` пересоздаёт контейнеры, а Docker-журнал живёт вместе с контейнером.
- Проверки `/api/health` (от `update.sh` и мониторинга) пишутся как обычные запросы.
- Ошибок клиента нет вообще: упавший экран или запрос видны только по слову пользователя.
- Точечные `app.log.error` есть в `routes.ts` (письма, база), `roblox.ts`; общий обработчик ошибок в `app.ts` пишет 5xx и отвечает клиенту `{error: 'internal_error'}`.

## Решение

**Хранить в Postgres, таблица `app_logs`**, плюс прежний вывод в Docker с ротацией.

- Таблица: `id` (bigserial, курсор для постраничной выдачи), `ts` (timestamptz), `level` (`info`/`warn`/`error`), `source` (`server`/`client`), `event` (короткий код: `server_started`, `family_created`, `login_failed`, `http_5xx`, `client_error` …), `message`, `context` (jsonb), `member_id`, `family_id` (без внешних ключей: журнал не должен пропадать вместе с семьёй), `request_id`, `app_version`.
- Индексы: `(ts desc)`, `(level, ts desc)`, `(source, ts desc)`, по `event`.
- Приёмник логов сервера: поток для pino (multistream рядом со stdout), собирает записи пачками (раз в 2 секунды или по 50 штук), пишет одним `insert`. Ошибка записи глотается, очередь ограничена 1000 записей (старые отбрасываются), журнал не логирует сам себя.
- Что пишется в таблицу: записи уровня warn и error, медленные запросы (больше 2 секунд, warn), ответы 5xx (error), и **события** через помощник `logEvent(event, context)` (уровень info). Остальные запросы в таблицу не идут.
- Версия: переменная сборки (`GIT_SHA` из `update.sh`) попадает в `/api/health`, в запись `server_started` и в каждую запись журнала: видно, какая выкладка что поменяла.

### События (первый набор)

`server_started` (с версией), `family_created`, `member_joined`, `login` и `login_failed` (с причиной: неверный код, исчерпаны попытки, выбор семьи), `email_code_failed`, `goal_purchased`, `push_failed` и `push_subscription_removed` (404 или 410), `roblox_failed`, `rate_limited` (429, склеивается по IP за минуту), `session_expired` (чистка), `admin_logs_exported`.

### Данные и приватность

- **Не пишем:** тексты сообщений, коды из писем, токены и заголовок `Authorization`, тела запросов, data URL картинок.
- Email маскируем (`e***@gmail.com`), участников и семьи пишем по id, IP только в событиях безопасности (вход, лимиты).
- Срок хранения: ошибки и предупреждения 90 дней, события 30 дней. Очистка раз в сутки той же задачей, что и чистка сессий. Жёсткий потолок 200 тысяч строк (при превышении удаляются самые старые info).

### Ошибки клиента

- Открытый эндпоинт `POST /api/client-log` (нужен и без входа: сбой может случиться на экране входа или при загрузке). Его надо **добавить в список открытых маршрутов** (`tests/api/security.test.ts` закрепляет этот список).
- Защита от спама: лимит 20 в минуту с IP (строгий лимит), размер тела до 4 КБ, склейка одинаковых ошибок (хэш сообщения и маршрута) за минуту, суточный потолок клиентских записей 2000, срок хранения как у ошибок.
- Что шлёт приложение (`lib/reportError.ts`): `window.onerror`, `unhandledrejection`, ошибки `ErrorBoundary`, ответы API 5xx и обрывы сети (кроме 4xx, которые ожидаемы). В запись: сообщение, стек (обрезанный), маршрут, версия приложения, user agent, id участника, если известен.
- Не слать из самого репортера (защита от цикла), очередь в памяти ограничена.

### Страница «Журнал» в «Сервисе»

- Маршрут `/profile/service/logs`, ссылка с карточки «Сервис»; в «Сервисе» карточка «ошибок за 24 часа» и время последней.
- Фильтры: уровень (все, предупреждения и выше, только ошибки), источник (сервер, клиент), период (1 час, 24 часа, 7 дней, 30 дней), поиск по `event` и `message`.
- Список новыми сверху, подгрузка по курсору (`before=<id>`), строка раскрывается и показывает контекст JSON; время в местном часовом поясе.
- «Скачать»: `GET /api/admin/logs/export?from&to&level&source&format=ndjson|csv` потоком, не больше 50 тысяч строк, `Content-Disposition`. Запрос идёт с заголовком `Authorization` (обычная ссылка не годится), файл собирается из ответа. На iPhone в режиме приложения скачивание работает хуже: дополнительно кнопки «Скопировать выбранное» и «Поделиться».
- Авто-обновление раз в 30 секунд, пока страница открыта (как у статистики).

## Риски и меры

- **Запись в базу не должна ломать приложение:** ошибки глотаются, очередь ограничена, логгер не пишет сам в себя.
- **Спам на `/api/client-log`:** лимиты, склейка, суточный потолок; без входа записи помечаются `anonymous`.
- **Объём:** сейчас сотни записей в сутки, десятки МБ за год; потолок строк и срок хранения закрывают худший случай.
- **Двойное хранение:** то, что пишется в таблицу, остаётся и в Docker-журнале (с ротацией), это нормально для разбора на сервере (`docker compose logs`).
- **Скачивание на iPhone:** см. выше, запасной путь «Поделиться».
- **Часовые пояса:** в базе UTC, показываем в местном; фильтр «период» считает клиент.
- **Согласие семьи:** сбор ошибок клиента фиксирует маршрут, версию, user agent и id участника без текстов сообщений; это стоит упомянуть в README.
