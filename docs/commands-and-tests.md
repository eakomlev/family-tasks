# Команды, тесты и CI

> Запуск проекта, демо-данные, проверки типов и сборки, тесты сервера и веба, CI. Общая карта проекта и правила: [CLAUDE.md](../CLAUDE.md). Ссылки «раздел ниже» в тексте относятся к этому файлу или к соседним файлам в `docs/`.


Полный стек в Docker на своём компьютере (http://localhost:8080, без HTTPS):

```bash
cp .env.example .env
docker compose up --build -d
docker compose down
```

Локальная разработка одной командой (БД и Mailpit в Docker, сервер и сервис отправки через tsx watch, Vite с HMR; скрипты в корневом `package.json`, зависимость только `concurrently`):

```bash
npm run setup   # один раз
npm run dev     # npm run dev:stop выключает БД и Mailpit
```

Демо-данные для проверки интерфейса (мама, папа, двое детей с расписаниями и заданиями; нужна запущенная БД, `npm run dev:infra`):

```bash
npm run seed                      # создать демо-семью (прежнюю демо-семью заменяет, остальное не трогает)
npm run seed -- --snippet Миша    # JS для консоли браузера: войти под этим участником (семью не пересоздаёт)
npm run seed -- --existing --json # токены сессий для curl и скриптов
```

Скрипт `server/scripts/seed.ts`, отказывается работать на нелокальной БД. Для агента есть проектный скил `.claude/skills/seed-demo-family` (участники, порядок входа в браузер, ловушки).

Service worker в dev выключен (в `vite.config.ts` нет `devOptions`), PWA и push проверяйте на сборке. Если порт 5173 занят, Vite молча берёт следующий, смотрите адрес в выводе. Порт 8025 (Mailpit) занят и в полном Docker-стеке, поэтому одновременно запускать оба режима нельзя.

Проверки типов и сборки:

```bash
cd web && npx tsc -b && npm run lint && npm test && npm run build
cd server && npx tsc --noEmit
```

Тесты сервера (Vitest, `server/tests/`): нужна запущенная БД (`npm run dev:infra`); тесты работают в **отдельной базе `family_tasks_test`** на том же Postgres, которую создают и мигрируют сами (нелокальный хост отвергается). Запуск из корня или из `server/`:

```bash
npm test                  # все тесты, около 3 секунд
cd server && npx vitest run tests/api/tasks.test.ts   # один файл
cd server && npm run typecheck                        # типы приложения и тестов
```

- `tests/unit/` — чистая логика без БД (повторы заданий, часовые пояса и окна уведомлений, тексты, коды).
- `tests/api/` — API через `app.inject` на настоящей БД (вход, профиль, приглашения, расписания, задания, push). Планировщик уведомлений тестирует `scheduler/tests`. Приложение собирается `buildApp` из `src/app.ts` (без запуска и без общего rate limit); `index.ts` только запускает его.
- Изоляция: файлы идут параллельно, каждый создаёт свою семью (`tests/helpers.ts`: `createFamily`, `api`, `removeFamilies`) и убирает за собой. Не делайте в тестах глобальных `delete` без условия по своим данным.
- Письма и push в тестах не отправляются, а ставятся в таблицу `outbox`, и «отправленное» это её строки (server вообще не отправляет: нет ни SMTP, ни `web-push`). Push читают `sentTo(endpoints)` (асинхронный: `await sentTo([...])`), `resetSent()` (очистка между тестами только по подпискам своего файла) и `subscribe` из `tests/webpush.ts`; письма с кодами читают из `outbox` напрямую (`auth.test.ts`: `lastCode`, `sentTo`). Параллельные файлы делят таблицу, поэтому всегда фильтруйте по своим адресам и подпискам; перед прогоном `globalSetup` очищает `outbox`. Настоящая доставка, ошибки провайдеров и повторы проверяются в `notifier/tests`. Сбой очереди проверяйте так: `vi.spyOn(outbox, 'enqueue').mockRejectedValueOnce(...)` (`import * as outbox from '../../src/outbox/index.js'`). Публичный ключ VAPID в тестах фиктивный (`vitest.config.ts`): серверу он нужен только как признак «push включён».
- Ловушки Vitest 5: `beforeEach(() => mock.mockReset())` без фигурных скобок возвращает функцию, и Vitest вызывает её как очистку после теста (пишите `beforeEach(() => { ... })`); счётчик вызова подмены при загрузке модуля к началу теста уже обнулён (для такой проверки перезагружайте модуль в отдельном файле, `push-setup.test.ts`).
- Ключи VAPID на время прогона генерируются в `vitest.config.ts`.
- Проверка, что тесты ловят ошибки: вносите в код осознанную поломку (например, уберите проверку автора в `tasks/routes.ts`) и убедитесь, что тест краснеет.
- CI (`.github/workflows/ci.yml`, GitHub Actions): на каждый пуш в `main` и pull request задания: сервер (`npm ci`, `npm run typecheck`, `npm test` с сервисом Postgres 17; адрес задаёт `DATABASE_URL`, тестовую базу тесты создают сами), сервис отправки и планировщик (то же в `notifier/` и `scheduler/`), фронтенд (`npx tsc -b`, `npm run lint`, `npm test`, `npm run build`) и конфигурация (`bash -n update.sh`, `docker compose config` для обычного и продакшен-режима, валидация `Caddyfile`). Любое изменение, которое надо проверять в CI, сначала воспроизводите локально теми же командами в чистой копии без `.env`. Названия заданий с двоеточием в YAML берите в кавычки.

Тесты фронтенда (`web/tests/`, Vitest + jsdom + Testing Library; БД и сервер не нужны):

```bash
npm run test:web                 # из корня; npm test запускает сервер и фронтенд подряд
cd web && npx vitest run tests/components/TaskEditor.test.tsx
```

- `tests/unit/` — чистая логика (даты, повторы и сортировка заданий, выбор дня на «Моём дне», черновики расписаний, тема, тексты ошибок); `tests/api/` — клиент API с подменой `fetch`; `tests/hooks/` — страницы (`TaskView`: отметка и поздравление); `tests/components/` — компоненты (`TaskItem`, `CodeStep`, `TaskEditor`). `tests/helpers.ts` — фабрики `task()` и `occ()`.
- Часовой пояс прогона фиксирован (`Europe/Moscow` в `vitest.config.ts`), даты в тестах строятся от понедельника 12 октября 2026. Отдельный конфиг `vitest.config.ts` без PWA-плагина; `tsconfig.tests.json` подключён в `tsc -b`, так что типы тестов проверяются вместе со сборкой.
- Ловушки: с `vi.useFakeTimers` не работают `userEvent` и `findBy*`/`waitFor` (используйте `fireEvent` и `act` с `advanceTimersByTimeAsync`; обратный отсчёт в `CodeStep` перезапускает таймер после каждого рендера, поэтому секунды отсчитывайте по одной); у метки поля с подсказкой (`Field` с `hint`) имя длиннее названия, ищите по `/^Дата/`; тело `Response` читается один раз, подмену `fetch` для нескольких запросов делайте фабрикой.
- Страницы целиком (роутинг, провайдеры) автотестами не покрыты, их проверяют вручную и скилом `seed-demo-family`.

Обновление на сервере: `./update.sh` (подробнее в разделе «Деплой и эксплуатация»).
