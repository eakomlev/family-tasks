# Моя семья (Family Tasks)

PWA для семьи: задания, расписание уроков и тренировок детей, дни рождения, уведомления. Монорепозиторий без workspaces: у `web/` и `server/` свои `package.json` и `node_modules`. Язык интерфейса и сообщений об ошибках для пользователя — русский, комментарии в коде тоже на русском.

- `web/` — React 19 + Vite 8 + TypeScript, стили на `styled-components`, PWA через `vite-plugin-pwa`, роутинг `react-router-dom`, данные на устройстве в IndexedDB (`idb-keyval`). Алиас `@/` → `web/src` (vite + `paths` в tsconfig).
- `server/` — Node 22 + Fastify 5 + `pg`, TypeScript (ESM, `NodeNext`, импорты с суффиксом `.js`).
- PostgreSQL 17, всё упаковано в Docker: nginx (раздаёт `web/dist`, проксирует `/api/` на `server:3000`) + server + db. В проде перед ними Caddy с HTTPS. Письма: `nodemailer` по SMTP, в dev Mailpit (профиль compose `dev-mail`, UI на :8025).

## Команды

Полный стек в Docker на своём компьютере (http://localhost:8080, без HTTPS):

```bash
cp .env.example .env
docker compose up --build -d
docker compose down
```

Локальная разработка одной командой (БД и Mailpit в Docker, сервер через tsx watch, Vite с HMR; скрипты в корневом `package.json`, зависимость только `concurrently`):

```bash
npm run setup   # один раз
npm run dev     # npm run dev:stop выключает БД и Mailpit
```

Демо-данные для проверки интерфейса (мама, папа, двое детей с расписаниями и заданиями; нужна запущенная БД, `npm run dev:infra`):

```bash
npm run seed                      # создать демо-семью (прежнюю демо-семью заменяет, остальное не трогает)
npm run seed -- --snippet Миша    # JS для консоли браузера: войти под этим участником (семью не пересоздаёт)
npm run seed -- --existing --json # токены сессий для curl и скриптов
```

Скрипт `server/scripts/seed.ts`, отказывается работать на нелокальной БД. Для агента есть проектный скил `.claude/skills/seed-demo-family` (участники, порядок входа в браузер, ловушки).

Service worker в dev выключен (в `vite.config.ts` нет `devOptions`), PWA и push проверяйте на сборке. Если порт 5173 занят, Vite молча берёт следующий, смотрите адрес в выводе. Порт 8025 (Mailpit) занят и в полном Docker-стеке, поэтому одновременно запускать оба режима нельзя.

Проверки типов и сборки:

```bash
cd web && npx tsc -b && npm run lint && npm test && npm run build
cd server && npx tsc --noEmit
```

Тесты сервера (Vitest, `server/tests/`): нужна запущенная БД (`npm run dev:infra`); тесты работают в **отдельной базе `family_tasks_test`** на том же Postgres, которую создают и мигрируют сами (нелокальный хост отвергается). Запуск из корня или из `server/`:

```bash
npm test                  # все тесты, около 3 секунд
cd server && npx vitest run tests/api/tasks.test.ts   # один файл
cd server && npm run typecheck                        # типы приложения и тестов
```

- `tests/unit/` — чистая логика без БД (повторы заданий, часовые пояса и окна уведомлений, тексты, коды).
- `tests/api/` — API через `app.inject` на настоящей БД (вход, профиль, приглашения, расписания, задания, push, планировщик). Приложение собирается `buildApp` из `src/app.ts` (без запуска и без общего rate limit); `index.ts` только запускает его.
- Изоляция: файлы идут параллельно, каждый создаёт свою семью (`tests/helpers.ts`: `createFamily`, `api`, `removeFamilies`) и убирает за собой. Не делайте в тестах глобальных `delete` без условия по своим данным.
- Почта (`src/mail.js`) и `web-push` подменяются (`vi.mock`), настоящих писем и запросов к push-сервисам нет; отправленное проверяется через `tests/webpush.ts` (`sentTo`, `subscribe`). Подписки других файлов в той же БД игнорируйте, фильтруя по своим адресам.
- Ловушки Vitest 5: `beforeEach(() => mock.mockReset())` без фигурных скобок возвращает функцию, и Vitest вызывает её как очистку после теста (пишите `beforeEach(() => { ... })`); счётчик вызова подмены при загрузке модуля к началу теста уже обнулён (для такой проверки перезагружайте модуль в отдельном файле, `push-setup.test.ts`).
- Ключи VAPID на время прогона генерируются в `vitest.config.ts`.
- Проверка, что тесты ловят ошибки: вносите в код осознанную поломку (например, уберите проверку автора в `tasks/routes.ts`) и убедитесь, что тест краснеет.
- CI (`.github/workflows/ci.yml`, GitHub Actions): на каждый пуш в `main` и pull request три задания: сервер (`npm ci`, `npm run typecheck`, `npm test` с сервисом Postgres 17; адрес задаёт `DATABASE_URL`, тестовую базу тесты создают сами), фронтенд (`npx tsc -b`, `npm run lint`, `npm test`, `npm run build`) и конфигурация (`bash -n update.sh`, `docker compose config` для обычного и продакшен-режима, валидация `Caddyfile`). Любое изменение, которое надо проверять в CI, сначала воспроизводите локально теми же командами в чистой копии без `.env`. Названия заданий с двоеточием в YAML берите в кавычки.

Тесты фронтенда (`web/tests/`, Vitest + jsdom + Testing Library; БД и сервер не нужны):

```bash
npm run test:web                 # из корня; npm test запускает сервер и фронтенд подряд
cd web && npx vitest run tests/components/TaskEditor.test.tsx
```

- `tests/unit/` — чистая логика (даты, повторы и сортировка заданий, выбор дня на «Моём дне», черновики расписаний, тема, тексты ошибок); `tests/api/` — клиент API с подменой `fetch`; `tests/hooks/` — страницы (`TaskView`: отметка и поздравление); `tests/components/` — компоненты (`TaskItem`, `CodeStep`, `TaskEditor`). `tests/helpers.ts` — фабрики `task()` и `occ()`.
- Часовой пояс прогона фиксирован (`Europe/Moscow` в `vitest.config.ts`), даты в тестах строятся от понедельника 12 октября 2026. Отдельный конфиг `vitest.config.ts` без PWA-плагина; `tsconfig.tests.json` подключён в `tsc -b`, так что типы тестов проверяются вместе со сборкой.
- Ловушки: с `vi.useFakeTimers` не работают `userEvent` и `findBy*`/`waitFor` (используйте `fireEvent` и `act` с `advanceTimersByTimeAsync`; обратный отсчёт в `CodeStep` перезапускает таймер после каждого рендера, поэтому секунды отсчитывайте по одной); у метки поля с подсказкой (`Field` с `hint`) имя длиннее названия, ищите по `/^Дата/`; тело `Response` читается один раз, подмену `fetch` для нескольких запросов делайте фабрикой.
- Страницы целиком (роутинг, провайдеры) автотестами не покрыты, их проверяют вручную и скилом `seed-demo-family`.

Обновление на сервере: `./update.sh` (подробнее в разделе «Деплой и эксплуатация»).

## Миграции БД

`node-pg-migrate`, SQL-файлы в `server/migrations/` с маркерами `-- Up Migration` / `-- Down Migration`. Сервер применяет их сам при старте (`server/src/migrate.ts`), поэтому в Docker отдельного шага нет. Применённые миграции не редактируем, любое изменение схемы — новый файл:

```bash
cd server && npm run migrate:create -- имя   # migrate:up / migrate:down — вручную
```

Откат кода не откатывает схему, поэтому перед обновлением с миграциями `update.sh` делает копию БД.

## Сервер: архитектура и правила

- **Вход по email + одноразовому коду** (`server/src/auth.ts`, таблица `email_codes`, purpose `signup`/`login`). Код 6 цифр, 10 минут, 5 попыток, повторная отправка раз в 60 с. Ответ на `POST /api/email-codes` одинаков для известного и неизвестного email (при `login` письмо уходит только известным; строка с кодом пишется всегда, чтобы cooldown не выдавал существование адреса). Не меняйте это поведение, не проверив, что оно не начало раскрывать email.
- **Участник** = имя + email (оба уникальны в рамках семьи, email хранится в нижнем регистре) + роль (`mama`/`papa`/`child`). Один email может быть в нескольких семьях: `POST /api/auth/login` отвечает `409 choose_member` с вариантами, код при этом не сжигается и используется повторно со `memberId`. Создатель семьи — только мама или папа, получает `is_owner`; присоединиться по приглашению могут все три роли.
- **Сессии** (`sessions`): по одной на устройство, клиент хранит токен в IndexedDB, в БД SHA-256 хэш, `Authorization: Bearer`. `DELETE /api/session` отзывает только текущую.
- **Приглашения** (`invites`): многоразовые, 7 дней. Новое приглашение удаляет старые (так можно отозвать утёкшую ссылку). Ссылка вида `/join?code=...`. Владелец видит и перевыпускает его на странице семьи.
- **Профиль и фото.** `PATCH /api/me` меняет имя (уникально в семье, иначе `409 name_taken`), фото и дату рождения; email и роль менять нельзя. Дата рождения (`members.birth_date`, тип `date`) ходит строкой `YYYY-MM-DD`: на сервере её всегда читают через `to_char(...)`, на клиенте разбирают вручную (`web/src/lib/date.ts`), потому что `new Date('YYYY-MM-DD')` и драйвер `pg` сдвигают день по часовому поясу. Проверка: реальная дата, не раньше 1900 и не в будущем (запас сутки на пояса), `null` очищает; ошибка `invalid_birth_date`. Фото хранится прямо в `members.avatar` как data URL (jpeg/png/webp, не больше 70 000 символов, ограничено схемой и `check` в БД). Клиент перед отправкой обрезает его до квадрата 128×128 JPEG (`web/src/lib/image.ts`, около 3–10 КБ), поэтому сервер ничего не ресайзит и не должен принимать оригиналы. Фото и дата рождения приходят в `/api/me` для всех участников семьи. Fastify вырезает неизвестные поля (`removeAdditional`) уже после `minProperties`, так что пустой итоговый патч проверяется вручную.
- **Расписание уроков** (`schedule_lessons`, `server/src/schedule.ts`): только у участников с ролью `child`, дни 1–6 (Пн–Сб), у урока предмет и необязательные время начала и конца (окончание строго позже начала), не больше 12 уроков в день. Сохраняется целиком через `PUT /api/members/:id/schedule`; порядок уроков в дне равен порядку в массиве.
- **Расписание тренировок** (`training_sessions`, `server/src/trainings.ts`) устроено так же, но дни 1–7 (Пн–Вс, ISO: воскресенье = 7, в отличие от `Date.getDay()`; помощники в `web/src/lib/weekdays.ts`), у тренировки название, необязательные место и время, не больше 8 в день. `GET/PUT /api/members/:id/trainings`.
- **Доступ к расписаниям** (`server/src/access.ts`, `authorizeChild`): читать и менять может сам ребёнок и любой родитель (мама/папа) его семьи, другие дети получают 403, чужая семья 404, не-ребёнок 400.
- **Задания** (`tasks`, `task_completions`, `server/src/tasks/`). Любой член семьи создаёт задание себе или другому. **Повторяющиеся задания в «Предстоящих»:** список просит `collapse=true`, и у серии остаётся одно текущее вхождение (`from` считается сегодняшним днём): есть вхождение на `from`, оно, выполненное или нет; иначе ближайшее будущее, но только если предыдущее вхождение серии (`previousOccurrence` в `tasks/recurrence.ts`, просмотр назад до 70 дней) не выполнено или его не было; выполненное предыдущее значит, что следующее появится только в свой день. Без `collapse` (блок «Задания на сегодня», карточки детей) список как раньше. **Видимость:** родители видят все задания семьи, ребёнок только свои (назначенные ему и созданные им); это проверяет сервер (`visibility`/`findTask` в `tasks/routes.ts`: список, «выполненные», просмотр, изменение, удаление, отметка), чужое задание ребёнка отвечает 404 как несуществующее. Сигнал сокета `tasks` уходит всей семье (в нём нет данных), а запрошенные после него данные уже отфильтрованы. Менять и удалять (`PUT/DELETE /api/tasks/:id`) может только автор (иначе 403), отмечать выполненным и снимать отметку (`POST /api/tasks/:id/complete|uncomplete`, тело `{date}`) — любой в семье. У задания необязательное описание (`description`, до 1000 символов, обрезается по краям; форма отправляет его целиком, без поля при `PUT` оно очищается). `GET /api/tasks/:id?date=` отдаёт задание и одно его вхождение `occurrence` (по умолчанию первое или «без срока», `null`, если такого вхождения нет). Срок необязателен: без даты это «без срока»; время допустимо только с датой. Повтор `none|daily|weekly|monthly` (`weekly` с днями 1–7, `monthly` на то же число, в коротком месяце на последний день), необязательное `until`. Расписание повторов считает только сервер (`tasks/recurrence.ts`, чистые функции с проверкой на граничных случаях); клиент получает готовые вхождения: `GET /api/tasks?from&to[&collapse=true]` (не больше 62 дней) отдаёт `{tasks, occurrences}`: вхождения периода, невыполненные просроченные разовые и задания без срока; `GET /api/tasks/done` — недавно выполненное. Выполнение хранится по каждому вхождению (`task_completions`, для задания без даты дата-заглушка `1970-01-01`), поэтому повторяющееся задание отмечается отдельно в каждый день; при смене графика отметки сбрасываются, при смене названия сохраняются. Уведомления (`notifyMember` в `push.ts`, тексты в `tasks/text.ts`): исполнителю при создании и изменении (если задание дал не он сам), автору при первой отметке выполнения (если выполнил не он сам). Напоминаний «в срок» нет.
- **Push-уведомления** (`server/src/push.ts`, `server/src/notifications/`, таблицы `push_subscriptions` и `notification_log`). Web Push через `web-push` и ключи VAPID из `.env` (без них функция выключена, `/api/push/*` отвечают 503). Планировщик (`scheduler.ts`) раз в минуту просматривает подписки и для каждой считает местное время по её `time_zone` (`Intl`, `time.ts`): в 10:00 день рождения (именинника поздравляем отдельным текстом, остальным «исполняется N»), в 17:00 для детей уроки следующего учебного дня (воскресенье и суббота без уроков пропускаются, как на «Моём дне»; нет уроков — ничего не шлём). Опоздавшее уведомление уходит в течение двух часов после назначенного времени, дальше нет. Тренировки: ребёнку за 2 часа до `starts_at` (`trainingMessages`; без времени начала напоминаний нет; окно отправки 15 минут без догона, потому что «за 2 часа» теряет смысл; тренировка в первые часы после полуночи анонсируется накануне вечером, поэтому у `PlannedMessage` есть `day` — дата самой тренировки для журнала). Дубли исключает `notification_log` (запись пишется до отправки: на одну подписку, вид и локальную дату). Подписка с ответом 404/410 удаляется. Тексты и выбор дня — чистые функции в `messages.ts`. Адрес подписки принимается только у известных push-сервисов (`ALLOWED_SUFFIXES` в `push.ts`, для тестов `PUSH_ALLOWED_HOSTS`): сервер сам обращается по этому адресу, иначе это SSRF. Подписка привязывается к устройству (`endpoint`) и переходит к тому, кто вошёл на нём последним. Принудительный проход для проверки: `npm run notify:tick -- HH:MM [--reset]` в `server/` (`server/scripts/tick.ts`).
- **Монеты детей** (`coin_transactions`, `server/src/coins.ts`). У детей есть баланс виртуальных монет. Он не хранится числом, а считается как сумма журнала (`amount` > 0 начисление, < 0 списание, 0 нельзя, `reason` до 200 знаков; баланс может быть отрицательным); `coinBalance(db, memberId)`. У записи есть автор `created_by` (участник семьи, `null` для системы или если автор удалён). История: `GET /api/coins?before=<id>&limit=&memberId=` (ребёнок видит свою; родитель только с `memberId` ребёнка своей семьи: без него 403 `not_a_child`, чужая семья 404 `member_not_found`, не ребёнок 400 `not_a_child`; ребёнку чужой `memberId` 403 `forbidden`; свежее сверху, страницы по 30, `before` это id самой старой загруженной записи, курсор по `(created_at, id)`; отдаёт `{balance, items:[{id, amount, reason, createdAt, createdBy}], hasMore}`). Баланс отдаёт `GET /api/me` и только самому ребёнку (`member.coins`; у родителей поля нет, в списке `members` монет нет). Способов получить монеты пока нет (ни награды за задания, ни ручного начисления): будущие начисления пишите строкой в журнал и публикуйте `publish(familyId, { type: 'members' })`, тогда клиент обновит `/api/me`. В демо-семье дети получают стартовые монеты (`npm run seed`).
  **Подтверждение родителем:** задание с наградой ребёнок только отправляет на проверку, награду выдаёт подтверждение родителя (любого). `POST …/complete` от ребёнка при `reward > 0` создаёт отметку `pending` (`task_completions.pending`, монет нет; push обоим родителям «Задание на проверку», `reviewMessage`); от родителя выполнение сразу подтверждённое с наградой, а если вхождение уже ждёт проверки, то подтверждает его (`completeOccurrence` в `tasks/routes.ts`). Явное подтверждение: `POST …/confirm {date}` (только родитель, иначе 403 `parents_only`; если проверять нечего, 400 `not_pending`, побочных эффектов нет). `uncomplete`: отправку снимает ребёнок или возвращает на доработку родитель (монет нет); подтверждённое задание с наградой ребёнок снять не может (403 `confirmed`), родитель может (награда возвращается). Вхождение в API: `done` только у подтверждённого, `pending` `{memberId, at}` у ожидающего проверки (оба `null` у открытого); ожидающее не попадает в «Выполненные» и в «заработано», а просроченное ожидающее остаётся в списке за период. `GET /api/tasks/pending` отдаёт все ожидающие (родителю по семье, ребёнку свои). Без награды всё как раньше: ребёнок завершает сам. **Награда за задание:** у задания поле `reward` (0–1000, по умолчанию 0; только если исполнитель ребёнок, иначе 400 `reward_requires_child`, и только если задание создаёт родитель: ребёнок не может назначить награду ни себе, ни другому ребёнку, 400 `reward_requires_parent`; проверка `rewardError` и при создании, и при изменении). При первой отметке вхождения (`POST …/complete`, в одной транзакции с отметкой) исполнителю пишется начисление `+reward` с причиной «Задание: название» от имени автора задания (запись связана с заданием и вхождением: `task_id`, `occurrence_date`), кто бы ни отметил (ребёнок сам или родитель), и публикуется `members`; за повторяющееся задание награда выдаётся за каждое выполнение отдельно. Снятие отметки (`uncomplete`) и смена графика задания (отметки сбрасываются) забирают выданное: `revokeRewards` пишет отмену на величину ещё не отменённого начисления по каждому ребёнку и вхождению («Отмена: …»), поэтому отметки и снятия по кругу не дают лишних монет. Смена награды после выполнения уже выданное не трогает; удаление задания оставляет монеты (связь с заданием обнуляется). Если выполнил не сам исполнитель, ему уходит push «Награда» (`rewardMessage`, ведёт на `/coins`).
- **Чат** (`messages`, `chat_reads`, `server/src/chat.ts`). У каждого общий чат семьи и по личному чату с каждым другим участником (ключ чата `chat_key`: `family` или id обоих через двоеточие по возрастанию, поэтому у собеседников он один; личное видят только двое). В API чат называется «глазами» участника: `family` или id собеседника. `GET /api/chats` (все чаты с последним сообщением и числом непрочитанных; сортировка по времени последнего сообщения, без сообщений в конце: сначала общий, потом по имени), `GET/POST /api/chats/:chat/messages` (страницы по 50 от свежих к старым, `?before=<id самого старого загруженного>`; только текст, 1–2000 знаков после обрезки), `POST /api/chats/:chat/read`. Статус своих сообщений («отправлено» / «прочитано»): `GET …/messages` отдаёт `readUpTo`, момент, до которого прочитали остальные участники чата (в личном это отметка собеседника, в общем самая ранняя из всех; у ни разу не открывавшего чат отсчёт с его появления в семье, поэтому пришедший позже не задерживает «прочитано» для старых сообщений); сообщение прочитано, если `createdAt <= readUpTo`. Непрочитанные считаются от `chat_reads.last_read_at`, а для нового участника от даты его появления (старая история непрочитанной не считается); своё сообщение отмечает чат прочитанным у автора, ответ тоже считается прочтением. Уведомления: при отправке `notifyMember` каждому участнику чата, кроме автора (в общем чате «Имя · Общий чат», в личном «Имя»; текст сжат до одной строки и 140 знаков; `tag: chat-<чат>` склеивает уведомления одного чата, нажатие ведёт на `/chat/<чат>`). Сигнал сокета `{type:'chat', chat}` уходит только участникам чата (`publishTo`, не всей семье) и содержит чат глазами получателя; `POST …/read` шлёт его другим устройствам этого же участника и остальным участникам чата (у них обновятся галочки), и только если что-то было непрочитано, иначе открытая переписка зациклилась бы на собственных отметках.
- **Реакции и монеты за сообщения детей** (`message_reactions`, `coin_transactions.message_id`, в `server/src/chat.ts`). Родитель (мама или папа) может на любое сообщение ребёнка в доступном ему чате (общий или личный с ребёнком; переписка двух детей родителям недоступна) поставить реакцию и/или начислить монеты автору: `POST /api/chats/:chat/messages/:messageId/feedback`, тело `{ emoji?: string | null, coins?: 1..1000 }` (нужно хотя бы одно поле; emoji только из `REACTIONS`, `null` снимает свою реакцию; у родителя одна реакция на сообщение, монеты можно начислять несколько раз, и разными родителями). Ответ: сообщение с `reactions` `[{memberId, emoji}]` и `awards` `[{amount, by}]` (эти поля есть у каждого сообщения в `GET …/messages`). Ошибки: ребёнку 403 `parents_only`, на сообщение взрослого 400 `not_a_child_message`, чужое или недоступное 404. Начисление пишется в журнал монет с причиной «За сообщение: начало текста» от имени родителя и привязкой `message_id` (при удалении сообщения реакции пропадают, монеты остаются). Сигналы: `chat` всем участникам чата, при монетах ещё `members` (баланс). Ребёнку при начислении приходит push от «Мамы» или «Папы»: «+20 монет за ваше сообщение» (с реакцией «и реакция 👍»); одна реакция без монет push не шлёт.
- **Живые обновления по WebSocket** (`server/src/realtime.ts`, `GET /api/ws`, плагин `@fastify/websocket`). По сокету идут только сигналы «что изменилось» (`tasks`, `members`, `schedule`/`trainings` с `memberId`), без данных: клиент по сигналу заново запрашивает данные обычными запросами, где доступ проверяется как всегда. Первое сообщение клиента `{"type":"auth","token":"…"}` (токен не в адресе, иначе он попадёт в журналы прокси), ответ `{"type":"ready"}`; не авторизовавшийся за 10 с, с неверным токеном и после выхода с устройства закрывается кодом 4401. Рассылка по семье: `publish(familyId, event)` / `publishForMember` после успешной записи (задания: создание, изменение, удаление, отметка и снятие; профиль и вступление в семью: `members`; расписания), вызывающему тоже (его другие устройства). Новая запись данных — вызов `publish` рядом. Проверка живости: ping раз в 30 с, молчащие соединения закрываются. Состояние только в памяти процесса: при нескольких экземплярах сервера нужен общий канал (например, Postgres `LISTEN/NOTIFY`).
- **Прокси и лимиты.** Сервер за nginx (и Caddy в проде): `trustProxy: true` для `X-Forwarded-For`. Rate limit — общий 120/мин и строгий 10/мин (`strictLimit` в `server/src/routes.ts`) на эндпоинты, где можно подбирать коды; строгий счётчик общий для этих маршрутов по IP. Сервер не должен торчать наружу в обход nginx.

## Клиент: экраны и данные

**Маршруты.** Публичные: `/`, `/create`, `/created`, `/join`, `/login`. Остальные лежат под `AppShell` (проверка входа, значок профиля справа сверху и нижняя панель табов `TabBar`): `/tasks`, `/tasks/new`, `/tasks/:taskId` (просмотр), `/tasks/:taskId/edit`, `/chat`, `/chat/:chat`, `/my-day`, `/family`, `/family/invite`, `/family/:memberId`, `/profile`, `/settings`, `/settings/schedule`, `/settings/trainings`, `/family/:memberId/schedule`, `/family/:memberId/trainings`. Стартовая страница после входа и при открытии приложения: «Мой день» (`START_PATH` в `lib/routes.ts`: на неё ведут `Welcome` для вошедшего, успешный вход, присоединение и «Семья создана»). Новый раздел: страница в `pages/`, роут внутри `AppShell` в `App/index.tsx` и запись в `TABS` (`components/TabBar/utils.ts`) (значок задаётся именем `icon` и рисуется в `TabBar/TabIcon.tsx` простым контурным SVG цветом текста таба, без эмодзи). В таб-баре раздел назван «Задачи», заголовок страницы «Задания». Страница «Чат» — список чатов (`pages/Chat`), переписка `/chat/:chat`.

**Семья и профиль.**
- «Моя семья» (`/family`): список участников, для владельца пункт «Пригласить» (страница `/family/invite`: ссылка, срок, копирование, перевыпуск; не-владельца оттуда перекидывает на `/family`),  Карточка ведёт на `/profile`, если это вы, иначе на превью `/family/:memberId` (фото, имя, роль, дата рождения и возраст, круглая кнопка-значок чата `Написать` в личный чат `/chat/:memberId`; email не показываем; у ребёнка для родителя пункты расписаний).
- `/profile`: имя, дата рождения, фото; email и роль только для чтения; в самом низу страницы кнопка «Выйти» с подтверждением (окно `useConfirm`; сессия на сервере отзывается, а если сервера нет, на устройстве всё равно выходим).
- Значок профиля (`Avatar`: фото, а без него круг стабильного цвета из `memberId` и первая буква имени) ведёт на `/profile`. Он стоит по центру строки с заголовком страницы (`top: 1.2rem` в `AppShell/styles.ts` при отступе страницы 1.5rem и заголовке около 31px; на «Моём дне» на одном уровне со смайликом приветствия) и скрыт на самой странице `/profile`. Если меняете размер заголовка или отступ `Page`, сверьте положение значка.
- `/api/me` запрашивается один раз для всех разделов (`web/src/profile`: `ProfileProvider` внутри `AppShell`, хук `useProfile`, `refresh()` после изменений); при 401 он очищает вход. Данные перезапрашиваются при каждом переходе и при возврате на вкладку, чтобы правки других участников (фото, имя, дата) были видны без перезагрузки. После смены имени обновляйте и `Identity` на устройстве (`save`).
- Состояние входа: `web/src/identity/` (провайдер читает IndexedDB, хук `useIdentity` в `context.ts`, `toIdentity` превращает ответ сервера в `Identity`).
- Регистрация и присоединение — общий `components/RoleForm` (шаг `DetailsStep`, затем `CodeStep`): сам показывает ошибки, страницы только вызывают API и бросают `ApiError`.

**Задания.**
- `/tasks`: вкладки «Предстоящие» (7 дней вперёд, просроченное сверху, «без срока» внизу; выполненные подтверждённые вхождения сюда не входят, они только во вкладке «Выполненные»; ожидающие проверки родителями остаются) и «Выполненные» (за месяц, с отметкой, кто выполнил), фильтр по человеку («Все», «Мои», каждый член семьи; у ребёнка его нет, у него только свои задания).
- `/tasks/:taskId` (`pages/TaskView`): все детали (описание, исполнитель, автор, срок, повтор, дата создания `createdAt`, кто и когда выполнил), внизу «Изменить» (только автору) и «Отметить выполненным»; `?date=YYYY-MM-DD` выбирает вхождение повторяющегося задания (ссылку с датой строит `TaskItem`). После отметки открывается экран поздравления `components/Celebration` на всю страницу с конфетти (`components/Confetti`: канвас и `requestAnimationFrame`, физика частиц в `utils.ts`, при «уменьшении движения» не рисуется; в скрытой панели Browser анимация не идёт, потому что там не работает `requestAnimationFrame`); «Отлично» ведёт к списку. Снять отметку можно там же, без поздравления. `/tasks/new` и `/tasks/:taskId/edit` (`pages/TaskForm`; `/tasks/new?assignee=<id>` заранее ставит исполнителя, так кнопка «Новая задача» на странице «Задания» передаёт выбранного в фильтре человека; чужой или неизвестный id игнорируется): форма с описанием, удаление только у автора; чужое задание перекидывает на просмотр.  Отмечать выполнение можно только на этой странице: в списках флажка нет.
- Общая карточка — `components/TaskItem`: целиком ссылка на страницу задания, слева значок состояния (список дел, галочка в круге, часы для просроченного), справа ›; в ней (срок, время, повтор с «до …», исполнитель, «от автора» если он не исполнитель, в выполненных дата вхождения и кто и когда отметил), склейка вхождений и сортировка — `lib/occurrences.ts`.

**Расписания.**
- Ребёнок правит своё из «Настроек» (`/settings/schedule`, `/settings/trainings`), родитель — с превью ребёнка (`/family/:memberId/...`). Страницы `pages/Schedule` и `pages/Trainings` — зеркальные редакторы: по умолчанию просмотр (`LessonViewList`, `TrainingViewList`), «Изменить» открывает редактор с черновиком (`saved` — серверное состояние, `draft` — правки), «Отмена» с несохранёнными правками просит подтверждение, пустые строки при сохранении отбрасываются.
- Общие `components/DayTabs` (дни передаются пропом) и `components/SortableList` (перетаскивание `@dnd-kit`, ручка слева, есть клавиатура; строки сами вызывают `useSortable`).

**Проверка родителем в интерфейсе:** `components/PendingReview` («Ждут подтверждения» со счётчиком: карточки заданий детей с кнопками «Подтвердить: +N» и «Вернуть»; только родителям и только когда есть что проверять) стоит наверху «Моего дня» и на странице «Задания» (учитывает фильтр по человеку; у родителей ожидающие в списках по дням скрыты, чтобы не дублировать). Карточка `TaskItem` в состоянии «на проверке» (песочные часы, янтарный цвет; кнопки лежат под ссылкой, а не внутри неё). Страница задания: ребёнок видит «Отправить на проверку» вместо «Отметить выполненным», затем «Отменить отправку», без праздника; праздник с «+N монет» приходит сам, когда родитель подтвердил, пока ребёнок на странице; родитель видит «Подтвердить: +N» и «Вернуть на доработку»; подтверждённое задание с наградой ребёнок снять не может. Действия родителя: хук `lib/useReview`.

**Награда в форме задания:** если исполнитель ребёнок и форму заполняет родитель (ребёнку награду назначать нельзя, плашек у него нет), в `TaskEditor` появляется `RewardPicker`: плашки «Без награды», 5, 10, 20, 50, 100 (`REWARD_CHOICES` в `lib/coins.ts`) и «Другая» с полем для своего целого числа от 1 до 1000 (`MAX_REWARD`; значение в форме строка `reward` и признак `rewardCustom`, награда вне готовых плашек у существующего задания открывается как «Другая»; проверка в `validate`, у формы `noValidate`, чтобы показывалось наше сообщение). При смене исполнителя на взрослого плашки скрываются и награда сбрасывается.

**«Указать время»:** дата, время и повтор спрятаны за чекбоксом `components/Checkbox` (`FormState.scheduled`; без галочки задание «без срока»). Включение ставит сегодняшнюю дату, выключение убирает дату, время и повтор; `toInput` без галочки отправляет `date/time` null и повтор `none`. Галочка без даты не проходит проверку. Награда видна в подписи карточки («+20 монет»), в деталях задания, а в экране поздравления исполнителю показано «+N монет».

**Монеты.** Правый верхний угол оболочки (`TopRight` в `AppShell`): у ребёнка слева от значка профиля баланс (`components/CoinBalance`: золотая монета и число, из `profile.me.coins`; это ссылка на `/coins`), у родителей только значок. На странице `/profile` значка профиля нет, баланс остаётся. Страница `/coins` (`pages/Coins`) у ребёнка показывает его монеты, у родителя `/coins/:memberId` монеты выбранного ребёнка (заголовок «Монеты: Имя», назад на `/family/:memberId`; родителя без `memberId` перекидывает на стартовую). Баланс-карточка `CoinBalanceCard` со ссылкой на историю стоит на `/profile` ребёнка и на странице ребёнка для родителя (`MemberPreview/components/ChildCoins`, `getCoinBalance`, обновляется по `members`). баланс крупно и история (`HistoryRow`: за что, «когда · кто» (родители для ребёнка «Мама» и «Папа», запись без автора «Система»), справа сумма со знаком, зелёная или красная; пустая причина «Без описания»). Старые записи подгружаются при прокрутке (`IntersectionObserver` на сторожа в конце списка с запасом 300px, плюс кнопка «Показать ещё» и «Повторить» при ошибке; повторные срабатывания во время запроса гасит `busy`), новые встают сверху по сигналу сокета `members` (`mergeNewest`). Автоподгрузку по прокрутке во встроенной панели Browser проверить нельзя (она скрыта и наблюдатель не срабатывает), только кнопкой и тестом. `AppShell` выставляет `--topbar-reserve` (место справа, которое занято углом); шапки страниц берут его в `padding-right`, а шапка заданий переносит выпадающий список на строку ниже, если он не помещается.

**Реакции и монеты в чате:** у родителя сообщения детей нажимаются (`role=button`, Enter и пробел тоже), открывается всплывающее окно `FeedbackDialog` (снизу поверх затемнения: реакция из `lib/reactions.ts`, `CoinPicker` с плашками и «Другая», «Отправить» доступна, когда выбрана новая реакция или монеты); под сообщением у всех видны реакции (одинаковые склеиваются с числом) и сумма начисленных монет (`MessageBubble`, плашки заезжают на нижний край пузыря на 0.6rem и сдвинуты внутрь на 0.7rem, обводка цветом фона отделяет их от пузыря). Общий `components/CoinPicker` используется и для награды в задании.

**«Сегодня заработано» на «Моём дне»:** ребёнку сверху под приветствием плашка с суммой монет, заработанных сегодня (`pages/MyDay/components/EarnedToday`, ссылка на `/coins`; пока 0 и у родителей плашки нет). Сумма с сервера: `GET /api/coins/earned?since=<ISO начала местного дня>` (час. пояс знает только клиент, `startOfDayIso`); считаются начисления (`amount > 0`) и отмены наград за задания (запись со `task_id` и отрицательной суммой), траты (списания без задания) не уменьшают «заработано», результат не меньше 0. Обновляется по сигналу `members`.

**«Что ты хочешь сообщить!»** (`/lesson-report?subject=…`, `pages/LessonReport`, только дети): на «Моём дне» у ребёнка уроки нажимаются (`LessonViewList` с `getLink`). Выбор оценки 5, 4, 3 или 2 (повторное нажатие снимает) и/или текст собираются `buildLessonReport` в сообщение вида «Урок «Математика»: оценка 5» и строкой ниже комментарий; оно отправляется в общий чат, затем открывается общий чат.

**Чат.** `/chat` (`pages/Chat`): список чатов (колонка списка `minmax(0, 1fr)`, превью в одну строку с многоточием: без этого длинное сообщение без пробелов раздувало карточку за экран) из `ChatsProvider` (`web/src/chat/`, в `AppShell`: список с непрочитанным обновляется по сигналу `chat`; из него же число на значке «Чат» в `TabBar`). `/chat/:chat` (`pages/ChatRoom`): сообщения по дням, пузыри (свои справа, имя автора над чужими только в общем чате; у своих рядом со временем галочки: одна «отправлено», двойная «прочитано», `messageStatus`), «Показать более ранние», поле ввода `Composer` (Enter отправляет, Shift+Enter перенос) прижато к панели табов. Переписка запрашивается заново по сигналу своего чата (`mergeLatest` сохраняет подгруженные старые сообщения), прокручивается вниз, только если читатель и так внизу; отметку «прочитано» ставит один раз на последнее чужое сообщение (`markedRef`, без этого сигнал о прочтении зациклил бы запросы). Неизвестный чат перекидывает на список. **Имена в чате:** ребёнок видит родителей как «Мама» и «Папа» вместо имён (`memberLabel` в `lib/roles.ts`: список чатов, аватар, превью и подписи авторов в общем чате, заголовок переписки); то же в push-уведомлениях для ребёнка (`senderLabel` в `server/src/chat.ts`). Родители и дети друг для друга по-прежнему видят имена. Сообщения прижаты к низу (`Feed` с `justify-content: flex-end`), чтобы при малом числе сообщений и открытой клавиатуре они оставались рядом с полем ввода. Клавиатуру на телефоне отслеживает `lib/useKeyboardViewport`: iOS не меняет размер страницы, меняется только `visualViewport`, поэтому хук пишет на корень `--vvh` (высота видимой области) и `data-keyboard`, пока клавиатура открыта; по нему стили прячут `TabBar`, обнуляют нижний отступ `Content`, прижимают `Composer` к низу и растягивают `Room` ровно на видимую область (правила `:root[data-keyboard] &`). На реальном iPhone это не проверялось (расчёт и эмуляция атрибутов в браузере).

**Живые обновления.** `web/src/realtime/`: `RealtimeProvider` (в `AppShell`, одно соединение на вход: подключение, auth первым сообщением, переподключение с нарастающей паузой 1–30 с, при потере и возврате связи, при возврате вкладки после 5+ с и при появлении сети рассылает `resync`) и хук `useLive(темы, обработчик)` (`realtime/context.ts`). Страница подписывается на тему и перезапрашивает данные: типичный приём `const [version, setVersion] = useState(0); useLive(['tasks'], () => setVersion(v => v + 1))` и `version` в зависимостях эффекта загрузки (список не очищается, мигания нет). Подписаны: «Задания», просмотр задания, «Задания на сегодня», расписания и тренировки (и их блоки на «Моём дне»), профиль (`members`). Форма изменения задания не подписана, чтобы чужие правки не затирали ввод. Нужен `ws: true` в прокси Vite и `location = /api/ws` с Upgrade в `web/nginx.conf` (Caddy пропускает WebSocket сам).

**«Мой день».** Приветствие по времени суток и блоки (`pages/MyDay`):
- «Задания на сегодня» (`TodayTasks`): мои просроченные и сегодняшние (по времени), затем отдельной группой «Без срока» (невыполненные; выполненные задания без срока сервер в список не отдаёт); будущие дни здесь не показываются. У ребёнка выполненные (подтверждённые) задания на этой странице скрыты, остаются открытые и ждущие проверки; если всё выполнено, написано «Все задания на сегодня выполнены»; у родителей свои выполненные остаются. Карточки ведут на страницу задания (отметить выполненным можно только там).
- Ребёнку «Уроки сегодня/завтра/в понедельник» (`TodayLessons`) и «Тренировки сегодня/завтра/в среду» (`TodayTrainings`).
- Родителю «Дети: уроки, тренировки и задания» (`FamilyLessons`): компактная карточка на каждого ребёнка; сверху ссылка в его расписание (уроки и ближайшая тренировка), ниже «Задания на сегодня» (`ChildTasks`): сегодняшние вхождения заданий ребёнка, в том числе выполненные (зачёркнуты, счётчик «выполнено N из M» считает только сегодняшние), каждое со ссылкой на задание, а под ними отдельной группой «Без срока» его невыполненные задания без срока; просроченные сюда не входят. Расписания грузятся параллельно по одному запросу на ребёнка, день для каждого выбирается отдельно, задания всей семьи одним запросом `listTasks(сегодня, сегодня)`; обновляется по сокету (`schedule`, `trainings`, `tasks`).
- Выбор дня (`pages/MyDay/utils.ts`): уроки (`pickLessonDay`) — до 18:00 сегодняшний, с 18:00 завтрашний, воскресенье и суббота без уроков пропускаются до понедельника; тренировки (`pickTrainingDay`) — с сегодняшнего (с 18:00 с завтрашнего) берётся ближайший день с тренировками, нет тренировок совсем — блока нет.

**«Настройки».** Для детей пункты расписаний, блок «Уведомления» (`NotificationsSetting`, хук `lib/usePushSubscription`: включение, проверка, выключение на этом устройстве), тема оформления внизу.

## PWA, кэширование, тема

- Service worker свой, `web/src/sw.ts` (стратегия `injectManifest`): кэш приложения (`/api/` в кэш не попадает) и обработчики `push` и `notificationclick`. Он собирается отдельным tsconfig (`tsconfig.sw.json`, lib `WebWorker`) и исключён из `tsconfig.app.json`. Иконки генерируются из `web/public/icon.svg` командой `npm run generate-pwa-assets` (в `web/`) (настройки в `web/pwa-assets.config.ts`: значок для iOS `apple-touch-icon` без полей и прозрачности, на всю плашку, потому что скругление iOS делает сам; maskable для Android с полями 15% на сплошном фоне). Название приложения «Моя семья» задано в манифесте (`vite.config.ts`), `<title>`, `apple-mobile-web-app-title` в `index.html`, по умолчанию в заголовке push (`sw.ts`) и в письмах (`mail.ts`).
- Обновление у пользователей: service worker с `skipWaiting` и `clientsClaim` ставится и активируется сам, но открытая страница работает на старой версии до перезагрузки. Хук `lib/useAppUpdate` слушает `controllerchange` (только если worker уже управлял страницей, первая установка не в счёт), раз в 30 минут и при возврате на вкладку вызывает `registration.update()`; `components/UpdateBanner` (в `App`) показывает вверху плашку «Доступна новая версия» с кнопками «Обновить» (перезагрузка) и «Позже». Принудительной перезагрузки нет, чтобы не потерять набранное. Старая и новая версии какое-то время живут вместе, поэтому API меняйте обратно совместимо. Кэширование (`web/nginx.conf`): `index.html` (включая `/` и все маршруты SPA, их отдаёт SPA fallback), `sw.js`, `registerSW.js` и `manifest.webmanifest` отдаются с `Cache-Control: no-cache` (браузер каждый раз сверяется по ETag, 304 если не менялись), файлы с хэшем в `/assets/` с `public, max-age=31536000, immutable`; манифест отдаётся с типом `application/manifest+json`. Если добавите файл, который меняется между сборками без хэша в имени, добавьте его в `no-cache`-правило, иначе пользователи будут видеть старую версию.
- **Безопасные зоны iPhone.** В `index.html` у viewport стоит `viewport-fit=cover`: без него iOS не сообщает `env(safe-area-inset-*)`, и нижняя панель табов оказывается под индикатором «Домой» и скруглёнными углами (крайние табы обрезаны). Все закреплённые к краям элементы учитывают отступы: `TabBar` (низ, лево, право; высота панели `--tabbar-height` в `AppShell` уже включает нижний отступ), кнопка «Новая задача», поле ввода чата и плашка обновления считают от него, а верхний отступ добавлен в `Page`, значок профиля, `ChatRoom` и плашку. Новые элементы у краёв экрана делайте так же. На симуляторе iOS это не проверялось (нужен полный Xcode), только расчётом.
- Тема: по умолчанию следует `prefers-color-scheme`, явный выбор (`pages/Settings/components/ThemeSetting`: как в системе / светлая / тёмная) хранится в `localStorage['theme']` и применяется атрибутом `data-theme` на `<html>`. Скрипт в `web/index.html` ставит его до первого рендера (без вспышки) и синхронизирует `<meta name="theme-color">`; логика дублирует `lib/theme.ts`, при изменении правьте оба места. Слушатель смены системной темы (`lib/useThemeSync`) подключён один раз в `App`.

## Структура `web/src`

Каждый компонент — папка с `index.tsx`. Рядом по необходимости: `styles.ts` (styled-components), `types.ts` (пропсы и типы), `utils.ts` (чистые функции). Вложенные компоненты, которые нужны только этому компоненту, лежат в его `components/` и устроены так же, на любую глубину.

- `App/`, `main.tsx` — корень, роуты.
- `pages/<Page>/` — страницы (default export), у них свои `components/`.
- `components/` — общие компоненты. Базовые примитивы (`Button`, `Chip`, `IconButton`, `Input`, `Notice`, `Page`, `Select`, `Stack`, `BackLink`) объявлены как styled-компоненты прямо в `index.tsx`; варианты задаются transient-пропсами (`$variant`, `$tone`, `$inline`, `$active`), ссылки получаются через `as={Link}`. Остальное: `AppShell`, `Avatar`, `CodeStep`, `ConfirmDialog`, `DayTabs`, `Field`, `LessonViewList`, `LinkBox`, `MenuLink`, `Placeholder`, `ReplaceGuard`, `RoleForm`, `SortableList`, `TabBar`, `TaskItem`, `TrainingViewList`.
- `GlobalStyle/` (в `components/`) — глобальные стили. Цвета заданы CSS-переменными, в styled-компонентах используйте `var(--...)`, а не жёсткие цвета. Новый цвет добавляйте в обе палитры (`lightColors`/`darkColors`).
- `api/` — клиент API по доменам: `client.ts` (`request`, `ApiError`), `auth/`, `families/`, `invites/`, `profile/`, `push/`, `schedule/`, `tasks/`, `trainings/` (в каждом `index.ts` с функциями и `types.ts`), наружу всё реэкспортирует `api/index.ts`, поэтому импортируем из `@/api`. Новый эндпоинт кладём в свой домен.
- `identity/`, `profile/` — провайдеры состояния (не UI): `context.ts` с хуком вынесен из `index.tsx` ради fast refresh.
- `lib/` — общие модули без UI: `date`, `errors`, `image`, `links`, `occurrences`, `roles`, `taskText`, `theme`, `validation`, `weekdays` и хуки `useNow`, `usePushSubscription`, `useThemeSync`.

## Соглашения

- Подтверждения только через `useConfirm()` (`components/ConfirmDialog`, провайдер в `App`): окно на всю страницу, `await confirm({ title, message, confirmLabel, danger })` → `true/false`. Системные `window.confirm/alert/prompt` не используем. В тестах компонентов с подтверждением оборачивайте их в `ConfirmProvider`.
- В `web/` включён `erasableSyntaxOnly`: никаких `enum` и parameter properties в конструкторах.
- API-запросы фронтенда только через `web/src/api` (общий `request`, ошибки как `ApiError` с `status` и `code`). Коды ошибок сервера — snake_case (`invite_expired`, `name_taken`), UI мапит их на тексты.
- Валидация входных данных на сервере через JSON-схемы Fastify; запросы к БД — параметризованный SQL через `pg`, без ORM. Даты и время отдаём строками через `to_char`.
- Секреты и `.env` не коммитим (`.env` и `backups/` в `.gitignore`, шаблон — `.env.example`).
- Коммиты на русском или английском без требований к формату; в `main` пушим только по просьбе пользователя.

## Деплой и эксплуатация

- **Прод:** на сервере в `.env` задано `COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml` и `DOMAIN`, тогда обычный `docker compose up -d --build` поднимает ещё и Caddy (`Caddyfile`, сертификат Let's Encrypt для `DOMAIN`, том `caddy_data` не удалять); веб-контейнер снаружи не публикуется (`ports: !reset []`). Первый запуск по шагам и повседневные команды описаны в README, раздел «Деплой на сервер».
- **Обновление:** `./update.sh` на сервере: `git pull --ff-only`, копия БД в `backups/` (последние 14, `--no-backup` пропускает), `docker compose up -d --build`, проверка здоровья сервера изнутри (до минуты) и, если задан `DOMAIN`, снаружи по HTTPS, `docker image prune`. При неудаче показывает лог сервера и команду отката (`git checkout <прежний коммит>`); миграции при откате кода не откатываются. Скрипт предупреждает, если изменился `.env.example` или появились миграции.
- **IP клиента.** Цепочка Caddy → nginx (`web`) → Fastify. Caddy ставит `X-Forwarded-For`, nginx принимает его через `real_ip` только от внутренних сетей Docker и передаёт серверу `X-Forwarded-For $remote_addr`, поэтому rate limit работает на каждого посетителя и заголовок подделать нельзя. Если поменять эту цепочку (например, добавить ещё прокси), проверьте, что IP клиента по-прежнему доходит до API (в логах сервера `remoteAddress`), иначе лимиты станут общими на всех.
- **Почта обязательна.** Без настоящего SMTP войти нельзя (только код из письма). DigitalOcean блокирует исходящие порты 25, 465 и 587, поэтому нужен сервис с портом 2525. Сервисы рассылок не разрешают отправлять «от имени» `@gmail.com` и подобных (DMARC), нужен адрес на **своём домене**, подтверждённом через DKIM и SPF; на бесплатных поддоменах (DuckDNS) этих DNS-записей не добавить. Mailpit (`COMPOSE_PROFILES=dev-mail`) в проде не включать.
- **Ключи VAPID** создаются один раз (`npx web-push generate-vapid-keys`) и больше не меняются: после смены все push-подписки перестают работать. `VAPID_SUBJECT` — настоящий контакт (для iPhone важно). Пароль БД в `.env` без символов `/ + = @ :` (ломают строку подключения), лучше hex.
- **Зависание на части устройств.** Если клиенты получают главную страницу, но не большой JS (стоп на 10–16 КБ; `curl` с такой же картиной: `-r 0-15000` проходит, `-r 0-16000` зависает), при этом на самом сервере файл отдаётся целиком, виновата сеть по дороге. На этом проекте причиной оказалось ограничение трафика к зарубежному хостингу (DigitalOcean) для пользователей в России: ни ICMP в Cloud Firewall, ни TCPMSS не помогли, помог перенос на российский хостинг. Запасной экран в `index.html` печатает диагностику, включая пробное скачивание главного скрипта (сколько байт из скольких).
- **Адрес и данные браузера.** Вход, подписки и приглашения привязаны к адресу сайта: при смене домена всё придётся делать заново.
- **Тома.** `pgdata` (БД) и `caddy_data` (сертификаты) не удалять: `docker compose down -v` стирает их.

## Известные ограничения и идеи

- Чат только с текстом (нет вложений, ответов, редактирования и удаления); напоминаний о заданиях «в срок» нет; страницы фронтенда целиком без автотестов (покрыта логика и ключевые компоненты).
- Во встроенной панели Browser (инструменты агента) service worker и уведомления не работают: настоящую доставку push проверять в обычном Chrome на собранной версии (README, раздел про push). На iPhone уведомления есть только у приложения, добавленного на экран «Домой» (iOS 16.4+), и нужен HTTPS.
- Название таба «Задачи» и страницы «Задания» разное, при желании унифицировать в `TABS`.
