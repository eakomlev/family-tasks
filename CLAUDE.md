# Моя Семья (Family Tasks)

PWA для семьи: задания, расписание уроков и тренировок детей, дни рождения, уведомления. Монорепозиторий без workspaces: у `web/`, `mobile/`, `server/`, `notifier/`, `scheduler/` и `media/` свои `package.json` и `node_modules`. Язык интерфейса и сообщений об ошибках для пользователя — русский, комментарии в коде тоже на русском.

- `web/` — React 19 + Vite 8 + TypeScript, стили на `styled-components`, PWA через `vite-plugin-pwa`, роутинг `react-router-dom`, данные на устройстве в IndexedDB (`idb-keyval`). Алиас `@/` → `web/src` (vite + `paths` в tsconfig).
- `mobile/` — будущее нативное приложение (Expo + React Native, Android и iPhone), заменит веб-версию; пока в разработке, см. раздел «Мобильное приложение» ниже и `docs/mobile-app-plan.md`.
- `server/` — Node 22 + Fastify 5 + `pg`, TypeScript (ESM, `NodeNext`, импорты с суффиксом `.js`).
- `notifier/` — сервис отправки писем и push из очереди `outbox` (Node 22 + `pg`, `nodemailer`, `web-push`, TypeScript как у `server/`), см. раздел «Сервис отправки» ниже.
- `realtime/` — живые обновления: держит WebSocket-соединения (`/api/ws`) и рассылает клиентам сигналы из канала Postgres (Node 22 + `pg` + `ws`), см. раздел «Живые обновления» ниже.
- `scheduler/` — планировщик плановых push (дни рождения, уроки, тренировки), ставит их в `outbox` (Node 22 + `pg`), см. раздел «Планировщик» ниже.
- `media/` — обработка и выдача фото из чатов (Node 22 + Fastify + `sharp`), хранит файлы во внешнем S3-совместимом хранилище (рег.ру, контейнера `s3` в compose нет), см. раздел «Медиа» ниже.
- PostgreSQL 17, всё упаковано в Docker: nginx (раздаёт `web/dist`, проксирует `/api/` на `server:3000` и `/media/` на `media`) + server + notifier + scheduler + realtime + media + s3 + db. В проде перед ними Caddy с HTTPS. Письма: `nodemailer` по SMTP, в dev Mailpit (профиль compose `dev-mail`, UI на :8025).

## Команды

Полный стек в Docker на своём компьютере (http://localhost:8080, без HTTPS):

```bash
cp .env.example .env
docker compose up --build -d
docker compose down
```

Локальная разработка одной командой (БД и Mailpit в Docker, сервер и сервис отправки через tsx watch, Vite с HMR; скрипты в корневом `package.json`, зависимость только `concurrently`):

```bash
npm run setup   # один раз
npm run dev     # npm run dev:stop выключает БД и Mailpit
```

Демо-данные для проверки интерфейса (мама, папа, двое детей с расписаниями и заданиями; нужна запущенная БД, `npm run dev:infra`):

```bash
npm run seed                      # создать демо-семью (прежнюю демо-семью заменяет, остальное не трогает)
npm run seed -- --snippet Миша    # JS для консоли браузера: войти под этим участником (семью не пересоздаёт)
npm run seed -- --existing --json # токены сессий для curl и скриптов
```

Скрипт `server/scripts/seed.ts`, отказывается работать на нелокальной БД. Для агента есть проектный скил `.claude/skills/seed-demo-family` (участники, порядок входа в браузер, ловушки).

Service worker в dev выключен (в `vite.config.ts` нет `devOptions`), PWA и push проверяйте на сборке. Если порт 5173 занят, Vite молча берёт следующий, смотрите адрес в выводе. Порт 8025 (Mailpit) занят и в полном Docker-стеке, поэтому одновременно запускать оба режима нельзя.

Проверки типов и сборки:

```bash
cd web && npx tsc -b && npm run lint && npm test && npm run build
cd server && npx tsc --noEmit
```

Тесты сервера (Vitest, `server/tests/`): нужна запущенная БД (`npm run dev:infra`); тесты работают в **отдельной базе `family_tasks_test`** на том же Postgres, которую создают и мигрируют сами (нелокальный хост отвергается). Запуск из корня или из `server/`:

```bash
npm test                  # все тесты, около 3 секунд
cd server && npx vitest run tests/api/tasks.test.ts   # один файл
cd server && npm run typecheck                        # типы приложения и тестов
```

- `tests/unit/` — чистая логика без БД (повторы заданий, часовые пояса и окна уведомлений, тексты, коды).
- `tests/api/` — API через `app.inject` на настоящей БД (вход, профиль, приглашения, расписания, задания, push). Планировщик уведомлений тестирует `scheduler/tests`. Приложение собирается `buildApp` из `src/app.ts` (без запуска и без общего rate limit); `index.ts` только запускает его.
- Изоляция: файлы идут параллельно, каждый создаёт свою семью (`tests/helpers.ts`: `createFamily`, `api`, `removeFamilies`) и убирает за собой. Не делайте в тестах глобальных `delete` без условия по своим данным.
- Письма и push в тестах не отправляются, а ставятся в таблицу `outbox`, и «отправленное» это её строки (server вообще не отправляет: нет ни SMTP, ни `web-push`). Push читают `sentTo(endpoints)` (асинхронный: `await sentTo([...])`), `resetSent()` (очистка между тестами только по подпискам своего файла) и `subscribe` из `tests/webpush.ts`; письма с кодами читают из `outbox` напрямую (`auth.test.ts`: `lastCode`, `sentTo`). Параллельные файлы делят таблицу, поэтому всегда фильтруйте по своим адресам и подпискам; перед прогоном `globalSetup` очищает `outbox`. Настоящая доставка, ошибки провайдеров и повторы проверяются в `notifier/tests`. Сбой очереди проверяйте так: `vi.spyOn(outbox, 'enqueue').mockRejectedValueOnce(...)` (`import * as outbox from '../../src/outbox/index.js'`). Публичный ключ VAPID в тестах фиктивный (`vitest.config.ts`): серверу он нужен только как признак «push включён».
- Ловушки Vitest 5: `beforeEach(() => mock.mockReset())` без фигурных скобок возвращает функцию, и Vitest вызывает её как очистку после теста (пишите `beforeEach(() => { ... })`); счётчик вызова подмены при загрузке модуля к началу теста уже обнулён (для такой проверки перезагружайте модуль в отдельном файле, `push-setup.test.ts`).
- Ключи VAPID на время прогона генерируются в `vitest.config.ts`.
- Проверка, что тесты ловят ошибки: вносите в код осознанную поломку (например, уберите проверку автора в `tasks/routes.ts`) и убедитесь, что тест краснеет.
- CI (`.github/workflows/ci.yml`, GitHub Actions): на каждый пуш в `main` и pull request задания: сервер (`npm ci`, `npm run typecheck`, `npm test` с сервисом Postgres 17; адрес задаёт `DATABASE_URL`, тестовую базу тесты создают сами), сервис отправки и планировщик (то же в `notifier/` и `scheduler/`), фронтенд (`npx tsc -b`, `npm run lint`, `npm test`, `npm run build`) и конфигурация (`bash -n update.sh`, `docker compose config` для обычного и продакшен-режима, валидация `Caddyfile`). Любое изменение, которое надо проверять в CI, сначала воспроизводите локально теми же командами в чистой копии без `.env`. Названия заданий с двоеточием в YAML берите в кавычки.

Тесты фронтенда (`web/tests/`, Vitest + jsdom + Testing Library; БД и сервер не нужны):

```bash
npm run test:web                 # из корня; npm test запускает сервер и фронтенд подряд
cd web && npx vitest run tests/components/TaskEditor.test.tsx
```

- `tests/unit/` — чистая логика (даты, повторы и сортировка заданий, выбор дня на «Моём дне», черновики расписаний, тема, тексты ошибок); `tests/api/` — клиент API с подменой `fetch`; `tests/hooks/` — страницы (`TaskView`: отметка и поздравление); `tests/components/` — компоненты (`TaskItem`, `CodeStep`, `TaskEditor`). `tests/helpers.ts` — фабрики `task()` и `occ()`.
- Часовой пояс прогона фиксирован (`Europe/Moscow` в `vitest.config.ts`), даты в тестах строятся от понедельника 12 октября 2026. Отдельный конфиг `vitest.config.ts` без PWA-плагина; `tsconfig.tests.json` подключён в `tsc -b`, так что типы тестов проверяются вместе со сборкой.
- Ловушки: с `vi.useFakeTimers` не работают `userEvent` и `findBy*`/`waitFor` (используйте `fireEvent` и `act` с `advanceTimersByTimeAsync`; обратный отсчёт в `CodeStep` перезапускает таймер после каждого рендера, поэтому секунды отсчитывайте по одной); у метки поля с подсказкой (`Field` с `hint`) имя длиннее названия, ищите по `/^Дата/`; тело `Response` читается один раз, подмену `fetch` для нескольких запросов делайте фабрикой.
- Страницы целиком (роутинг, провайдеры) автотестами не покрыты, их проверяют вручную и скилом `seed-demo-family`.

Обновление на сервере: `./update.sh` (подробнее в разделе «Деплой и эксплуатация»).

## Сервис отправки (`notifier/`)

Фаза 1 плана `docs/notification-queue-plan.md`: отдельный пакет и контейнер, который берёт строки из таблицы `outbox` и отправляет письма (SMTP) и push (Web Push). Код `server` и `notifier` друг друга не импортируют; контракт это таблица `outbox` и payload версии `v: 1` (типы продублированы: `server/src/outbox/contract.ts` и `notifier/src/contract.ts`; общий образец `contracts/outbox-v1.json` в корне читают тесты обоих пакетов, при изменении контракта правьте его; тип `PushMessage` живёт в `outbox/contract.ts`, проверка часового пояса `isValidTimeZone` в `lib/timeZone.ts`). Таблицы `outbox` и `notifier_heartbeat` создаёт миграция `server`, `notifier` миграций не выполняет (если он стартует раньше сервера, он пишет `waiting_for_migrations` и ждёт).

- **Очередь.** Забор пачки (`queue.ts: claim`) одним запросом с `for update skip locked`, порядок `priority, id`. Аренда: забирая строку, `notifier` сдвигает `next_attempt_at` на 60 секунд вперёд и увеличивает `attempts`; если он упал, строка вернётся после аренды, но попытка уже посчитана. Всего **3 попытки** (`MAX_ATTEMPTS`): паузы для письма 5 и 30 секунд, для push 1 и 10 минут, разброс ±20%, `Retry-After` провайдера удлиняет паузу (не дольше часа). Результат не хранится: строка удаляется после успеха, после третьей неудачи и по `expires_at`; окончательная неудача пишется в журнал событием `outbox_failed` (`outbox_expired` для просроченного), успехи не пишутся. Строка версии `v` новее, чем понимает `notifier`, откладывается на минуту без траты попытки (`outbox_unsupported_version`): так выкладка нового `server` перед новым `notifier` ничего не теряет.
- **Лимиты** (фаза 3, `notifier/src/limits.ts`). Итог `defer` (`Outcome`): упёрлись в лимит, строка возвращается без траты попытки (`defer` в `queue.ts`) и предлагается снова через `seconds`; сколько бы раз ни откладывали, строка умрёт только по `expires_at`. **Дневной бюджет почты** (`createDailyBudget`): таблица `provider_usage (provider, day, count)`, единица занимается атомарно (`insert … on conflict do update … where count < лимит`), поэтому несколько `notifier` вместе лимит не превысят; сутки по UTC; единица возвращается, если письмо не принято (`limitMail`), так что простой SMTP бюджет не жжёт; `MAIL_DAILY_LIMIT` (по умолчанию 2800 при лимите сервиса 3000, `0` без лимита) . В журнал раз за сутки на экземпляр: `mail_budget_80` (warn) и `mail_budget_exhausted` (error); при исчерпании письма откладываются на 60 секунд и до истечения кода не уйдут. **Скорость**: токен-бакет `TokenBucket` (почта `MAIL_RATE_PER_SECOND`, по умолчанию 2; push `PUSH_RATE_PER_SECOND`, по умолчанию 50, свой бакет на группу сервиса `hostGroup`: fcm, mozilla, apple, windows, other); пауза до 5 секунд (`MAX_SLEEP_MS`) ждётся, длиннее откладывается (`rate_limited`). Скорость считается на экземпляр, при нескольких `notifier` делите её между ними. `Retry-After` push-сервиса (429 или 503) тормозит всю его группу (`gate.pause`, событие `provider_throttled`), у SMTP такого заголовка нет. Отказ API при исчерпании бюджета (`503 mail_busy`) описан в разделе «Вход по email» ниже.
- **Счётчики для страницы «Сервис»** (фаза 6): результат строки не хранится, поэтому после каждого прохода `processBatch` добавляет итоги в `delivery_stats (channel, day, sent, failed)` (`recordDelivery`, сутки по UTC, один upsert на канал за проход; сбой записи только предупреждение `delivery_stats_failed`). К `failed` относятся окончательные неудачи (`fail`, исчерпанные попытки) и просроченные строки; пропуск, откладывание и повторы не считаются. Служебные таблицы чистит `housekeeping` (раз в 15 секунд вместе с меткой живости): `delivery_stats` старше 30 суток, `provider_usage` старше 7.
- **Push в приложение** (Android, Firebase Cloud Messaging; фаза 6 `docs/mobile-app-plan.md`): у подписки `push_subscriptions.kind` (`web` или `fcm`), у `fcm` токен устройства лежит в `endpoint`, ключей нет. `notifier` выбирает провайдера по виду (`providers/pushRouter.ts`), `providers/fcm.ts` отправляет через FCM HTTP v1 (токен доступа подписывается ключом сервисного аккаунта сам, `FCM_SERVICE_ACCOUNT_BASE64`; устройство не найдено (404, UNREGISTERED, SENDER_ID_MISMATCH) снимает подписку, 400, 401 и 403 постоянные, 429 и 5xx повторяются, скорость пока не ограничивается). Серверу и планировщику нужен только `FCM_ENABLED=true` (`pushEnabled` в `server/src/push.ts` теперь «VAPID или FCM»); регистрация устройства `POST /api/push/devices {token, timeZone}`. Формат очереди не менялся: сообщение ссылается на подписку по id.
- **Push на iPhone напрямую через APNs** (`providers/apns.ts`, вид подписки `apns`, миграция `…036000`; токен устройства в `endpoint`): HTTP/2 к `api.push.apple.com`, токен провайдера (JWT ES256, ключ `.p8`) подписывается средствами `node:crypto` и обновляется раз в 40 минут (или при `ExpiredProviderToken`), одно соединение на процесс. Настройки только у `notifier`: `APNS_KEY_BASE64`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID`, `APNS_PRODUCTION` (по умолчанию боевой APNs, для сборок из Xcode `false`); серверу и планировщику нужен `APNS_ENABLED=true`. Регистрация: `POST /api/push/devices {token, timeZone, platform: 'ios'}` (токен APNs это hex, иначе 400 `invalid_token`: из него формируется адрес запроса). Классификация ошибок: 410, `Unregistered`, `BadDeviceToken`, `DeviceTokenNotForTopic` снимают подписку, 400, 403 и 413 постоянные, 429 и 5xx повторяются. `tag` уходит как `apns-collapse-id` (до 64 байт), `url` и `tag` отдельными ключами рядом с `aps`. Проверено тестами с подменой сети; настоящая доставка на устройство не проверялась.
- **Число на значке приложения.** Это непрочитанные сообщения получателя во всех чатах, кроме отключённых (mute) и убранных в архив (задания и игры в число не входят). `server/src/badge.ts: unreadBadge` считает его при постановке каждого push (`enqueueToMember` кладёт в `PushMessage.badge`, необязательное поле, у плановых напоминаний `scheduler` его нет и значок не меняется), клиенты считают то же по своему списку чатов (`appBadgeCount` в `web/src/chat/badge.ts` и `mobile/src/chat/badgeCount.ts`). Доставка: Web Push несёт его в данных, `sw.ts` ставит `navigator.setAppBadge` (Badging API: установленное приложение на компьютере и на iPhone, на Android Chrome числа нет, только точка); APNs `aps.badge`; FCM `android.notification.notification_count` (число покажет не каждый лаунчер, у остальных значок это точка по числу уведомлений). Пока приложение открыто, число ставят `useAppBadge` (веб: `setAppBadge`/`clearAppBadge`, при закрытии экрана сбрасывается; приложение: `Notifications.setBadgeCountAsync`, на iPhone нужно разрешение на уведомления). Менять определение числа нужно в трёх местах сразу: сервер и два клиента.
- **Ошибки провайдеров** (`providers/`): SMTP 5xx и `EENVELOPE` постоянные, остальные (сеть, 4xx) временные; push 404/410 удаляют подписку и тихо снимают строку, 400/401/403/413 постоянные, 429, 5xx и сеть временные. Без ключей VAPID push-строки отбрасываются как `push_not_configured`. Адрес подписки `notifier` проверяет сам по тому же списку, что `server/src/push.ts` (`allowlist.ts`, для тестов `PUSH_ALLOWED_HOSTS`): запрос по нему делает он.
- **Цикл** (`index.ts`): проход `processBatch(db, providers, {now, limit, concurrency, leaseSeconds})` (время параметром, как `runTick`), затем ожидание сигнала `listen outbox` (`listener.ts`, сигнал не хранится и только ускоряет реакцию) или секунды. Метка живости раз в 15 секунд в `notifier_heartbeat` (по имени хоста контейнера); healthcheck контейнера `node dist/healthcheck.js` проверяет её свежесть (порта нет), `update.sh` ждёт его после запуска. Настройки: `NOTIFIER_BATCH_SIZE` (20), `NOTIFIER_CONCURRENCY` (5), `NOTIFIER_LEASE_SECONDS` (60), `MAIL_DAILY_LIMIT`, `MAIL_RATE_PER_SECOND`, `PUSH_RATE_PER_SECOND`, `SMTP_*`, `VAPID_*`.
- **Тесты** (`notifier/tests/`, Vitest, нужна БД `npm run dev:infra`): своя база `family_tasks_notifier_test` с миграциями из `../server/migrations`; файлы идут по очереди (`fileParallelism: false`), потому что проходы забирают строки общей таблицы. Запуск: `npm run test:notifier` из корня или `npm test` в `notifier/`; типы: `npm run typecheck` в `notifier/`. Провайдеры подменяются передачей функций (`createMailProvider(transport, from)`, `createPushProvider(db, send, enabled)`), настоящей сети нет. Ловушка: проверка `skip locked` держит блокировку строк в соседней транзакции (параллельные вызовы из одного процесса гонку не воспроизводят).
- **CI:** задание `notifier` (`npm ci`, `npm run typecheck`, `npm test`, Postgres 17).
- **Выкладка.** Очередь включена всегда (прежний флаг `QUEUE_ENABLED` удалён, в `.env` он игнорируется), `server` не умеет отправлять сам: если `notifier` не запущен, письма и push копятся в очереди и не уходят (коды входа истекают за 10 минут). Поэтому `update.sh` после запуска ждёт метку живости `notifier` и при её отсутствии показывает лог и команду отката. SMTP и ключи VAPID берутся из `.env` в `notifier` (в compose они есть только у него), серверу нужен только `VAPID_PUBLIC_KEY`. Ключи создаёт `cd notifier && npm run vapid`. Ловушка песочницы агента: `docker build` падает на `npm ci` (в логе `SELF_SIGNED_CERT_IN_CHAIN`, затем «Exit handler never called!»), потому что исходящий TLS идёт через прокси со своим сертификатом, которому контейнер сборки не доверяет; к Dockerfile это не относится и на обычной машине или сервере не воспроизводится. Проверить образ в песочнице можно временной копией Dockerfile: положить рядом `/root/.ccr/ca-bundle.crt` как `ca.crt`, после `WORKDIR /app` добавить `COPY ca.crt /ca.crt` и `ENV NODE_EXTRA_CA_CERTS=/ca.crt` (в репозиторий это не попадает; проверку TLS отключать нельзя).
- **`POST /api/push/test`** ставит проверочное сообщение в очередь и отвечает `{queued, sent: queued, failed: 0}`: итог доставки сразу неизвестен, поля `sent`/`failed` оставлены, чтобы клиент прежней версии показал «Отправили» (сообщение «Не удалось доставить» не появляется; отозванную подписку снимает `notifier`).
- **Фаза 2 доведена** (`docs/notification-queue-plan.md`): из `server` удалены синхронный драйвер, `mail.ts`, `sendPush`, зависимости `nodemailer` и `web-push`, `SMTP_*`, приватный ключ VAPID и `VAPID_SUBJECT`. `pushEnabled` в `push.ts` теперь означает «задан публичный ключ VAPID» (от него зависят `enqueueToMember` и маршруты `/api/push/*`; планировщик в `scheduler/` проверяет ключ сам): если на `server` пропадёт `VAPID_PUBLIC_KEY`, уведомления перестанут ставиться.

## Планировщик (`scheduler/`)

Планировщик (фазы 1–2 плана `docs/scheduler-service-plan.md`): отдельный пакет и контейнер, который раз в минуту решает, кому что напомнить (день рождения 10:00, уроки следующего дня 17:00, тренировка за 2 часа), и ставит push в очередь `outbox`; отправляет их `notifier`. Код `server`, `notifier` и `scheduler` друг друга не импортируют: контракт это таблицы БД и payload версии `v: 1` (копия типов в `scheduler/src/contract.ts`, общий образец `contracts/outbox-v1.json` проверяют тесты всех пакетов). Прежний планировщик из `server` удалён (`server/src/notifications/`, тесты и `notify:tick`); напоминания, которые он успел записать в `notification_log`, не дублируются. Если несколько экземпляров `scheduler`, проход делает один: лидер берёт `pg_try_advisory_lock(SCHEDULER_LOCK_KEY)` (7301001; сбой снятия закрывает соединение, и блокировка уходит с ним). Если `scheduler` не запущен, плановые напоминания не уходят (остальное работает); `update.sh` ждёт его метку живости.

- **Читает** `push_subscriptions`, `members` (роль, семья, имя, дата рождения), `schedule_lessons`, `training_sessions`; **пишет** `outbox` (`src/outbox.ts`, без склейки по `tag`: у плановых он уникален), `notification_log` и `scheduler_state`. Переименование этих колонок в `server` ломает планировщик: тесты идут на настоящей схеме из `../server/migrations`.
- **Файлы:** `tick.ts` (`runTick(pool, now)`, `runTickAsLeader`: запись в журнал и постановка в одной транзакции, лидер через `pg_try_advisory_lock`), `messages.ts` и `time.ts` (копии чистой логики из `server`), `state.ts` (метка живости и итог прохода в `scheduler_state`), `index.ts` (первый проход через 5 секунд, затем раз в минуту; метка раз в 15 секунд; завершение по SIGTERM дожидается прохода), `healthcheck.ts` (метка свежее минуты, порта нет; `update.sh` ждёт её). Без `VAPID_PUBLIC_KEY` ничего не планируется (как у `server`).
- **Правила** (в `messages.ts` и `time.ts`): опоздавшее уведомление уходит в течение двух часов после назначенного времени (окно догона), дальше нет; именинника поздравляем отдельным текстом, остальным «исполняется N»; воскресенье и суббота без уроков пропускаются, как на «Моём дне», нет уроков — ничего не шлём; тренировка: ребёнку за 2 часа до `starts_at`, без времени начала напоминаний нет, окно отправки 15 минут без догона, тренировка в первые часы после полуночи анонсируется накануне вечером (у `PlannedMessage` есть `day` — дата самой тренировки для журнала). Дубли исключает `notification_log` (запись пишется до постановки: на подписку, вид и локальную дату). Журнал чистится в конце прохода от **переданного времени** (записи старше 7 суток от `now`, а не от часов базы): иначе тесты с фиксированной датой «старели» бы вместе с календарём (так 14 октября 2026 упали три теста: их день 6 октября попал под чистку по `current_date`).
- **События и задания** (`messages.ts: eventMessages`, `taskMessages`, повторы в `recurrence.ts` — копия `server/src/tasks/recurrence.ts`): событие, которое начинается сегодня и видно участнику (автор, участник, вся семья): со временем за час до начала (окно 15 минут без догона), на весь день в 9:00 (окно догона 2 часа); задание исполнителю: со временем в назначенную минуту, без времени в 9:00 в день вхождения; уже отмеченное (в том числе «на проверке») вхождение не напоминается. Ключ журнала `event:<id>` и `task:<id>` на подписку и день, адреса `/calendar/events/<id>` и `/tasks/<id>?date=`. Тесты: `tests/unit/reminders.test.ts`.
- **Ручной проход:** `cd scheduler && npm run notify:tick -- 10:05 [--reset]` (подписки берутся из БД, уведомление уйдёт на устройства, где оно включено).
- **Тесты** (`scheduler/tests/`, Vitest, нужна БД `npm run dev:infra`): своя база `family_tasks_scheduler_test` с миграциями из `../server/migrations`, файлы идут по очереди. `npm run test:scheduler` из корня или `npm test` в `scheduler/`; типы: `npm run typecheck`. CI: задание `scheduler`.
- **Состояние** (фаза 3): таблица `scheduler_state` (миграция `server`; экземпляр, `beat_at`, итог последнего прохода лидера `last_tick_at`/`last_sent`/`last_error`). `GET /api/admin/queue` отдаёт в `QueueStats` поле `scheduler` (`alive` если метка свежее минуты, `instances`, `lastBeatSeconds`, `lastTickSeconds` и `lastSent`/`lastError` последнего прохода среди экземпляров; поле добавлено обратно совместимо, на клиенте оно необязательное). Страница `/profile/service`: блок «Планировщик» (состояние, давность прохода, сколько поставлено) и предупреждения в `queueAlerts`: не отвечает → ошибка; жив, но проход не шёл дольше 5 минут (`TICK_STALE_SECONDS`) → предупреждение (пока проходов не было, молчим); последний проход с ошибкой → предупреждение с её текстом. В тестах `server` таблицу `scheduler_state` пишет только `admin.test.ts` (проверки точные).

## Медиа (`media/`)

Фазы 0–3 плана `docs/chat-photos-plan.md`: отдельный пакет и контейнер для фото из чатов (в `server` подключён, см. «Фото в чатах» в разделе про сервер; клиент см. «Фото в чатах» в разделе про клиент). Принимает JPEG от `server`, перекодирует, хранит в S3-совместимом хранилище и отдаёт по подписанным ссылкам. Базы данных нет: записи о файлах ведёт `server`. Код пакетов друг друга не импортирует, контракт описан образцом `contracts/media-v1.json` (контрольный пример подписи; его проверяют тесты `media` и `server`).

- **Внутренний API** (заголовок `x-internal-token` = `MEDIA_INTERNAL_TOKEN`, наружу nginx его не проксирует): `PUT /internal/media/:family/:id` (тело `image/jpeg`, ответ `{width, height, size, thumbSize}`; не JPEG или битый файл 422 `invalid_image`, слишком большой 413, другой тип 415), `DELETE /internal/media/:family/:id` (204, повтор безопасен), `GET /internal/media/:family` (`{items:[{id,size}]}` для уборки сирот), `DELETE /internal/families/:family`. Идентификаторы только uuid (иначе 400): в ключ не попадает произвольный путь.
- **Обработка** (`src/image.ts`): принимается только JPEG (сигнатура), перекодируется через `sharp`: ориентация применяется к пикселям, EXIF (геопозиция) пропадает, полный вариант до 1600 px (качество 82), превью до 480 px (75), без увеличения; защита от огромных картинок (50 Мпикс). Ключи в хранилище `<семья>/<файл>/full.jpg` и `thumb.jpg`.
- **Раздача** `GET /media/:family/:id/(full|thumb)?exp=&sig=`: `sig` это hex HMAC-SHA256 от `семья/файл/срок` секретом `MEDIA_SECRET` (`src/sign.ts`), срок в секундах Unix не в прошлом и не дальше 3 суток. Любая ошибка (подпись, срок, чужая семья, нет файла, неизвестный вариант) даёт один и тот же 404, по ответу ничего не узнать. `Cache-Control: private, max-age` до конца подписи (не больше суток), `ETag` и `304`. nginx проксирует только `/media/` (`web/nginx.conf`, `$media_upstream`).
- **Хранилище** (`src/store.ts`, интерфейс `BlobStore`: `put/get/delete/list/ping`): клиент `@aws-sdk/client-s3`, настройки `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION`, `S3_FORCE_PATH_STYLE`; значения без запасных в compose, без них `media` не стартует. У разработки отдельный бакет (локальный `.env`), у сервера свой. Бакет создаётся в кабинете рег.ру вручную; `media` при старте проверяет его и повторяет попытки (до двух минут), healthcheck (`GET /health`) проверяет бакет, `update.sh` ждёт `media` до трёх минут. Перенос с прежнего контейнера SeaweedFS сделан `rclone copy` (разово).
- **Настройки:** `MEDIA_SECRET` (подпись ссылок, после смены старые ссылки не открываются), `MEDIA_INTERNAL_TOKEN`, `MEDIA_MAX_UPLOAD_BYTES` (3 МБ), `PORT`. Без обязательных переменных сервис не стартует. В `.env.example` значения `change-me-…` для разработки, в проде задайте свои (`openssl rand -hex 32`).
- **Тесты** (`media/tests/`, Vitest): нужен S3: по умолчанию SeaweedFS на `localhost:8333` (одноразовая команда `docker run` в README, раздел про фото; контейнера в compose нет, адрес и ключи по умолчанию в `tests/s3.ts`, свой бакет `media-test`) или любой бакет через `S3_TEST_ENDPOINT`, `S3_TEST_ACCESS_KEY`, `S3_TEST_SECRET_KEY`, файлы идут по очереди; `unit/` подпись и обработка, `api/` хранилище и API на настоящем S3. Запуск: `npm run test:media` из корня или `npm test` в `media/`, типы `npm run typecheck`. CI: задание `media` (S3 поднимается `docker run` перед тестами: сервисы GitHub Actions не позволяют задать команду контейнера).
- **Копии и состояние** (фаза 3): `update.sh` фото не копирует (хранилище внешнее, копии бакета настраивайте у провайдера или `rclone`; прежнее копирование тома `s3` удалено). Копии БД и фото берите парой. `GET /api/admin/media` (`MediaStats`: `configured`, `alive` по `MediaClient.health()` = `GET /health` сервиса, `photos`, `bytes`, `unattached`, `quotaBytes`, `busiestFamilyBytes`; не администратору 404, без токена 401) и блок «Фото в чатах» на `/profile/service` (`useGetMediaStatsQuery`, опрос раз в 30 секунд, `mediaAlerts`: фото не настроены → пояснение, сервис не отвечает → ошибка, семья от 80% квоты → предупреждение, от 100% → ошибка; `formatBytes`). В тестах `server` таблица `media` общая: проверяйте нижние границы.
- **Проверка:** сервис проверен в Docker (образ на Alpine, `sharp` работает, `media` ждёт хранилище и становится healthy) и через nginx (фото открывается по верной подписи, при плохой 404, `/internal/` снаружи недоступен).

## Мобильное приложение (`mobile/`)

План и решения: `docs/mobile-app-plan.md` (фазы 0–9, статус фазы 2 в разделе «Состояние фазы 2»). Expo SDK 58, Expo Router (`src/app`), TypeScript, `styled-components/native`, RTK Query. **Общей кодовой базы с `web/` нет:** подходящие модули скопированы (`api/`, `store/`, `realtime/`, `lib/`, `identity/`, `profile/`) и дальше живут отдельно; исправление логики, нужное обоим, вносите в оба места, пока жива веб-версия. Пока в приложении: вход по email и коду, создание семьи и присоединение по приглашению, «Мой день» (настроение, уроки, тренировки, сводка по детям), разделы «Задания», «Семья», монеты и цели, профиль и тема, «Чат» с фото и файлами, расписания, «Что ты хочешь сообщить!», семейный календарь (уведомлений ещё нет) (приветствие, прогресс, задания на сегодня), табы с заглушками. Правила проекта те же (русский язык, комментарии на русском, защита от двойного нажатия, цвета из темы).

- **Команды:** `cd mobile && npx expo start`; `npm run typecheck`; `npm test` (Vitest в Node, около секунды; из корня `npm run test:mobile`); `npx expo-doctor`; сборка-проверка `npx expo export --platform android`. Версии пакетов ставьте только `npx expo install`; для Expo писать код по актуальной документации (`mobile/AGENTS.md`), SDK новее обычных знаний. CI: задание `mobile` (типы и тесты).
- **Адрес сервера:** `EXPO_PUBLIC_API_URL` (`lib/config.ts`; по умолчанию `http://localhost:8080`, на телефоне нужен адрес компьютера в сети). По нему API (`/api`), WebSocket и ссылки приглашений.
- **Хранение:** токен сессии в SecureStore (`identity/`), кэш данных и настройки в MMKV через `lib/kv.ts` (`getKv()`, синхронный интерфейс `KeyValueStore`; в Node и тестах хранилище в памяти, подмена `setKv`). MMKV и push не работают в Expo Go: нужна development-сборка.
- **Тесты** (`mobile/tests/`, Vitest, среда Node): только логика и хранилище данных; `react-native` и NetInfo подменены (`tests/stubs`, алиасы в `vitest.config.ts`), часовой пояс `Europe/Moscow`, адрес сервера в тестах `https://family.test`. Экраны проверяйте на устройстве; быстрый просмотр вёрстки в браузере: `npm run web:preview` (порт 8090, конфигурация `mobile-web` в `.claude/launch.json`; на вебе нет SecureStore и MMKV, поэтому вход не сохранится, на телефоне и в эмуляторе не проверялось).
- **Сборка APK** (`.github/workflows/mobile-apk.yml`): на каждый пуш в `main` с изменениями в `mobile/` (и вручную) Actions собирает подписанный APK (`expo prebuild` + `gradlew assembleRelease`, arm64 и armeabi-v7a) и пересоздаёт релиз `mobile-latest`; ссылка `https://github.com/<репозиторий>/releases/download/mobile-latest/moya-semya.apk` постоянная. Нужны секреты `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` и переменная репозитория `MOBILE_API_URL` (адрес сервера вшивается в сборку); создание ключа и секретов описано в `mobile/README.md`. Подпись и `versionCode` (номер запуска) подключает плагин `plugins/withReleaseSigning.js`; он падает с понятной ошибкой, если шаблон `build.gradle` в новом SDK Expo изменился. Ключ подписи нельзя терять: без него новые сборки не обновят установленное приложение. Папка `android/` в `.gitignore`; `expo prebuild` перезаписывает скрипты `android` и `ios` в `package.json`, после локального запуска верните `expo start --android` и `expo start --ios`. Локально сборка проверена на Windows (JDK 17, Android SDK 37, Gradle 9.4.1): APK около 39 МБ (arm64), подпись своим ключом и `versionCode` из окружения подтверждены `apksigner` и `aapt2`; на Linux в Actions workflow ещё не запускался. Ловушки Windows: лимит пути 260 знаков роняет ninja (`mkdir(...): No such file or directory`), у ninja 1.10 из Android SDK длинные пути не поддерживаются даже при `LongPathsEnabled`, поэтому локально собирайте скриптом `mobile/scripts/build-apk-windows.ps1` (короткая папка `E:m` и `ANDROID_CXX_STAGING=E:`, плагин передаёт её как `buildStagingDirectory`); в Groovy запись `versionCode (x).toInteger()` разбирается как вызов функции, пишите `versionCode Integer.parseInt(x)`.
- **Значки приложения** (`mobile/assets/images/*.png`) генерируются из `web/public/icon.svg` скриптом `node scripts/generate-icons.cjs` (в `mobile/`, берёт `sharp` из `media/node_modules`): `icon.png` для iOS, фон, передний план и одноцветный значок для адаптивных значков Android (рисунок в центральных ~60%), `splash-icon.png`, `favicon.png`. Меняете рисунок: правьте SVG в `web/public` и `HOUSE`/`CHECK` в скрипте и запускайте его заново.
- **Структура навигации** (`src/app/(app)`): внутри `(app)` лежит группа `(tabs)` с четырьмя главными разделами (`index` «Мой день», `tasks`, `chat`, `family`) и панелью табов в `(tabs)/_layout.tsx`, а рядом обычные экраны поверх них: `profile`, `coins`, `goals`, `calendar`, `lesson-report` (у каждой папки свой `_layout` со Stack). **Не прячьте разделы через `Tabs.Screen options={{ href: null }}`**: в этой версии Expo Router скрытая вкладка недоступна и переход на неё молча перенаправляет на первую вкладку («Мой день»; так «не открывался» профиль). Верхний правый угол (баланс монет ребёнка и значок профиля) рисует `TopRight` в `(app)/_layout.tsx` поверх экранов, поэтому заголовки страниц (`PageTitle`) оставляют справа `TOP_RIGHT_RESERVE`, а `Screen` сверху только небольшой отступ. Новые экраны делайте в `src/features/<раздел>/…Screen.tsx`, а в `app/` оставляйте тонкий файл маршрута.
- **Навигация «как в мобильных приложениях»:** в `(tabs)` лежат только корни четырёх разделов (`index`, `tasks/index`, `chat/index`, `family/index`) с панелью табов. Всё остальное (задание и его форма, переписка, участник семьи, приглашение, удаление семьи, цели, профиль, календарь…) лежит в `(app)` в общем Stack поверх табов, панель там скрыта (`tabBarVisible` в `lib/tabBar.ts` истинно только на четырёх корнях). Поэтому «назад» (стрелка слева сверху `BackLink`, жест, кнопка Android) возвращает именно на экран, откуда пришли (например, из задания, открытого в календаре, в календарь), а не на «Мой день». Не кладите экраны-вложения внутрь `(tabs)/<раздел>/`: открытие их из другого раздела переключает вкладку. Возврат кодом: `goBack(router, запасной адрес)` из `lib/navigation.ts` после сохранения, `router.dismissTo(адрес)` после удаления (страница удалённого объекта остаётся в стеке и её надо пропустить). URL-ы не менялись.

## Миграции БД

`node-pg-migrate`, SQL-файлы в `server/migrations/` с маркерами `-- Up Migration` / `-- Down Migration`. Сервер применяет их сам при старте (`server/src/migrate.ts`), поэтому в Docker отдельного шага нет. Применённые миграции не редактируем, любое изменение схемы — новый файл:

```bash
cd server && npm run migrate:create -- имя   # migrate:up / migrate:down — вручную
```

Откат кода не откатывает схему, поэтому перед обновлением с миграциями `update.sh` делает копию БД.

## Сервер: архитектура и правила

- **Вход по email + одноразовому коду** (`server/src/auth.ts`, таблица `email_codes`, purpose `signup`/`login`). Код 6 цифр, 10 минут, 5 попыток, повторная отправка раз в 60 с. Ответ на `POST /api/email-codes` одинаков для известного и неизвестного email (при `login` письмо уходит только известным; строка с кодом пишется всегда, чтобы cooldown не выдавал существование адреса). Не меняйте это поведение, не проверив, что оно не начало раскрывать email. **Капча** (Яндекс SmartCaptcha, `server/src/captcha.ts`): включается, когда в `.env` заданы `SMARTCAPTCHA_CLIENT_KEY` и `SMARTCAPTCHA_SERVER_KEY` (без них её нет: разработка и тесты). `POST /api/email-codes` принимает `captchaToken`; проверка первая в обработчике и не зависит от адреса: нет токена 400 `captcha_required`, не прошёл 400 `captcha_failed`; если сервис Яндекса не ответил (сеть, 5xx, неверный серверный ключ 403), проверка пропускается с записью в журнал (иначе его сбой не даст войти никому; от перебора защищает строгий лимит). `GET /api/captcha/config` (открытый) отдаёт `{siteKey}` или `null`. В `buildApp` проверяющий внедряется параметром `captcha` (в тестах подмена, `tests/api/captcha.test.ts`). Клиент мобильного приложения: `lib/captcha.ts` и `components/CaptchaHost` (невидимый виджет в WebView, страница `lib/captchaPage.ts`, подробности в `docs/mobile-app-plan.md`, «Капча в приложении»). Клиент веба: `lib/captcha.ts: getCaptchaToken` создаёт один невидимый виджет и на каждую отправку запрашивает новый токен (в том числе при «Отправить ещё раз»), его вызывает `requestEmailCode`; задание, если сервис сочтёт человека подозрительным, показывает сам виджет; отмена окна `captcha_cancelled`, недоступность `captcha_unavailable` (тексты в `lib/errors.ts`). В CSP добавлен `smartcaptcha.cloud.yandex.ru` (script, frame, connect, img). **Бюджет писем** (фаза 5): обработчик первым делом спрашивает `mailBudgetExhausted` (`outbox/budget.ts`): отправленное сегодня по UTC (`provider_usage`, счётчик `notifier`) плюс ждущие письма в `outbox` не меньше `MAIL_DAILY_LIMIT` (тот же, что у `notifier`, по умолчанию 2800, `0` без лимита; в compose передаётся и `server`) → `503 mail_busy`. Проверка стоит до выпуска кода и не зависит от адреса: ответ одинаков для известного и неизвестного email, код и пауза «раз в минуту» не создаются (после освобождения бюджета повтор проходит сразу). Клиент показывает «Сервис отправки писем сейчас перегружен. Попробуйте позже.» (`describeCodeError` на первом шаге и `describeResendError` в `CodeStep` при повторной отправке). Ответ 204 приходит сразу, без ожидания SMTP, а форма кода с таймером на 60 секунд уже показана. **Код и письмо фиксируются одной транзакцией** (`issueEmailCode(email, purpose, tx)` и `enqueue(tx, …)` в обработчике): сбой очереди откатывает и код, поэтому «код есть, письма нет» и пауза «раз в минуту» не возникают; при регистрации это честный 500 (`internal_error`), при входе сбой скрывается (204, как у неизвестного адреса: иначе ошибка выдала бы, что email известен). Прежних `502 mail_failed` и ручного `discardEmailCode` на этом пути больше нет.
- **Участник** = имя + email (оба уникальны в рамках семьи, email хранится в нижнем регистре) + роль (`mama`/`papa`/`grandma`/`grandpa`/`child`, правила в `server/src/roles.ts` и `web/src/lib/roles.ts`: `isParent` = мама/папа, `isAdult` = все кроме ребёнка). **Бабушка и дедушка** видят всё, что родители (все задания семьи, расписания, цели, монеты и историю детей, чаты), но ничего не меняют у детей: расписания уроков и тренировок (`authorizeChild(req, reply, true)` даёт 403 `parents_only`), цели (создание, изменение, удаление), монеты в чате, награда в задании, подтверждение заданий и очистка чата только у мамы и папы. Бабушка или дедушка, отметившие задание ребёнка с наградой, отправляют его на проверку, как ребёнок; push о проверке и о покупке цели получают только мама и папа. Ребёнок видит их в чате как «Бабушка» и «Дедушка». **В семье не больше 6 участников** (`MAX_FAMILY_MEMBERS`): вступление по приглашению седьмого даёт 409 `family_full` (проверка в транзакции под блокировкой семьи); создать семью могут только мама или папа, присоединиться любая роль. Один email может быть в нескольких семьях: `POST /api/auth/login` отвечает `409 choose_member` с вариантами, код при этом не сжигается и используется повторно со `memberId`. Создатель семьи — только мама или папа, получает `is_owner`; присоединиться по приглашению могут все три роли.
- **Приглашение по email** (`server/src/invites.ts`, таблица `invite_emails`). `POST /api/invite/email {email}` (только создатель семьи, строгий лимит): на адрес уходит письмо `kind: 'invite'` (`{inviterName, link, ttlMinutes}`, приоритет `event`) со ссылкой `<адрес сайта>/join?code=…&email=…`. Ссылка семьи берётся действующая (она не отзывается), если её нет или истекла, выпускается новая. Адрес сайта только из настроек сервера (`PUBLIC_URL`, иначе `https://DOMAIN`, иначе `http://localhost:8080`; в compose передаются обе переменные): адрес из запроса позволил бы слать письма со ссылкой на чужой сайт. Отказы: уже в семье 409 `already_member`, 6 участников 409 `family_full`, тот же адрес раньше чем через 10 минут 429 `too_soon`, больше 20 писем семьи за сутки 429 `invite_limit`, бюджет писем 503 `mail_busy`. Получатель открывает ссылку: поле email заполнено (`Join` читает `email`, `RoleForm initialEmail`), дальше обычное вступление: капча, код на почту, выбор роли. Клиент: страница `/family/invite` в двух карточках: «Выбрать контакты» (`pages/Invite/components/InviteByEmail`: «Выбрать из контактов», ссылка «Добавить адрес» открывает небольшое окно `AddEmailDialog`, кнопка «Пригласить: N» появляется, когда есть адреса) и «Отправить ссылку вручную» (`InviteSection`: ссылка выпускается сама, если её нет или она истекла, `components/LinkBox`: ссылка в одну строку со значком «копировать» справа и «Поделиться» там, где браузер умеет). «Выбрать из контактов» в вебе это Contact Picker API (`lib/contacts.ts`, только Chrome на Android; на iPhone и компьютерах кнопки нет), письма уходят по одному, у каждого адреса свой результат. Контракт письма: `contracts/outbox-v1.json` (`emailInvite`), отправляет `notifier` (`renderInvite`); выкладывайте `server` и `notifier` вместе (старый `notifier` отвергнет неизвестный вид письма).
- **Удаление семьи** (`family_deletions`, `server/src/familyDeletion.ts`, `scheduler/src/familyDeletion.ts`). `POST /api/family/deletion` (только создатель семьи, иначе 403; строгий лимит) оставляет заявку и отвечает `202 {requestedAt}`; повторная заявка ничего не меняет. Сам сервер ничего не удаляет: заявку исполняет **планировщик** на ближайшем проходе (раз в минуту, лидер под `pg_try_advisory_lock(7301002)`, не больше 5 семей за проход, работает и без ключей VAPID). Порядок: сначала `DELETE /internal/families/:family` сервиса `media` (все файлы семьи в хранилище; планировщику для этого нужны `MEDIA_URL` и `MEDIA_INTERNAL_TOKEN`, в compose заданы; без токена удалять в хранилище нечего и шаг пропускается), потом `delete from families`: все таблицы семьи связаны каскадом (участники, сессии, push-подписки, задания, расписания, чаты и сообщения, цели, монеты, события, приглашения, записи о медиа, сама заявка), email участников освобождаются. Если хранилище не ответило, семья остаётся целой, в заявке растут `attempts`, пишется `last_error`, повтор через 1, 2, 4 … минут (не дольше часа); сбой одной семьи не мешает остальным; в журнал (`family_deleted`, `family_deletion_failed`) попадают id семьи и число участников, без имён и адресов. Клиент: у создателя в самом низу `/family` ссылка «Удалить семейный аккаунт» → `/family/delete` (`pages/FamilyDelete`: что будет удалено, красная «Удалить», подтверждение `useConfirm`, после заявки прощание «Данные вашей семьи будут удалены… Надеемся, мы ещё увидимся!» и «До встречи!»: выход на этом устройстве и стартовая страница; не создателя страница возвращает на `/family`). Остальные участники теряют доступ, когда планировщик удалит строки: их сессии пропадают, следующий запрос даёт 401 и приложение выходит само. Отмены и отсрочки нет.
- **Удаление своего аккаунта** (`server/src/account.ts`, `DELETE /api/me`, 204, строгий лимит). Нельзя ребёнку (403 `children_cannot_delete`) и создателю семьи (403 `owner_cannot_delete`: у него только удаление всей семьи). Всё в одной транзакции под блокировкой строки участника: удаляются его сообщения, **личные чаты с ним целиком** (в том числе сообщения собеседников; ключ `a:b` разбирается через `split_part`), чаты созданных им событий, записи `chat_reads/mutes/archives/visits` этих чатов, записи `media` (загруженные им и вложения в удалённых чатах), затем сама строка `members`, от которой каскадом уходят задания (где он автор или исполнитель), цели, монеты, события, игры, подписки и сессии. Файлы убираются из хранилища `media` после фиксации (недоступное хранилище оставляет лишь занятое место). Остальным участникам уходят сигналы `members`, `tasks`, `events`, `games` и `chat`. Клиент: пункт «Удалить аккаунт» в конце меню профиля (только не ребёнку и не создателю), страница `/profile/delete` (`pages/AccountDelete`, в приложении `features/profile/AccountDeleteScreen`): что исчезнет, подтверждение `useConfirm`, прощание и «До встречи!» (выход на устройстве). Тесты: `server/tests/api/account.test.ts`, `web/tests/components/AccountDelete.test.tsx`.
- **Сессии** (`sessions`): по одной на устройство, клиент хранит токен в IndexedDB, в БД SHA-256 хэш, `Authorization: Bearer`. `DELETE /api/session` отзывает только текущую.
- **Приглашения** (`invites`): многоразовые, 7 дней. Новое приглашение удаляет старые (так можно отозвать утёкшую ссылку). Ссылка вида `/join?code=...`. Владелец видит и перевыпускает его на странице семьи.
- **Профиль и фото.** `PATCH /api/me` меняет имя (уникально в семье, иначе `409 name_taken`), фото и дату рождения; email и роль менять нельзя. Дата рождения (`members.birth_date`, тип `date`) ходит строкой `YYYY-MM-DD`: на сервере её всегда читают через `to_char(...)`, на клиенте разбирают вручную (`web/src/lib/date.ts`), потому что `new Date('YYYY-MM-DD')` и драйвер `pg` сдвигают день по часовому поясу. Проверка: реальная дата, не раньше 1900 и не в будущем (запас сутки на пояса), `null` очищает; ошибка `invalid_birth_date`. Фото хранится прямо в `members.avatar` как data URL (jpeg/png/webp, не больше 70 000 символов, ограничено схемой и `check` в БД). Клиент перед отправкой обрезает его до квадрата 128×128 JPEG (`web/src/lib/image.ts`, около 3–10 КБ), поэтому сервер ничего не ресайзит и не должен принимать оригиналы. Фото и дата рождения приходят в `/api/me` для всех участников семьи. Fastify вырезает неизвестные поля (`removeAdditional`) уже после `minProperties`, так что пустой итоговый патч проверяется вручную.
- **Расписание уроков** (`schedule_lessons`, `server/src/schedule.ts`): только у участников с ролью `child`, дни 1–6 (Пн–Сб), у урока предмет, необязательные время начала и конца (окончание строго позже начала) и необязательный кабинет (`room`, текст до 12 знаков, пустой становится `null`; виден в просмотре расписания и на «Моём дне» подписью «каб. 12а», в редакторе узкое поле «Каб.» после времени, в push не входит), не больше 12 уроков в день. Сохраняется целиком через `PUT /api/members/:id/schedule`; порядок уроков в дне равен порядку в массиве.
- **Расписание тренировок** (`training_sessions`, `server/src/trainings.ts`) устроено так же, но дни 1–7 (Пн–Вс, ISO: воскресенье = 7, в отличие от `Date.getDay()`; помощники в `web/src/lib/weekdays.ts`), у тренировки название, необязательные место и время, не больше 8 в день. `GET/PUT /api/members/:id/trainings`.
- **Доступ к расписаниям** (`server/src/access.ts`, `authorizeChild`): читать и менять может сам ребёнок и любой родитель (мама/папа) его семьи, другие дети получают 403, чужая семья 404, не-ребёнок 400.
- **Задания** (`tasks`, `task_completions`, `server/src/tasks/`). Любой член семьи создаёт задание себе или другому. **Повторяющиеся задания в «Предстоящих»:** список просит `collapse=true`, и у серии остаётся одно текущее вхождение (`from` считается сегодняшним днём): есть вхождение на `from`, оно, выполненное или нет; иначе ближайшее будущее, но только если предыдущее вхождение серии (`previousOccurrence` в `tasks/recurrence.ts`, просмотр назад до 70 дней) не выполнено или его не было; выполненное предыдущее значит, что следующее появится только в свой день. Без `collapse` (блок «Задания на сегодня», карточки детей) список как раньше. **Видимость:** родители видят все задания семьи, ребёнок только свои (назначенные ему и созданные им); это проверяет сервер (`visibility`/`findTask` в `tasks/routes.ts`: список, «выполненные», просмотр, изменение, удаление, отметка), чужое задание ребёнка отвечает 404 как несуществующее. Сигнал сокета `tasks` уходит всей семье (в нём нет данных), а запрошенные после него данные уже отфильтрованы. Менять и удалять (`PUT/DELETE /api/tasks/:id`) может только автор (иначе 403), отмечать выполненным и снимать отметку (`POST /api/tasks/:id/complete|uncomplete`, тело `{date}`) — любой в семье. У задания необязательное описание (`description`, до 1000 символов, обрезается по краям; форма отправляет его целиком, без поля при `PUT` оно очищается). `GET /api/tasks/:id?date=` отдаёт задание и одно его вхождение `occurrence` (по умолчанию первое или «без срока», `null`, если такого вхождения нет). Срок необязателен: без даты это «без срока»; время допустимо только с датой. Повтор `none|daily|weekly|monthly` (`weekly` с днями 1–7, `monthly` на то же число, в коротком месяце на последний день), необязательное `until`. Расписание повторов считает только сервер (`tasks/recurrence.ts`, чистые функции с проверкой на граничных случаях); клиент получает готовые вхождения: `GET /api/tasks?from&to[&collapse=true]` (не больше 62 дней) отдаёт `{tasks, occurrences}`: вхождения периода, невыполненные просроченные разовые и задания без срока; `GET /api/tasks/done` — недавно выполненное. Выполнение хранится по каждому вхождению (`task_completions`, для задания без даты дата-заглушка `1970-01-01`), поэтому повторяющееся задание отмечается отдельно в каждый день; при смене графика отметки сбрасываются, при смене названия сохраняются. Уведомления (`enqueueToMember` в `outbox/index.ts`, тексты в `tasks/text.ts`): исполнителю при создании и изменении (если задание дал не он сам), автору при первой отметке выполнения (если выполнил не он сам). Напоминаний «в срок» нет.
- **Отправка писем и push идёт через `server/src/outbox/`** (план `docs/notification-queue-plan.md`): `server` ничего не отправляет сам, а ставит элемент через `enqueue(db, item)` (или `enqueueToMember(db, memberId, message)` для всех устройств участника; приоритеты `PRIORITY.code/event/planned`); отправляет сервис `notifier`. Типы элементов и payload версии `v: 1` в `outbox/contract.ts` (менять только обратно совместимо). `enqueueRow` (`queueDriver.ts`) вставляет строку в `outbox` и шлёт `pg_notify('outbox')`; срок жизни `expires_at`: у письма столько же, сколько у кода, у push 6 часов; если `db` это клиент транзакции, строка появляется вместе с остальными изменениями, а сигнал уходит при фиксации. `enqueue` ничего не возвращает. **Склейка по `tag`**: ещё не взятое в работу (`attempts = 0`) push-сообщение с тем же `tag` для той же подписки заменяется новым, как это делает само устройство; строка, которую `notifier` уже забрал (`attempts > 0`), не трогается, в том числе при гонке (PostgreSQL перепроверяет условие после блокировки, есть тест). Письма не склеиваются. Новую отправку пишите только через `enqueue`.
- **Push-уведомления** (`server/src/push.ts`, таблицы `push_subscriptions` и `notification_log`). Сам Web Push отправляет `notifier`, плановые уведомления (день рождения 10:00, уроки следующего учебного дня 17:00 детям, тренировка за 2 часа) планирует отдельный сервис `scheduler/` (раздел «Планировщик» выше; из `server` он удалён). Серверу нужен только публичный ключ VAPID из `.env` (без него функция выключена, `/api/push/*` отвечают 503, уведомления не ставятся). Подписку с ответом push-сервиса 404/410 удаляет `notifier`. Адрес подписки принимается только у известных push-сервисов (`ALLOWED_SUFFIXES` в `push.ts`, для тестов `PUSH_ALLOWED_HOSTS`): сервер сам обращается по этому адресу, иначе это SSRF. `isValidTimeZone` для часового пояса подписки лежит в `lib/timeZone.ts`. Подписка привязывается к устройству (`endpoint`) и переходит к тому, кто вошёл на нём последним.
- **Фото в чатах** (фаза 1 плана `docs/chat-photos-plan.md`; сервис `media/` описан в разделе «Медиа»). Таблицы `media` (запись о файле: семья, загрузивший, размеры, размер полного варианта, `attached_at`) и `message_media` (фото сообщения по порядку), у `messages` признак `photo_only`. Загрузка `POST /api/chats/:chat/media`: сырой JPEG (`content-type: image/jpeg`, до 3 МБ, иначе 413/415), нужен доступ к чату; проверяется квота семьи (`MEDIA_QUOTA_BYTES`, по умолчанию 2 ГБ по сумме `media.size`, сверх 413 `media_quota`), файл уходит в сервис `media` (отклонён 400 `invalid_media`, сервис недоступен 502 `media_unavailable` без подробностей, фото не настроены 503 `media_disabled`), отвечает `{mediaId, width, height}`; свой лимит 60 запросов в минуту; в nginx для этого адреса тело до 4 МБ. Отправка `POST /api/chats/:chat/messages` принимает `{text?, mediaIds?}` (до 10 фото, порядок сохраняется, нужен текст или фото, иначе 400 `invalid_text`): в одной транзакции под блокировкой проверяется, что все файлы загрузил этот же участник в этой семье и они ещё не прикреплены (иначе 400 `invalid_media`, сообщение не создаётся), ставится `attached_at`. **Совместимость со старым клиентом:** у сообщения только с фото в `text` заглушка («📷 Фото», для нескольких «📷 Фото ×3»), `photo_only = true`; в DTO сообщения `text` это значение из базы, `caption` подпись (пустая у сообщения только с фото), `media` список `{id, width, height, thumbUrl, fullUrl}`. Новый клиент показывает `caption` и `media`, старый видит заглушку. Ссылки подписаны (`media/sign.ts`, тот же алгоритм и контрольный пример `contracts/media-v1.json`, что у сервиса `media`), срок кратен суткам (`expiryFor`), поэтому адрес фото в течение суток не меняется и браузер его кэширует; адреса строятся при каждой выдаче сообщений (чаты, список чатов, ответ на реакцию), так что доступ определяется доступом к чату. Уведомление: «📷 Фото» или «📷 подпись»; в списке чатов превью берёт `last.text`. **Файлы в чатах** (документы, архивы и т. п., не фото): тот же путь, что у фото, в той же таблице `media` (`kind = 'file'`, `file_name`, `size` это размер файла, размеров картинки нет; квота семьи, сироты и очистка общие). Загрузка `POST /api/chats/:chat/files`: сырые байты (`content-type: application/octet-stream`), имя в заголовке `x-file-name` (в процентной записи UTF-8), до 50 МБ (`MAX_FILE_BYTES` у `server`, `MEDIA_MAX_FILE_BYTES` у `media`; в nginx для этого адреса тело до 51 МБ и таймауты 5 минут; запрещённые виды те же, предел поднят с 10 МБ), 30 запросов в минуту; имя очищается от пути и управляющих знаков (`cleanFileName`), исполняемое, сценарии и страницы (`exe`, `bat`, `js`, `sh`, `html`, `svg` и др., по последнему расширению, `BLOCKED_EXTENSIONS` в `media/index.ts`, копия в `web/src/lib/files.ts`) дают 415 `file_type_blocked`; ответ `{fileId, name, size}`. Содержимое не разбирается и не исполняется: сервис `media` кладёт байты как есть (`PUT /internal/files/:family/:id`, ключ `<семья>/<id>/file`) и отдаёт `GET /media/:family/:id/file?exp&sig&name` только как `application/octet-stream` с `Content-Disposition: attachment`, `nosniff` и `CSP: sandbox` (имя в `name` не подписано и очищается, `contentDisposition`). Отправка `POST …/messages` принимает `fileIds` (до 5, после фото; виды не путаются: файл нельзя отправить как фото и наоборот, иначе 400 `invalid_media`); в DTO сообщения `files: [{id, name, size, url}]` (у прежних сообщений пусто), у сообщения только с файлами `photo_only` и заглушка в `text` («📎 имя» или «📎 Файлы ×N», для старых клиентов), push «📎 …». Список всех фото чата (`/media`) файлы не показывает. Клиент: скрепка в `Composer` принимает любые файлы (картинки идут фото, остальное файлами, до 5; размер и запрещённый вид проверяются на устройстве, `lib/files.ts`), в пузыре файл строкой с именем и размером, нажатие сохраняет без ухода со страницы (`lib/saveFile.ts`, как «Сохранить» у фото), в списке чатов «📎 имя». Выкладывайте `server` и `media` вместе (новый `server` вызывает `/internal/files/`).
  **Видео в чатах** (до 100 МБ и 3 минут, до 3 в сообщении, веб и приложение). Сервис `media` сжимает видео настоящим `ffmpeg` (в образе `apk add ffmpeg`, около 100 МБ; `media/src/video.ts: createFfmpegProcessor`): проверка `ffprobe` (есть видеопоток, длительность не больше `MEDIA_MAX_VIDEO_SECONDS`, иначе 422 `video_too_long`, не видео 422 `invalid_video`), MP4 H.264 + AAC, длинная сторона до 1280, `crf 28`, `+faststart`, кадр-превью 480 px (`thumb.jpg`, как у фото); обработки идут по одной (очередь в процессе), сжатие занимает секунды, у долгого видео десятки. Внутренний API `PUT /internal/videos/:family/:id` (тело `video/*`, предел `MEDIA_MAX_VIDEO_BYTES`, ответ `{width, height, duration, size, thumbSize}`, размеры уже после поворота и сжатия), ключ в хранилище `<семья>/<id>/video.mp4`; раздача `GET /media/:family/:id/video?exp&sig` **с поддержкой `Range`** (206, `Content-Range`, `Accept-Ranges`; 416 при плохом диапазоне; это единственный вариант с Range, `BlobStore.get(key, range)`), удаление и подсчёт места учитывают видео. Без ffmpeg проверка сжатия в тестах пропускается (`describe.skipIf`, на Windows разработчика его нет; запуск в контейнере: `docker run --rm -e S3_TEST_ENDPOINT=http://host.docker.internal:8333 -v …/media:/src:ro node:22-alpine`, `apk add ffmpeg`, копия без `node_modules`, `npm ci`, `npx vitest run tests/unit/video.test.ts`), в CI ffmpeg ставится. Сервер (миграция `…038000`: `media.kind = 'video'`, колонка `duration`): `POST /api/chats/:chat/videos` (сырой файл с `video/*`, `MAX_VIDEO_BYTES` у `server`, 10 запросов в минуту, квота семьи общая, `MediaRejected` с кодом превращается в 400 `video_too_long` или `invalid_video`, ответ `{videoId, width, height, duration}`; клиент `uploadVideo` ждёт до 5 минут), отправка принимает `videoIds` (до 3, после фото и файлов, виды не путаются), в DTO `videos: [{id, width, height, duration, thumbUrl, url}]`, заглушка в `text` «🎬 Видео» или «🎬 Видео ×N» (смешанные «📎 Вложения ×N»), push «🎬 …»; список фото чата видео не показывает. nginx: у `/api/chats/*/videos` тело до 101 МБ и таймауты 10 минут, в CSP добавлен `media-src 'self' blob:` (без blob: не читается длительность до загрузки). Клиенты: веб (`lib/video.ts`, `Composer` принимает видео по типу или расширению, длительность читается из метаданных `<video>`, видео в списке вложений со статусом «Загружается и обрабатывается…», `MessageBubble` показывает кадр с кнопкой «играть» и длительностью, `VideoViewer` это плеер браузера); приложение (`lib/video.ts`, пункты «Видео из галереи» и «Снять видео» в меню скрепки, длительность из `ImagePicker`, плеер `expo-video` в `features/chat/VideoPlayer.tsx`: нативный модуль, нужна новая сборка APK и iOS). Видео из «Поделиться» идёт как видео (`classifyShared` кладёт его в `videos`, `Composer` прогоняет через `addVideos`; длительность неизвестна, её проверяет сервер, размер до 100 МБ проверяется на устройстве), остальное как файлы до 50 МБ. **Потоковая загрузка.** Файлы (до 50 МБ) и видео (до 100 МБ) не лежат в памяти целиком: `server` принимает тело потоком (разборщики `application/octet-stream` и `video/*` в `app.ts` отдают поток, а не буфер), берёт размер из `Content-Length` (без него 411 `length_required`, больше предела 413 `payload_too_large`, предел Fastify `bodyLimit` для потока не действует), проверяет по нему квоту семьи и передаёт поток в `media` по `http` с тем же `Content-Length` (`createMediaClient`: `uploadFile(family, id, stream, length)`, `uploadVideo(family, id, stream, length, type)`); `limitedStream` обрывает поток, если пришло больше заявленного. `media` складывает тело во временный файл на диске (`spool.ts`, лишнее сверх предела отбрасывается, а тело дочитывается до конца, иначе клиент не получит 413), кладёт его в хранилище потоком (`BlobStore.putFile`), а видео сжимает прямо из файла (`VideoProcessor.process(inputPath)` возвращает путь к результату и `cleanup`). Временные файлы лежат в системной папке контейнера `media` (до размера загрузки, плюс результат сжатия видео) и убираются в `finally`. Проверено на сквозной загрузке 49 МБ: память `server` и `media` остаётся около 110 МБ (раньше росла на размер файла в каждом из двух сервисов). Фото (до 3 МБ) по-прежнему буфером. **Выкладка:** образ `media` пересобирается с ffmpeg (первая сборка дольше), выкладывайте `server`, `media` и `web` вместе; старые клиенты видят у сообщения с видео заглушку «🎬 Видео».

**Все фото чата:** `GET /api/chats/:chat/media?before=<id фото>&limit=` (доступ как к чату; свежие сообщения первыми, внутри сообщения по порядку; страницы по 60; отдаёт `{items:[{id, width, height, thumbUrl, fullUrl, messageId, senderId, createdAt}], hasMore}`, без настроенных фото пусто). Клиент: пункт «Медиа файлы» в меню чата (`useChatActions`) ведёт на `/chat/:chat/media` (`pages/ChatMedia`: сетка превью по три, подгрузка по прокрутке и кнопкой «Показать ещё», нажатие открывает `PhotoViewer`; это обычная страница с панелью табов, `AppShell` не считает её экраном переписки). **Уборка:** `media/cleanup.ts: deleteOrphanMedia` при старте и раз в сутки убирает записи без прикрепления старше суток вместе с файлами (недоступный `media` оставляет запись до следующего раза). Фото не настроены (`MEDIA_SECRET` или `MEDIA_INTERNAL_TOKEN` пусты): `buildApp` получает `media: null`, текст в чатах работает как раньше. В `buildApp` клиент `media` внедряется параметром (`media: { client, secret }`), в тестах это `FakeMedia` (`tests/api/chat-media.test.ts`). Файлы удалённой семьи и сообщений в хранилище пока не чистятся: удаления семей и сообщений в приложении нет, при их появлении они должны вызывать `DELETE /internal/families/:family` и `DELETE /internal/media/…` сервиса `media`.
- **Монеты детей** (`coin_transactions`, `server/src/coins.ts`). У детей есть баланс виртуальных монет. Он не хранится числом, а считается как сумма журнала (`amount` > 0 начисление, < 0 списание, 0 нельзя, `reason` до 200 знаков; баланс может быть отрицательным); `coinBalance(db, memberId)`. У записи есть автор `created_by` (участник семьи, `null` для системы или если автор удалён). История: `GET /api/coins?before=<id>&limit=&memberId=` (ребёнок видит свою; родитель только с `memberId` ребёнка своей семьи: без него 403 `not_a_child`, чужая семья 404 `member_not_found`, не ребёнок 400 `not_a_child`; ребёнку чужой `memberId` 403 `forbidden`; свежее сверху, страницы по 30, `before` это id самой старой загруженной записи, курсор по `(created_at, id)`; отдаёт `{balance, items:[{id, amount, reason, createdAt, createdBy}], hasMore}`). Баланс отдаёт `GET /api/me` и только самому ребёнку (`member.coins`; у родителей поля нет, в списке `members` монет нет). Способов получить монеты пока нет (ни награды за задания, ни ручного начисления): будущие начисления пишите строкой в журнал и публикуйте `publish(familyId, { type: 'members' })`, тогда клиент обновит `/api/me`. В демо-семье дети получают стартовые монеты (`npm run seed`).
  **Подтверждение родителем:** задание с наградой ребёнок только отправляет на проверку, награду выдаёт подтверждение родителя (любого). `POST …/complete` от ребёнка при `reward > 0` создаёт отметку `pending` (`task_completions.pending`, монет нет; push обоим родителям «Задание на проверку», `reviewMessage`); от родителя выполнение сразу подтверждённое с наградой, а если вхождение уже ждёт проверки, то подтверждает его (`completeOccurrence` в `tasks/routes.ts`). Явное подтверждение: `POST …/confirm {date}` (только родитель, иначе 403 `parents_only`; если проверять нечего, 400 `not_pending`, побочных эффектов нет). `uncomplete`: отправку снимает ребёнок или возвращает на доработку родитель (монет нет); подтверждённое задание с наградой ребёнок снять не может (403 `confirmed`), родитель может (награда возвращается). Вхождение в API: `done` только у подтверждённого, `pending` `{memberId, at}` у ожидающего проверки (оба `null` у открытого); ожидающее не попадает в «Выполненные» и в «заработано», а просроченное ожидающее остаётся в списке за период. `GET /api/tasks/pending` отдаёт все ожидающие (родителю по семье, ребёнку свои). Без награды всё как раньше: ребёнок завершает сам. **Награда за задание:** у задания поле `reward` (0–1000, по умолчанию 0; только если исполнитель ребёнок, иначе 400 `reward_requires_child`, и только если задание создаёт родитель: ребёнок не может назначить награду ни себе, ни другому ребёнку, 400 `reward_requires_parent`; проверка `rewardError` и при создании, и при изменении). При первой отметке вхождения (`POST …/complete`, в одной транзакции с отметкой) исполнителю пишется начисление `+reward` с причиной «Задание: название» от имени автора задания (запись связана с заданием и вхождением: `task_id`, `occurrence_date`), кто бы ни отметил (ребёнок сам или родитель), и публикуется `members`; за повторяющееся задание награда выдаётся за каждое выполнение отдельно. Снятие отметки (`uncomplete`) и смена графика задания (отметки сбрасываются) забирают выданное: `revokeRewards` пишет отмену на величину ещё не отменённого начисления по каждому ребёнку и вхождению («Отмена: …»), поэтому отметки и снятия по кругу не дают лишних монет. Смена награды после выполнения уже выданное не трогает; удаление задания оставляет монеты (связь с заданием обнуляется). Если выполнил не сам исполнитель, ему уходит push «Награда» (`rewardMessage`, ведёт на `/coins`).
- **Чат** (`messages`, `chat_reads`, `server/src/chat.ts`). У каждого общий чат семьи и по личному чату с каждым другим участником (ключ чата `chat_key`: `family` или id обоих через двоеточие по возрастанию, поэтому у собеседников он один; личное видят только двое). В API чат называется «глазами» участника: `family` или id собеседника. `GET /api/chats` (все чаты с последним сообщением, числом непрочитанных и `readUpTo` (как в `GET …/messages`; по нему в списке у моего последнего сообщения галочки рядом со временем, `lastMessageStatus`, `components/ReadTicks`: одна «отправлено» серая, две «прочитано» акцентные, у чужого последнего сообщения нет); сортировка по времени последнего сообщения, без сообщений в конце: сначала общий, потом по имени), `GET/POST /api/chats/:chat/messages` (страницы по 50 от свежих к старым, `?before=<id самого старого загруженного>`; только текст, 1–2000 знаков после обрезки), `POST /api/chats/:chat/read`. Статус своих сообщений («отправлено» / «прочитано»): `GET …/messages` отдаёт `readUpTo`, момент, до которого прочитали остальные участники чата (в личном это отметка собеседника, в общем самая поздняя среди остальных: «прочитано», как только прочёл хотя бы один (как в группах Telegram; раньше требовалось, чтобы прочли все, и один неактивный участник навсегда оставлял сообщения «отправленными»), своё прочтение автора не считается; у ни разу не открывавшего чат отсчёт с его появления в семье); сообщение прочитано, если `createdAt <= readUpTo`. Непрочитанные считаются от `chat_reads.last_read_at`, а для нового участника от даты его появления (старая история непрочитанной не считается); своё сообщение отмечает чат прочитанным у автора, ответ тоже считается прочтением. Уведомления: при отправке `enqueueToMember` каждому участнику чата, кроме автора (в общем чате «Имя · Общий чат», в личном «Имя»; текст сжат до одной строки и 140 знаков; `tag: chat-<чат>` склеивает уведомления одного чата, нажатие ведёт на `/chat/<чат>`). Сигнал сокета `{type:'chat', chat}` уходит только участникам чата (`publishTo`, не всей семье) и содержит чат глазами получателя; `POST …/read` шлёт его другим устройствам этого же участника и остальным участникам чата (у них обновятся галочки), и только если что-то было непрочитано, иначе открытая переписка зациклилась бы на собственных отметках. **Уведомления и очистка** (`chat_mutes`, миграция `…026000`): `PUT /api/chats/:chat/mute {muted}` отключает push о сообщениях чата только для себя (на всех своих устройствах; строка `chat_mutes (member_id, chat_key)`), `GET /api/chats` отдаёт `muted` у каждого чата, отправка сообщения не ставит push тем, кто отключил (непрочитанный счётчик остаётся; push о реакциях и монетах отключение не затрагивает). `DELETE /api/chats/:chat/messages` очищает чат у всех участников безвозвратно: только мама или папа (иначе 403 `parents_only`), личный чат только свой (`resolveChat`); в одной транзакции удаляются сообщения (реакции и связи с фото каскадом, монеты остаются) и записи `media` их фото, после фиксации файлы убираются из хранилища (недоступный `media` только пишет предупреждение: запись уже удалена, файл остаётся занятым местом); участникам уходит сигнал `chat`.
- **Ответы, правка и удаление сообщений** (миграция `…034000`: `messages.reply_to` с `on delete set null`, `edited_at`). `POST …/messages` принимает `replyTo` (сообщение этого же чата, иначе 400 `invalid_reply`); в DTO `replyTo: {id, senderId, text}|null` (выдержка до 140 знаков, после удаления исходного `null`) и `editedAt`. `PATCH /api/chats/:chat/messages/:id {text}` и `DELETE …/:id`: только автор (чужое 403 `forbidden`, нет сообщения 404), у сообщения только с вложениями без подписи правка 400 `not_editable`; удаление убирает записи `media` и файлы, как очистка чата, реакции пропадают, монеты остаются; участникам уходит сигнал `chat`. Клиенты: действия «Ответить», «Изменить», «Удалить» в окне долгого нажатия (`FeedbackDialog`), цитата в пузыре, отметка «изменено», плашка в `Composer`. Push об ответе и правке отдельно не шлются.
- **Игры** (`games`, миграция `…035000`, `server/src/games.ts`, приложение и веб; готовы шахматы, крестики-нолики (миграция `…037000` расширила `kind`) и шашки (миграция `…039000`), морской бой заглушка в `features/games/utils.ts` и `web/src/lib/games.ts`). Один участник приглашает другого: `POST /api/games {kind, opponentId}` (push «зовёт играть»; между двумя участниками одна открытая игра каждого вида, иначе 409 `game_exists` с игрой в ответе), `accept` (только приглашённый; белые назначаются случайно, ход у белых), `decline` (приглашённый) и `cancel` (пригласивший); `GET /api/games` (приглашения, идущие и завершённые за 24 часа), `GET /api/games/:id`. Ход `POST …/move {from,to}` (превращение пешки в ферзя): правила и конец игры (мат, пат, ничья) считает `chess.js` на сервере, позицию он каждый раз восстанавливает по списку ходов (`state.moves`, работают повторения и правило 50 ходов), ошибки `not_your_turn`, `illegal_move`, `not_active`; `resign` — сдаться. **Крестики-нолики** (`kind: 'tictactoe'`): состояние `state {board, cells}` (поле 9 знаков по строкам «X»/«O»/«-», клетки по порядку ходов), первым ходит и играет крестиками тот, кто в `white_id` (случайно при принятии); ход `POST /api/games/:id/place {cell: 0..8}` (ошибки `cell_taken`, `not_your_turn`, `not_active`, `wrong_game` для ходов не того вида), итог `result.reason: 'line'` (победа) или `'draw'` (поле заполнено); в DTO `board`, `cells`, `lastCell` (у шахмат `board: null`), у крестиков-ноликов `fen` пуст. Клиенты: `TicTacToeBoard` (`components/` в вебе, `features/games/` в приложении), `winningLine` продублирована в `lib/ticTacToe.ts` и `features/games/ticTacToe.ts`; новую игру добавляйте так же: вид в `GAME_KINDS`, ход отдельным маршрутом, доска и ветка в экране игры. **Шашки** (русские, `server/src/checkers.ts`): правила только на сервере, клиенты рисуют доску и отправляют выбранный путь. Поле это 64 знака (`state.board`: ряды снизу вверх, a1 это знак 0, `.` пусто, `w`/`W` белая шашка/дамка, `b`/`B` чёрная), первым ходит и играет белыми тот, кто в `white_id` (случайно при принятии). Шашка ходит вперёд на клетку и бьёт во все стороны, дамка ходит и бьёт издалека; бить обязательно (большинство не обязательно), удар продолжается до конца, шашка, дошедшая до последнего ряда в ходе удара, бьёт дальше как дамка, побитые снимаются после хода (одну фигуру дважды не бить, она мешает проходу), с клетки приземления дамки, откуда удар можно продолжить, вставать обязательно. Ход `POST /api/games/:id/play {path}`: путь клеток («c3», «e5», «g7»; при ударе все остановки), он должен совпасть с одним из допустимых (`DTO.legal`: допустимые ходы того, чей ход), иначе 400 `illegal_move`; `lastPath` последний ход, `board` поле. Конец: у соперника нет ходов или фигур (`reason: 'no_moves'`), ничья после 30 полуходов дамками без боя и хода шашкой (`quiet`) или по соглашению (общие маршруты `draw/*` у шахмат и шашек). Клиент (`CheckersBoard` в вебе и приложении): нажатие на шашку, у которой есть допустимый ход, показывает следующие клетки, удар в несколько прыжков набирается клик за кликом и уходит, когда путь совпал с допустимым целиком. После окончания игры вместо строки статуса под доской показывается итог с кнопками «Новая партия» (приглашение тому же ссопернику в ту же игру сразу, без подтверждения; если игра с ним уже есть, открывается она, `game_exists`) и «Выйти»; отдельного серверного маршрута для реванша нет. Итог в `result {winnerId, reason}`. **Счёт** между мной и одним участником: `GET /api/games/score?opponentId=` отдаёт `{scores: [{kind, wins, losses, draws}]}` по всем видам игр (нули, если партий не было), считается по завершённым партиям таблицы `games` (сдача и ничья по соглашению входят, незавершённые и отклонённые нет), побед и поражений со стороны спрашивающего. Менять правила звука нужно в обоих местах, тесты `gameSound.test.ts` есть и там и там. **Подписи линий** на досках шахмат и шашек как на chess.com: номер ряда в левом верхнем углу клеток первого столбца, буква вертикали в правом нижнем углу клеток нижнего ряда, цвет контрастный к клетке; у чёрных доска и подписи перевёрнуты (веб: `Coord` в `ChessBoard/styles.ts` и `CheckersBoard/styles.ts`, приложение: `features/games/BoardCoord.tsx`, шрифт приложения не масштабирует подпись; тест порядка подписей в `ChessBoard.test.tsx` и `CheckersBoard.test.tsx`). Все вызовы сейчас стоят после `commit` (проверено), новый `publish` пишите так же. Сигнал по сокету это только «что изменилось» (`tasks`, `members`, `schedule`/`trainings` с `memberId`, …), без данных: клиент заново запрашивает данные обычными запросами, где доступ проверяется как всегда. Контракт сообщения канала `{v:1, to:'family'|'member'|'session', id, event}` (`to: 'session'` закрывает соединения, `id` это SHA-256 токена): образец `contracts/realtime-v1.json`, типы продублированы в `server/src/realtime.ts` и `realtime/src/contract.ts`, образец проверяют тесты обоих пакетов. Первое сообщение клиента `{"type":"auth","token":"…"}` (токен не в адресе, иначе он попадёт в журналы прокси), ответ `{"type":"ready"}`; не авторизовавшийся за 10 с, с неверным токеном и после выхода с устройства закрывается кодом 4401. **Новый вид события сокета** добавляйте в четыре места клиентов (веб и приложение): тип в `realtime/types.ts`, разбор в `realtime/utils.ts: parseMessage`, теги в `store/invalidate.ts: tagsForEvent` и подписку моста в `store/topics.ts` (и тип события в `server/src/realtime.ts` и `realtime/src/contract.ts`); пропуск любого звена молча оставляет экран без обновления (так `goals`, `events` и `games` не доходили до экранов, пока не появились тесты `realtime-utils.test.ts`, проверяющие разбор и подписку на каждый вид).

## Живые обновления (`realtime/`)

Отдельный пакет и контейнер, который держит сокеты и больше ничего: `server` и `realtime` общаются только через БД (канал `realtime` и две таблицы), код друг друга не импортируют. Благодаря этому деплой `server` не рвёт соединения, а `server` можно запускать в нескольких экземплярах.

- **Рассылка** (`src/app.ts`, `src/hub.ts`): `LISTEN realtime` на отдельном постоянном соединении (`src/listener.ts`), сообщение разбирает `parseMessage` (непонятное и версию новее пропускает), `Hub` ищет адресатов по индексам (семья, участник, сессия), а не перебором. Клиент, у которого накопилось больше 1 МБ неотправленного, отключается (переподключится сам). Не больше 30 подключений на участника (лишние вытесняют старые, код 1012), 600 попыток подключения в минуту с адреса (`X-Forwarded-For` от nginx), сообщение клиента до 2 КБ.
- **Вход:** токен проверяется по `sessions` (`src/auth.ts`, срок 90 дней как у `server`, продление `last_used_at` раз в сутки). Раз в минуту проверяются все открытые сессии: отозванные без сигнала (участник или семья удалены, срок истёк) закрываются кодом 4401. Выход с устройства закрывает его сокет через сообщение `to: 'session'`.
- **Какой чат открыт** (`viewing`, таблица `realtime_viewing`): клиент по сокету сообщает чат на экране, `realtime` пишет строку (ключ `connection_id`), каждый ping (30 с) освежает `updated_at`, закрытие соединения удаляет строку, упавший экземпляр не оставит вечных отметок (`housekeeping` чистит строки старше 5 минут). `isViewingChat` в `server` теперь **асинхронный запрос** к таблице: чат считается открытым, если отметка не старше 90 секунд. Визиты в личные чаты (`chat_visits`, «был в чате») пишет тоже `realtime`, собеседнику уходит сигнал через тот же канал.
- **Обрыв слушателя.** NOTIFY не хранится: пока соединение с БД потеряно, сигналы теряются. После каждого восстановления (кроме первого подключения) сервис закрывает все сокеты кодом 1012, клиенты переподключаются и заново запрашивают данные (`resync`).
- **Состояние:** `realtime_state (instance, beat_at, connections)`, метка раз в 15 секунд и **только пока слушается канал**, поэтому проверка контейнера (`node dist/healthcheck.js`, свежесть метки до минуты; порта для неё не нужно, у сервиса есть ещё `GET /health`) замечает потерянный канал. `GET /api/admin/queue` отдаёт `realtime: {alive, instances, connections, lastBeatSeconds}` (необязательное поле на клиентах), блок «Живые обновления» на `/profile/service` и ошибка в `queueAlerts`, если сервис не отвечает. `update.sh` после запуска ждёт его метку (как у `notifier` и `scheduler`).
- **Маршрут:** в `web/nginx.conf` `location = /api/ws` идёт на `$realtime_upstream` (`http://realtime:3000`, адрес через DNS Docker при каждом запросе, как у остальных). В разработке Vite проксирует `/api/ws` на `localhost:3002` (раньше общего `/api`), порт задаёт `REALTIME_PORT`, запуск `npm run dev:realtime` (входит в `npm run dev`). Мобильное приложение против локального `server:3000` напрямую сокет не получит: ходите через nginx (`:8080`) или поднимайте `realtime`.
- **Выкладка.** Выкладывайте `server`, `web` (nginx) и `realtime` вместе (`update.sh` так и делает): новый `server` больше не отвечает на `/api/ws`, а старый nginx шёл бы на него. Откат кода схему не откатывает, таблицы `realtime_*` старому коду просто не нужны.
- **Тесты** (`realtime/tests/`, Vitest, нужна БД `npm run dev:infra`): своя база `family_tasks_realtime_test` с миграциями из `../server/migrations`; настоящие сокеты клиента `ws` к сервису на свободном порту (`startRealtime` с быстрыми таймерами): вход и отказы, доставка семье и участнику, закрытие сессии, отозванная сессия, вытеснение, `viewing` (запись, освежение, удаление, визиты), метка живости, обрыв слушателя. `npm run test:realtime` из корня или `npm test` в `realtime/`; типы `npm run typecheck`. Тесты `server` слушают канал сами (`tests/api/realtime.test.ts`: «клиент» принимает то, что получил бы участник; **ждите «барьер» (`settle`) перед подключением и проверкой тишины**, сигнал приходит уже после ответа API). CI: задание `realtime`.
- **Авторизация по умолчанию** (`server/src/app.ts`). Хук `onRequest` отвечает 401 на любой запрос под `/api/` без действующего токена раньше проверки схемы и маршрутов (неизвестный адрес тоже 401, список маршрутов не прощупать). Открытый маршрут надо пометить `config: { public: true }`; сейчас открыты ровно: `GET /api/health`, `GET /api/push/config`, `POST /api/email-codes`, `POST /api/families`, `GET /api/invites/:code`, `POST /api/invites/:code/join`, `POST /api/auth/login`, `DELETE /api/session` (выход проходит и с просроченным токеном, без токена 401 даёт обработчик), `GET /api/ws` (токен первым сообщением). Список закреплён тестом `tests/api/security.test.ts`: новый открытый маршрут надо добавить туда осознанно. `authenticate(req)` вычисляется один раз на запрос (результат хука переиспользуют обработчики).
- **Администратор сервиса** (`server/src/admin.ts`). Адреса администраторов в переменной `ADMIN_EMAILS` (через запятую, регистр и пробелы не важны; на сервере в `.env`, в `docker-compose.yml` пробрасывается в `server`; пусто: администраторов нет). `isAdminEmail(email)` читает переменную при каждой проверке. `GET /api/admin/stats?since=<ISO начала дня клиента>` (часовой пояс знает только клиент) отдаёт `{accounts, families, messages}`, у каждого `total` и `today` (создано с `since`); не администратору 404 `not_found` (раздела для него нет), без токена 401. В `/api/me` у самого участника есть `isAdmin`. Клиент: в профиле пункт «Сервис» только при `me.isAdmin`, страница `/profile/service` (`pages/Service`, `store/admin.ts`: карточки «Всего», «Новых сегодня», семьи, сообщения; обновляется раз в 30 секунд, не администратора возвращает в профиль). Проверка прав всегда на сервере, флаг на клиенте только прячет пункт. **Очередь отправки** (фаза 6): `GET /api/admin/queue` (те же права: не администратору 404, без токена 401) отдаёт `QueueStats` (`admin.ts`): `notifier` (`alive` если метка свежее минуты, `instances`, `lastBeatSeconds`), `waiting` по каналам (`attempts = 0`, в том числе отложенные из-за лимита), `retrying` (`attempts > 0`), `oldestSeconds` (возраст старейшей строки, `null` при пустой очереди), `mail` (`usedToday` из `provider_usage` и `limit` из `MAIL_DAILY_LIMIT`), `today` (итоги отправки и окончательных неудач из `delivery_stats` за сутки по UTC). Клиент: секция «Очередь отправки» на `/profile/service` (`store/admin.ts: useGetQueueStatsQuery`, опрос раз в 30 секунд) с карточками и предупреждениями `queueAlerts` (`pages/Service/utils.ts`: notifier не отвечает → ошибка; старейшее сообщение ждёт дольше 5 минут → предупреждение; расход бюджета писем от 80% → предупреждение, 100% → ошибка со временем обновления в часовом поясе устройства; неудачи за сегодня → предупреждение). Строки очереди и метки пишет только `notifier` и тесты, в тестах `server` их общая таблица делится с параллельными файлами: проверяйте нижние границы, а точные числа только для таблиц, которые пишет один файл (`notifier_heartbeat`, `provider_usage`, `delivery_stats`: их пишет `admin.test.ts`, поэтому другие тесты в них не пишут).
- **Сессии с сроком.** Токен устройства действует, пока им пользуются: `sessions.last_used_at` обновляется не чаще раза в сутки, без использования 90 дней (`SESSION_TTL_DAYS` в `auth.ts`) сессия считается истёкшей (401, клиент выходит), истёкшие удаляются при старте сервера и раз в сутки. «Выйти на всех устройствах» пока нет.
- **Ошибки сервера.** Единый обработчик (`setErrorHandler` в `app.ts`): ответы 5xx содержат только `{error: 'internal_error'}`, подробности только в журнале; ошибки клиента (4xx, проверка схемы) отдаются как раньше.
- **Заголовки безопасности.** `web/security-headers.conf` (X-Content-Type-Options, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy, CSP со своими источниками и `'unsafe-inline'` для двух inline-скриптов в `index.html` и styled-components) подключается в `nginx.conf` в `server` и в каждый `location` со своим `add_header` (nginx не наследует заголовки родителя, если в `location` есть свой). Новый `location` с `add_header` тоже должен подключать этот файл. Ловушка CSP: `fetch` по адресам `data:` и `blob:` запрещён правилом `connect-src` (картинки в `<img>` и `createImageBitmap` разрешены): data URL превращайте в файл разбором base64 (`dataUrlToFile` в `lib/image.ts`), а не через `fetch`; так сломался «Аватар из Roblox» после включения CSP (запрос к серверу проходил, а сохранения не было). Внешний ресурс один, Яндекс SmartCaptcha (см. «Капча»): если появятся другие (шрифты, аналитика), их надо добавить в CSP. HSTS (год) ставит Caddy, `server_tokens off` прячет версию nginx.
- **Прокси и лимиты.** Сервер за nginx (и Caddy в проде): `trustProxy: true` для `X-Forwarded-For`. Rate limit — общий 600/мин на IP (`GENERAL_LIMIT_PER_MINUTE` в `app.ts`: семья сидит за одним адресом, а один переход между экранами даёт до десятка запросов; при 120 лимит упирался уже на быстром переключении табов и ответы 429 ломали загрузку чатов и подключение сокета) и строгий 10/мин (`strictLimit` в `server/src/routes.ts`) на эндпоинты, где можно подбирать коды; строгий счётчик общий для этих маршрутов по IP. Сервер не должен торчать наружу в обход nginx.

**Расписания.**
- Ребёнок правит своё из профиля (`/profile/schedule`, `/profile/trainings`), родитель — с превью ребёнка (`/family/:memberId/...`). Страницы `pages/Schedule` и `pages/Trainings` — зеркальные редакторы: по умолчанию просмотр (`LessonViewList`, `TrainingViewList`), «Изменить» открывает редактор с черновиком (`saved` — серверное состояние, `draft` — правки), «Отмена» с несохранёнными правками просит подтверждение, пустые строки при сохранении отбрасываются.
- Общие `components/DayTabs` (дни передаются пропом) и `components/SortableList` (перетаскивание `@dnd-kit`, ручка слева, есть клавиатура; строки сами вызывают `useSortable`).

**Проверка родителем в интерфейсе:** `components/PendingReview` («Ждут подтверждения» со счётчиком: карточки заданий детей с кнопками «Подтвердить: +N» и «Вернуть»; только родителям и только когда есть что проверять) стоит наверху «Моего дня» и на странице «Задания» (учитывает фильтр по человеку; у родителей ожидающие в списках по дням скрыты, чтобы не дублировать). Карточка `TaskItem` в состоянии «на проверке» (песочные часы, янтарный цвет; кнопки лежат под ссылкой, а не внутри неё). Страница задания: ребёнок видит «Отправить на проверку» вместо «Отметить выполненным», затем «Отменить отправку», без праздника; праздник с «+N монет» приходит сам, когда родитель подтвердил, пока ребёнок на странице; родитель видит «Подтвердить: +N» и «Вернуть на доработку»; подтверждённое задание с наградой ребёнок снять не может. Действия родителя: хук `lib/useReview`.

**Награда в форме задания:** если исполнитель ребёнок и форму заполняет родитель (ребёнку награду назначать нельзя, плашек у него нет), в `TaskEditor` появляется `RewardPicker`: плашки «Без награды», 5, 10, 20, 50, 100 (`REWARD_CHOICES` в `lib/coins.ts`) и «Другая» с полем для своего целого числа от 1 до 1000 (`MAX_REWARD`; значение в форме строка `reward` и признак `rewardCustom`, награда вне готовых плашек у существующего задания открывается как «Другая»; проверка в `validate`, у формы `noValidate`, чтобы показывалось наше сообщение). При смене исполнителя на взрослого плашки скрываются и награда сбрасывается.

**«Указать время»:** дата, время и повтор спрятаны за чекбоксом `components/Checkbox` (`FormState.scheduled`; без галочки задание «без срока»). Включение ставит сегодняшнюю дату, выключение убирает дату, время и повтор; `toInput` без галочки отправляет `date/time` null и повтор `none`. Галочка без даты не проходит проверку. Награда видна в подписи карточки («+20 монет»), в деталях задания, а в экране поздравления исполнителю показано «+N монет».

**Монеты.** Правый верхний угол оболочки (`TopRight` в `AppShell`): у ребёнка слева от значка профиля баланс (`components/CoinBalance`: золотая монета и число, из `profile.me.coins`; это ссылка на `/coins`), у родителей только значок. На странице `/profile` значка профиля нет, баланс остаётся; в переписке (`/chat/:chat`) баланс скрыт, в списке чатов `/chat` виден. Страница `/coins` (`pages/Coins`) у ребёнка показывает его монеты, у родителя `/coins/:memberId` монеты выбранного ребёнка (заголовок «Монеты: Имя», назад на `/family/:memberId`; родителя без `memberId` перекидывает на стартовую). Баланс-карточка `CoinBalanceCard` со ссылкой на историю стоит на `/profile` ребёнка и на странице ребёнка для родителя (`MemberPreview/components/ChildCoins`, `getCoinBalance`, обновляется по `members`). баланс крупно и история (`HistoryRow`: за что, «когда · кто» (родители для ребёнка «Мама» и «Папа», запись без автора «Система»), справа сумма со знаком, зелёная или красная; пустая причина «Без описания»). Старые записи подгружаются при прокрутке (`IntersectionObserver` на сторожа в конце списка с запасом 300px, плюс кнопка «Показать ещё» и «Повторить» при ошибке; повторные срабатывания во время запроса гасит `busy`), новые встают сверху по сигналу сокета `members` (`mergeNewest`). Автоподгрузку по прокрутке во встроенной панели Browser проверить нельзя (она скрыта и наблюдатель не срабатывает), только кнопкой и тестом. `AppShell` выставляет `--topbar-reserve` (место справа, которое занято углом); шапки страниц берут его в `padding-right`, а шапка заданий переносит выпадающий список на строку ниже, если он не помещается.

**Реакции и монеты в чате:** у всех любое сообщение открывает компактное окно `FeedbackDialog` долгим нажатием (`pages/ChatRoom/useLongPress`: удержание 450 мс, сдвиг пальца больше 10 px и отпускание раньше отменяют; правая кнопка мыши и системное меню Android через `contextmenu`; с клавиатуры Enter и пробел при `role=button`; обычный клик ничего не делает, а у пузыря отключены системное выделение и меню, поэтому текст из чата не скопировать) со строкой реакций из `lib/reactions.ts` и, только у родителя на сообщении ребёнка (`canAward`), строкой быстрых сумм монет 5/10/20/50/100; кнопок «Отправить» и «Отмена» нет: нажатие применяется сразу и окно закрывается, повторное нажатие на свою реакцию снимает её, закрыть без выбора можно Escape или нажатием на затемнение; своей суммы монет в чате больше нет; под сообщением у всех видны реакции (одинаковые склеиваются с числом) и сумма начисленных монет (`MessageBubble`, плашки заезжают на нижний край пузыря на 0.6rem и сдвинуты внутрь на 0.7rem, обводка цветом фона отделяет их от пузыря). Общий `components/CoinPicker` используется и для награды в задании.

**«Сегодня заработано» на «Моём дне»:** ребёнку сверху под приветствием плашка с суммой монет, заработанных сегодня (`pages/MyDay/components/EarnedToday`, ссылка на `/coins`; пока 0 и у родителей плашки нет). Сумма с сервера: `GET /api/coins/earned?since=<ISO начала местного дня>` (час. пояс знает только клиент, `startOfDayIso`); считаются начисления (`amount > 0`) и отмены наград за задания (запись со `task_id` и отрицательной суммой), траты (списания без задания) не уменьшают «заработано», результат не меньше 0. Обновляется по сигналу `members`.

**Фото в чатах** (фаза 2 плана `docs/chat-photos-plan.md`; серверная часть описана в разделе про сервер). В поле ввода (`Composer`) скрепка выбирает фото из галереи или снимает камерой (`<input type="file" accept="image/*" multiple>`, до 10 на сообщение, `MAX_PHOTOS`). Выбранные фото по очереди уменьшаются на устройстве (`lib/image.ts: resizeToPhoto`: длинная сторона до 1600 px, JPEG качество 0,82, при размере выше предела сервера качество снижается; метка геопозиции пропадает, поворот камеры применяется к пикселям) и сразу загружаются (`uploadChatPhoto`, `POST /api/chats/:chat/media`), над полем лента превью с «×»; ошибка показана на самом фото («Ещё раз» повторяет загрузку без повторного уменьшения, не удавшееся подготовить фото можно только убрать), пока фото грузятся или не загрузились, «Отправить» заблокирована (`canSendMessage`), у фото без текста отправка разрешена, поле тогда называется «Подпись». Отправка `{text, mediaIds}`; при ошибке фото и подпись остаются, загружать заново не нужно. Двойное нажатие «Отправить» отправляет один раз (`useInFlight`, проверка в `DoubleSubmit.test.tsx`). В пузыре (`MessageBubble`) сообщение с фото показывает `media` и подпись `caption` (текст из базы с заглушкой «📷 Фото» новый клиент не показывает: `bubbleText`); одно фото крупно по своим пропорциям (полный вариант), 2–4 плитками в два столбца, 5–10 в три (превью); ширина пузыря с фото задана (`min(82%, 17rem или 21rem)`), иначе плитки вылезали за пузырь. **Аватар автора слева от чужого сообщения** в групповых чатах (общий и событие), как в Телеграме: у последнего сообщения подряд от одного автора в этом дне его аватар (`senderAvatar` у `MessageBubble`, считает `senderAvatar()` в `ChatRoom`: фото профиля или цветной круг с инициалом), у предыдущих пустое место такой же ширины (`null`), у своих и в личных чатах колонки нет (`undefined`); колонка `Line > Side` в `MessageBubble`, `Wrap` с `data-message-id` остаётся прежним (поиск и подсветка работают). **Пузырь с фото или видео без отступов** (`Bubble $media`): медиа занимает всю ширину пузыря от верха и по бокам (пузырь обрезает по скруглению, `overflow: hidden`), боковые отступы остаются только у имени автора, цитаты, файлов, подписи и времени (`> :not([data-media])`; у медиа-блоков `data-media`), отступ снизу там, где время; у видео ширина как у одного фото (17rem). Нажатие на фото открывает `PhotoViewer` (на весь экран, `createPortal` в `body`: переписка лежит в слое с анимацией, и угол оболочки с монетами оказывался поверх просмотра). **Слайдер:** все фото сообщения лежат в одной горизонтальной ленте с привязкой к краям (`Track`: `overflow-x: auto`, `scroll-snap-type: x mandatory`, у слайда `scroll-snap-stop: always`), фото едет за пальцем нативной прокруткой, а не обработчиком жеста; кнопки «вперёд/назад» и стрелки клавиатуры прокручивают ленту плавно (`scrollTo({behavior: 'smooth'})`), с последнего на первое мгновенно. Номер берётся из положения ленты (`round(scrollLeft / clientWidth)`), а пока идёт наша плавная прокрутка (700 мс), события прокрутки не читаются: на полпути лента стоит над соседним фото, и без этого номер откатывался назад и кнопка «вперёд» спорила с лентой (тест «пока лента плавно едет…»). Открывается сразу на нужном фото без анимации. **«Сохранить» не уходит со страницы** (`savePhoto`): раньше это была ссылка с `download`, и в установленном приложении (PWA без кнопки «назад») она открывала саму картинку в том же окне, откуда выйти было нечем. Теперь кнопка запрашивает файл (он идёт через кэш фото) и отдаёт его меню «Поделиться» (`navigator.share({files})`, на iPhone там «Сохранить изображение»; закрытое меню не ошибка), а если меню нет, скачивает из памяти (`blob:` и `download`); при сбое под панелью сообщение «Не удалось сохранить фото», просмотр остаётся и закрывается крестиком, Escape или нажатием на пустое место рядом с фото; двойное нажатие запрашивает файл один раз (`useInFlight`). Прокрутка страницы за просмотром блокируется. Долгое нажатие по-прежнему открывает окно реакции, а «клик» после него просмотр не открывает (700 мс защиты в `MessageBubble`). В списке чатов превью «📷 Фото», «📷 3 фото» или «📷 подпись» (`chatPreviewParts`). Кэш прежней версии без полей `caption` и `media` считается текстовым (`CACHE_VERSION` поднят до 2). Тексты ошибок: `describePhotoError` (`lib/errors.ts`). Dev: `/media` проксируется Vite на `localhost:3001` (`npm run dev:media`, порт `MEDIA_PORT`), сервис ставится в `npm run dev` и `npm run setup`. Проверка в настоящем браузере делалась на связке server + media + S3 (Playwright, `chromium` из `/opt/pw-browsers`): так нашлись две ошибки, которых юнит-тесты не видят (плитки вылезали за пузырь, просмотр не помещал вертикальное фото и закрывался монетами), поэтому после правок вёрстки фото проверяйте так же.

**«Что ты хочешь сообщить!»** (`/lesson-report?subject=…`, `pages/LessonReport`, только дети): на «Моём дне» у ребёнка уроки нажимаются (`LessonViewList` с `getLink`). Выбор оценки 5, 4, 3 или 2 (повторное нажатие снимает) и/или текст собираются `buildLessonReport` в сообщение вида «Урок «Математика»: оценка 5» и строкой ниже комментарий; оно отправляется в общий чат, затем открывается общий чат.

**Чат.** `/chat` (`pages/Chat`): значок общего чата контурный в стиле иконок табов (`TabIcon family`, акцентный цвет на тонированном круге, `FamilyIcon`), без эмодзи; список в духе Telegram: строки во всю ширину без карточек, аватар 3,4rem, имя и время в первой строке, во второй превью с выделенной подписью («Вы:» серым, имя автора в общем чате акцентным, `chatPreviewParts`) и круглым счётчиком непрочитанного, тонкая линия между строками начинается от текста; пока список грузится, серые строки-заглушки (колонка списка `minmax(0, 1fr)`, превью в одну строку с многоточием: без этого длинное сообщение без пробелов раздувало строку за экран) из `ChatsProvider` (`web/src/chat/`, в `AppShell`: список с непрочитанным обновляется по сигналу `chat`; из него же число на значке «Чат» в `TabBar`). `/chat/:chat` (`pages/ChatRoom`): аватар и имя собеседника сверху в личной переписке ведут на его профиль `/family/:id` (`WhoLink`), в общем чате это просто подпись; под заголовком в общем чате число участников («4 участника», `participantsLabel`), в личном когда собеседник был в чате; шапка, лента и поле ввода стоят на своих местах с первого кадра (пока сообщения грузятся, в ленте серые пузыри `MessagesSkeleton`, при ошибке сообщение там же): сообщения по дням, пузыри (свои справа, имя автора над чужими только в общем чате; у своих рядом со временем галочки: одна «отправлено», двойная «прочитано», `messageStatus`), «Показать более ранние», поле ввода `Composer` (Enter отправляет, Shift+Enter перенос) прижато к панели табов. Переписка запрашивается заново по сигналу своего чата (`mergeLatest` сохраняет подгруженные старые сообщения), прокручивается вниз, только если читатель и так внизу; отметку «прочитано» ставит один раз на последнее чужое сообщение (`markedRef`, без этого сигнал о прочтении зациклил бы запросы). Неизвестный чат перекидывает на список. **Имена в чате:** ребёнок видит родителей как «Мама» и «Папа» вместо имён (`memberLabel` в `lib/roles.ts`: список чатов, аватар, превью и подписи авторов в общем чате, заголовок переписки); то же в push-уведомлениях для ребёнка (`senderLabel` в `server/src/chat.ts`). Родители и дети друг для друга по-прежнему видят имена. **Меню чата:** три точки справа в шапке переписки (`MenuButton`) и долгое нажатие (или правая кнопка мыши) на строке списка открывают `pages/Chat/components/ChatMenu` на общем `components/ActionSheet` (панель снизу: действие выполняется по нажатию, при успехе меню закрывается, при ошибке остаётся с сообщением, `useInFlight` против двойного нажатия; z-index 90, ниже окна подтверждения). Действия собирает `pages/Chat/useChatActions`: «Отключить/Включить уведомления» всем (`setChatMuted`, значок перечёркнутого колокольчика `MutedMark` у названия в списке и в шапке, счётчик непрочитанного у отключённого серый) и «Очистить чат» только родителям (подтверждение `useConfirm`, `clearChat`; переписка в кэше пустеет сразу). После долгого нажатия «клик» по строке переход не делает (700 мс, как у фото). **Прокрутка и клавиатура:** страница переписки не прокручивается, экран `Room` стоит `position: fixed` ровно на видимой области (`top: var(--vv-top)`, `height: var(--vvh)`), прокручивается только лента `Feed` между шапкой и полем ввода (`Composer` в обычном потоке внизу). `lib/useKeyboardViewport` пишет на корень `--vvh` (высота `visualViewport`), `--vv-top` (его сдвиг: iOS при фокусе сдвигает видимую область) и `data-keyboard`, пока клавиатура открыта (определяется по наибольшей высоте видимой области при той же ширине, а не по `innerHeight`: на части Android он уменьшается вместе с ней). **Панель ввода парит над лентой, как в Telegram** (`Composer`: `Dock` внизу экрана, `position: absolute` в `Room`; кнопки и поле это «стекло»: полупрозрачная заливка, `backdrop-filter: blur`, светлая кромка): круглая скрепка слева, стеклянная таблетка с полем и значком эмодзи внутри справа, круглая кнопка отправки (приглушена, пока отправлять нечего); сама панель без фона, а под ней лента затемняется градиентом (`Dock::before`). Лента идёт до самого низа и прокручивается под панелью: `Composer` измеряет свою высоту (`ResizeObserver`) и пишет её в `--composer-h` на `Room`, `Feed` берёт её в `padding-bottom` (и компенсирует `--tabbar-height` отрицательным `margin-bottom`), поэтому рост поля, открытая панель эмодзи, ответ и вложения сдвигают ленту сами. Предупреждения «не удалось отправить» лежат внутри `Dock` над полем. **Шапка парит так же** (`Top` вверху `Room`: шапка и в чате события вкладки «Событие | Чат», без фона и рамки, градиент от верха `Top::before`; высота измеряется в `--top-h`, `Feed` берёт её в `padding-top`; измерение стоит выше раннего `return null` экрана и следит за готовностью данных, иначе шапка не измерялась бы). Сообщения прижаты к низу внутренним `FeedContent` (`min-height: 100%` и `justify-content: flex-end`; на самой прокручиваемой ленте `flex-end` отрезал бы верх). Прижатость к низу (`stick`) помнит прокрутка ленты, а `ResizeObserver` на ленте и содержимом возвращает прижатую ленту к низу при любом изменении размеров: клавиатура на Android выезжает за несколько кадров, и одна прокрутка в момент открытия оставляла конец переписки (особенно высокое фото) под клавиатурой. «Показать более ранние» сохраняет место (`keepFromBottom`). Ловушка: `Content` в `AppShell` задаёт странице (`> main`) `min-height` во весь экран, и он сильнее `height` экрана переписки; клавиатура не меняет `dvh`, поэтому без `min-height: 0` (в `Room` через `&&`) поле ввода уходило под клавиатуру. Эмуляция уменьшением окна этого не ловит (там меняется и `dvh`): проверяйте, меняя только `--vvh`. Проверено в Chrome с мобильной эмуляцией (поэтапное уменьшение экрана, тест «прокрутка переписки» в `Chat.test.tsx`); на реальных iPhone и Android не проверялось.

**Данные интерфейса: Redux Toolkit и RTK Query** (миграция закончена, план и история в `docs/redux-migration.md`). `web/src/store/`: `api.ts` (`createApi`, теги `TAGS`, `fromApi` оборачивает функции клиента `@/api` для запросов, `toApiError` возвращает ошибку мутации как `ApiError`, `refetchOnMountOrArgChange: 30` и `keepUnusedDataFor` неделя), по доменам `profile.ts`, `tasks.ts`, `schedules.ts`, `coins.ts`, `goals.ts`, `chat.ts` (чтения с `providesTags`, мутации с `invalidatesTags` и, где нужен мгновенный отклик, с `updateQueryData` в `onQueryStarted` и откатом при ошибке). Кэш сохраняется в `localStorage` (`persist.ts`: ключ по пользователю, срок 7 дней, версия схемы `CACHE_VERSION`, бюджет `MAX_BYTES`, при ошибке квоты работаем без кэша; на устройстве лежит кэш только текущего пользователя) и читается синхронно при старте (`makeStore`), поэтому первый кадр уже с данными, а свежие приходят следом. `SessionSync` выставляет токен (`session.ts`; токен остаётся в IndexedDB и не попадает в Redux) и стирает кэш при выходе, 401 и смене пользователя. События сокета только сбрасывают кэш: `RealtimeBridge` (в `AppShell`, единственное место с `useLive`) превращает событие в `invalidateTags` (`invalidate.ts`: теги с адресом для расписаний, тренировок и чатов, склейка за 200 мс, `resync` сбрасывает всё), активные экраны запрашивают данные заново сами. Экраны на сигналы не подписываются и счётчиков `version` не ведут. Не в кэше (разово или после действия): старые страницы истории монет и переписки (подгружает сам экран, первая страница в кэше), приглашения, вход и регистрация, Roblox-аватар. Новое чтение данных пишите как endpoint в нужном `store/*.ts` с `providesTags`, запись как мутацию с `invalidatesTags`. Тесты экранов оборачивайте в `Provider` со свежим `makeStore({ hydrate: false })` и выставляйте `setSession({ token: 'tok', memberId })`; чтобы проверять реакцию на сигналы сокета, рядом нужен `RealtimeBridge`; для данных из `@/api` подмена функций работает как раньше.

**Нет связи.** Любой запрос через `api/client.ts: request` сообщает о результате в `lib/connection.ts` (сетевая ошибка или событие `offline` браузера: связи нет; любой ответ сервера, даже с ошибкой: есть). `components/ConnectionBanner` (в `App`) показывает сверху полосу «Соединение…», пока связи нет, сам проверяет её `GET /api/health` каждые 2–3 секунды (`RETRY_DELAY_MS`) и при возвращении связи сбрасывает все теги кэша. **Чтение не заканчивается ошибкой без связи:** `fromApi` для query повторяет запрос каждые 2–3 секунды (`lib/retry.ts: retryRead`; повторяются сетевая ошибка и 502/503/504, остальные ответы сервера нет; отмена по `signal`, когда экран ушёл), поэтому экраны показывают «Загрузка…» или прежние данные вместо «Не удалось загрузить»; изменяющие запросы (mutation) не повторяются, там ошибку видит человек. Загрузки вне RTK Query (старые страницы переписки и истории монет, «Медиа файлы», приглашения) оборачивайте в `retryRead` с `useAbortOnUnmount`. Сообщение «Не удалось загрузить» теперь появляется только при настоящей ошибке сервера.

**Живые обновления.** `web/src/realtime/`: `RealtimeProvider` (в `AppShell`, одно соединение на вход: подключение, auth первым сообщением, переподключение с нарастающей паузой 1–30 с, при потере и возврате связи, при возврате вкладки после 5+ с и при появлении сети рассылает `resync`) и хук `useLive(темы, обработчик)` (`realtime/context.ts`), на который опирается только `store/RealtimeBridge`: сигнал сбрасывает теги кэша, а экраны, которым нужны эти данные, обновляются сами (см. «Данные интерфейса»). Форма изменения задания и цели кэш не перезаписывает (поля заполняются данными один раз), чтобы чужие правки не затирали ввод. ## PWA, кэширование, тема

- **Выезд страниц справа** (`SlideInPage` в `components/Page`, экран переписки `Room`) играет только при переходе вперёд: `lib/useSlideIn` не анимирует переход типа `POP` (кнопка «назад» браузера, жест, открытие по адресу) и переход со `state.back` (его ставят `BackLink` и кнопка назад в переписке через `BACK_STATE`). Новую ссылку «←» делайте через `BackLink`: она возвращает на страницу, с которой пришли (по истории, вместе с адресом, видом и днём календаря: задание, тренировки, профиль участника и расписание из календаря вернут в календарь), а адрес `to` нужен как запасной, когда пришли не из приложения (открыли ссылку или уведомление; без записи истории внутри приложения, `canGoBack`) и для открытия в новой вкладке.

- Service worker свой, `web/src/sw.ts` (стратегия `injectManifest`): кэш приложения (`/api/` в кэш не попадает) и обработчики `push` и `notificationclick`. Фото из чатов (`/media/…/full|thumb`) он отдаёт «сначала из кэша» (`CacheFirst`, кэш `chat-photos`, `lib/photoCache.ts`): ключ это путь без подписи, потому что подпись меняется раз в сутки, а файл неизменяем; до 400 записей и 60 дней. Кэш стирается при выходе и смене пользователя (`SessionSync`). Одного HTTP-кэша мало: при смене подписи фото качались заново, а на iPhone HTTP-кэш маленький и быстро вытесняется. Он собирается отдельным tsconfig (`tsconfig.sw.json`, lib `WebWorker`) и исключён из `tsconfig.app.json`. Значок: золотой контур дома с тёплым светом в двери на тёмном фоне (`web/public/icon.svg`, квадрат без скругления: скругляет система; цвет `#4f46e5` задан фоном для iOS и maskable в `pwa-assets.config.ts`; при смене рисунка меняйте SVG, `mobile/scripts/generate-icons.cjs`, `mobile/src/components/AppLogo`; приложение пересобирает значки командой `node scripts/generate-icons.cjs`). Старый значок был золотой монетой на тёмном индиго. В манифесте постоянный `id: '/'`: смена названия и значка воспринимается как обновление того же приложения. Иконки генерируются из `web/public/icon.svg` командой `npm run generate-pwa-assets` (в `web/`) (настройки в `web/pwa-assets.config.ts`: значок для iOS `apple-touch-icon` без полей и прозрачности, на всю плашку, потому что скругление iOS делает сам; maskable для Android с полями 15% на сплошном фоне). Название приложения «Моя Семья» (с заглавной С; раздел «Моя семья» в табах называется как раньше) задано в манифесте (`vite.config.ts`), `<title>`, `apple-mobile-web-app-title` в `index.html`, по умолчанию в заголовке push (`sw.ts`) и в письмах (`notifier/src/providers/mail.ts`).
- Обновление у пользователей: service worker с `skipWaiting` и `clientsClaim` ставится и активируется сам, но открытая страница работает на старой версии до перезагрузки. Хук `lib/useAppUpdate` слушает `controllerchange` (только если worker уже управлял страницей, первая установка не в счёт), раз в 30 минут и при возврате на вкладку вызывает `registration.update()`; `components/UpdateBanner` (в `App`) показывает вверху плашку «Доступна новая версия» с кнопками «Обновить» (перезагрузка) и «Позже». Плашка яркая (акцентный фон, отступ сверху 1rem), пока видна, кладёт свой нижний край в `--update-banner-bottom`, и плашка уведомлений встаёт под ней. Принудительной перезагрузки нет, чтобы не потерять набранное. Старая и новая версии какое-то время живут вместе, поэтому API меняйте обратно совместимо. Кэширование (`web/nginx.conf`): `index.html` (включая `/` и все маршруты SPA, их отдаёт SPA fallback), `sw.js`, `registerSW.js` и `manifest.webmanifest` отдаются с `Cache-Control: no-cache` (браузер каждый раз сверяется по ETag, 304 если не менялись), файлы с хэшем в `/assets/` с `public, max-age=31536000, immutable`; манифест отдаётся с типом `application/manifest+json`. Если добавите файл, который меняется между сборками без хэша в имени, добавьте его в `no-cache`-правило, иначе пользователи будут видеть старую версию.
- **Безопасные зоны iPhone.** В `index.html` у viewport стоит `viewport-fit=cover`: без него iOS не сообщает `env(safe-area-inset-*)`, и нижняя панель табов оказывается под индикатором «Домой» и скруглёнными углами (крайние табы обрезаны). Все закреплённые к краям элементы учитывают отступы: `TabBar` (низ, лево, право; высота панели `--tabbar-height` в `AppShell` уже включает нижний отступ), кнопка «Новая задача», поле ввода чата и плашка обновления считают от него, а верхний отступ добавлен в `Page`, значок профиля, `ChatRoom` и плашку. Новые элементы у краёв экрана делайте так же. На симуляторе iOS это не проверялось (нужен полный Xcode), только расчётом.
- **Дизайн «Квест»** (макет в артефакте Design: «День как уровень в игре»). Шрифт Nunito лежит у нас (`@fontsource-variable/nunito`, подключён в `main.tsx`; CSP не пускает внешние шрифты), кириллица и латиница в precache service worker (`injectManifest.globPatterns` в `vite.config.ts`); 900 для заголовков и чисел, 700–800 для подписей. Токены в `GlobalStyle` (обе палитры; значения общие с приложением, `mobile/src/theme/palettes.ts`, при смене правьте оба места): фон `#f5f6fb` / `#0b0e1f`, акцент `#4b3bff` / `#7b6cff`, лайм `--lime`/`--on-lime` для действий и выполненного (кнопка `$variant="lime"`, «Класс!», «Подтвердить»), монеты `--coin`, `--coin-bg`/`--coin-text`, плашки `--done-*`, `--review-*`, `--track`, `--check-border`, яркий блок `--hero-*`. Карточки: `--card-border` (в светлой прозрачная, в тёмной тонкая рамка), `--card-shadow` (в тёмной нет), `--radius-card`; новую карточку делайте на них, а `--border` оставьте полям ввода и разделителям. Кнопки и чипы — «таблетки» (radius 999px), основная с цветной тенью `--accent-shadow`. Значок календаря на «Моём дне» (`components/CalendarIcon`, проп `date`) — карточка с днём недели и числом.
- Тема: по умолчанию следует `prefers-color-scheme`, явный выбор (`pages/Settings/components/ThemeSetting`: как в системе / светлая / тёмная) хранится в `localStorage['theme']` и применяется атрибутом `data-theme` на `<html>`. Скрипт в `web/index.html` ставит его до первого рендера (без вспышки) и синхронизирует `<meta name="theme-color">`; логика дублирует `lib/theme.ts`, при изменении правьте оба места. Слушатель смены системной темы (`lib/useThemeSync`) подключён один раз в `App`.

## Структура `web/src`

Каждый компонент — папка с `index.tsx`. Рядом по необходимости: `styles.ts` (styled-components), `types.ts` (пропсы и типы), `utils.ts` (чистые функции). Вложенные компоненты, которые нужны только этому компоненту, лежат в его `components/` и устроены так же, на любую глубину.

- `App/`, `main.tsx` — корень, роуты.
- `pages/<Page>/` — страницы (default export), у них свои `components/`.
- `components/` — общие компоненты. Базовые примитивы (`Button`, `Chip`, `IconButton`, `Input`, `Notice`, `Page`, `Select`, `Stack`, `BackLink`) объявлены как styled-компоненты прямо в `index.tsx`; варианты задаются transient-пропсами (`$variant`, `$tone`, `$inline`, `$active`), ссылки получаются через `as={Link}`. Остальное: `AppShell`, `Avatar`, `CodeStep`, `ConfirmDialog`, `DayTabs`, `Field`, `LessonViewList`, `LinkBox`, `MenuLink`, `Placeholder`, `ReplaceGuard`, `RoleForm`, `SortableList`, `TabBar`, `TaskItem`, `TrainingViewList`.
- `GlobalStyle/` (в `components/`) — глобальные стили. Цвета заданы CSS-переменными, в styled-компонентах используйте `var(--...)`, а не жёсткие цвета. Новый цвет добавляйте в обе палитры (`lightColors`/`darkColors`).
- `api/` — клиент API по доменам: `client.ts` (`request`, `ApiError`), `auth/`, `families/`, `invites/`, `profile/`, `push/`, `schedule/`, `tasks/`, `trainings/` (в каждом `index.ts` с функциями и `types.ts`), наружу всё реэкспортирует `api/index.ts`, поэтому импортируем из `@/api`. Новый эндпоинт кладём в свой домен.
- `identity/`, `profile/` — провайдеры состояния (не UI): `context.ts` с хуком вынесен из `index.tsx` ради fast refresh.
- `lib/` — общие модули без UI: `date`, `errors`, `image`, `links`, `occurrences`, `roles`, `taskText`, `theme`, `validation`, `weekdays` и хуки `useNow`, `usePushSubscription`, `useThemeSync`.

## Соглашения

- Подтверждения только через `useConfirm()` (`components/ConfirmDialog`, провайдер в `App`): окно на всю страницу, `await confirm({ title, message, confirmLabel, danger })` → `true/false`. Системные `window.confirm/alert/prompt` не используем. В тестах компонентов с подтверждением оборачивайте их в `ConfirmProvider`.
- Действия, меняющие данные (сохранить, создать, удалить, отметить, отправить, оплатить), защищены от повторного нажатия двумя слоями: `disabled` от `busy` (для вида) и `useInFlight()` из `lib/useInFlight` (`const save = guard(async () => { … })`: пока действие не закончилось, второй вызов любого обёрнутого действия компонента игнорируется, даже если два нажатия пришли до перерисовки; у `useReview` и `usePushSubscription` то же через `useRef`). Новое такое действие оборачивайте так же и добавляйте проверку в `web/tests/components/DoubleSubmit.test.tsx` (два нажатия подряд внутри одного `act`).
- В `web/` включён `erasableSyntaxOnly`: никаких `enum` и parameter properties в конструкторах.
- API-запросы фронтенда только через `web/src/api` (общий `request`, ошибки как `ApiError` с `status` и `code`). Коды ошибок сервера — snake_case (`invite_expired`, `name_taken`), UI мапит их на тексты.
- Валидация входных данных на сервере через JSON-схемы Fastify; запросы к БД — параметризованный SQL через `pg`, без ORM. Даты и время отдаём строками через `to_char`.
- Секреты и `.env` не коммитим (`.env` и `backups/` в `.gitignore`, шаблон — `.env.example`).
- Коммиты на русском или английском без требований к формату; в `main` пушим только по просьбе пользователя.

## Деплой и эксплуатация

- **Прод:** на сервере в `.env` задано `COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml` и `DOMAIN`, тогда обычный `docker compose up -d --build` поднимает ещё и Caddy (`Caddyfile`, сертификат Let's Encrypt для `DOMAIN`, том `caddy_data` не удалять); веб-контейнер снаружи не публикуется (`ports: !reset []`). Первый запуск по шагам и повседневные команды описаны в README, раздел «Деплой на сервер».
- **Обновление:** `./update.sh` на сервере: `git pull --ff-only`, копия БД в `backups/` (последние 14, `--no-backup` пропускает), `docker compose up -d --build`, проверка здоровья сервера изнутри (до минуты) и, если задан `DOMAIN`, снаружи по HTTPS, `docker image prune`. При неудаче показывает лог сервера и команду отката (`git checkout <прежний коммит>`); миграции при откате кода не откатываются. Скрипт предупреждает, если изменился `.env.example` или появились миграции.
- **Адрес API в nginx.** `web/nginx.conf` берёт адрес контейнера `server` через DNS Docker при каждом запросе (`resolver 127.0.0.11` и `proxy_pass $api_upstream` через переменную), а не один раз при старте: после падения `server` с новым внутренним адресом `web` не отдаёт 502 до своего перезапуска. Проверено на двух контейнерах со сменой адреса (со старой конфигурацией 502, с новой 200). Новые `proxy_pass` на `server` пишите тоже через `$api_upstream`.
- **IP клиента.** Цепочка Caddy → nginx (`web`) → Fastify. Caddy ставит `X-Forwarded-For`, nginx принимает его через `real_ip` только от внутренних сетей Docker и передаёт серверу `X-Forwarded-For $remote_addr`, поэтому rate limit работает на каждого посетителя и заголовок подделать нельзя. Если поменять эту цепочку (например, добавить ещё прокси), проверьте, что IP клиента по-прежнему доходит до API (в логах сервера `remoteAddress`), иначе лимиты станут общими на всех.
- **Почта обязательна.** Без настоящего SMTP войти нельзя (только код из письма). DigitalOcean блокирует исходящие порты 25, 465 и 587, поэтому нужен сервис с портом 2525. Сервисы рассылок не разрешают отправлять «от имени» `@gmail.com` и подобных (DMARC), нужен адрес на **своём домене**, подтверждённом через DKIM и SPF; на бесплатных поддоменах (DuckDNS) этих DNS-записей не добавить. Mailpit (`COMPOSE_PROFILES=dev-mail`) в проде не включать.
- **Ключи VAPID** создаются один раз (`npx web-push generate-vapid-keys`) и больше не меняются: после смены все push-подписки перестают работать. `VAPID_SUBJECT` — настоящий контакт (для iPhone важно). Пароль БД в `.env` без символов `/ + = @ :` (ломают строку подключения), лучше hex.
- **Зависание на части устройств.** Если клиенты получают главную страницу, но не большой JS (стоп на 10–16 КБ; `curl` с такой же картиной: `-r 0-15000` проходит, `-r 0-16000` зависает), при этом на самом сервере файл отдаётся целиком, виновата сеть по дороге. На этом проекте причиной оказалось ограничение трафика к зарубежному хостингу (DigitalOcean) для пользователей в России: ни ICMP в Cloud Firewall, ни TCPMSS не помогли, помог перенос на российский хостинг. Запасной экран в `index.html` печатает диагностику, включая пробное скачивание главного скрипта (сколько байт из скольких).
- **Адрес и данные браузера.** Вход, подписки и приглашения привязаны к адресу сайта: при смене домена всё придётся делать заново.
- **Тома.** `pgdata` (БД) и `caddy_data` (сертификаты) не удалять: `docker compose down -v` стирает их.
- **Журналы контейнеров** ротируются (`x-logging` в `docker-compose.yml` и `docker-compose.prod.yml`: `json-file`, не больше 3 файлов по 10 МБ на сервис), новому сервису в compose добавляйте `logging: *logging`. Посмотреть: `docker compose logs --tail 200 <сервис>`. Уведомления ставятся в очередь до ответа API (сервер ждёт постановки), поэтому тестам сервера ждать их таймерами не нужно.

- Название таба «Задачи» и страницы «Задания» разное, при желании унифицировать в `TABS`.
