# Family Tasks

PWA для семьи: задания, расписание уроков и тренировок детей, дни рождения, уведомления. Монорепозиторий без workspaces: у `web/` и `server/` свои `package.json` и `node_modules`. Язык интерфейса и сообщений об ошибках для пользователя — русский, комментарии в коде тоже на русском.

- `web/` — React 19 + Vite 8 + TypeScript, стили на `styled-components`, PWA через `vite-plugin-pwa`, роутинг `react-router-dom`, данные на устройстве в IndexedDB (`idb-keyval`). Алиас `@/` → `web/src` (vite + `paths` в tsconfig).
- `server/` — Node 22 + Fastify 5 + `pg`, TypeScript (ESM, `NodeNext`, импорты с суффиксом `.js`).
- PostgreSQL 17, всё упаковано в Docker: nginx (раздаёт `web/dist`, проксирует `/api/` на `server:3000`) + server + db. В проде перед ними Caddy с HTTPS. Письма: `nodemailer` по SMTP, в dev Mailpit (профиль compose `dev-mail`, UI на :8025).

## Команды

Полный стек в Docker на своём компьютере (http://localhost:8080, без HTTPS):

```bash
cp .env.example .env
docker compose up --build -d
docker compose down
```

Локальная разработка одной командой (БД и Mailpit в Docker, сервер через tsx watch, Vite с HMR; скрипты в корневом `package.json`, зависимость только `concurrently`):

```bash
npm run setup   # один раз
npm run dev     # npm run dev:stop выключает БД и Mailpit
```

Демо-данные для проверки интерфейса (мама, папа, двое детей с расписаниями и заданиями; нужна запущенная БД, `npm run dev:infra`):

```bash
npm run seed                      # создать демо-семью (прежнюю демо-семью заменяет, остальное не трогает)
npm run seed -- --snippet Миша    # JS для консоли браузера: войти под этим участником (семью не пересоздаёт)
npm run seed -- --existing --json # токены сессий для curl и скриптов
```

Скрипт `server/scripts/seed.ts`, отказывается работать на нелокальной БД. Для агента есть проектный скил `.claude/skills/seed-demo-family` (участники, порядок входа в браузер, ловушки).

Service worker в dev выключен (в `vite.config.ts` нет `devOptions`), PWA и push проверяйте на сборке. Если порт 5173 занят, Vite молча берёт следующий, смотрите адрес в выводе. Порт 8025 (Mailpit) занят и в полном Docker-стеке, поэтому одновременно запускать оба режима нельзя.

Проверки типов и сборки:

```bash
cd web && npx tsc -b && npm run lint && npm run build
cd server && npx tsc --noEmit
```

Тесты сервера (Vitest, `server/tests/`): нужна запущенная БД (`npm run dev:infra`); тесты работают в **отдельной базе `family_tasks_test`** на том же Postgres, которую создают и мигрируют сами (нелокальный хост отвергается). Запуск из корня или из `server/`:

```bash
npm test                  # все тесты, около 3 секунд
cd server && npx vitest run tests/api/tasks.test.ts   # один файл
cd server && npm run typecheck                        # типы приложения и тестов
```

- `tests/unit/` — чистая логика без БД (повторы заданий, часовые пояса и окна уведомлений, тексты, коды).
- `tests/api/` — API через `app.inject` на настоящей БД (вход, профиль, приглашения, расписания, задания, push, планировщик). Приложение собирается `buildApp` из `src/app.ts` (без запуска и без общего rate limit); `index.ts` только запускает его.
- Изоляция: файлы идут параллельно, каждый создаёт свою семью (`tests/helpers.ts`: `createFamily`, `api`, `removeFamilies`) и убирает за собой. Не делайте в тестах глобальных `delete` без условия по своим данным.
- Почта (`src/mail.js`) и `web-push` подменяются (`vi.mock`), настоящих писем и запросов к push-сервисам нет; отправленное проверяется через `tests/webpush.ts` (`sentTo`, `subscribe`). Подписки других файлов в той же БД игнорируйте, фильтруя по своим адресам.
- Ловушки Vitest 5: `beforeEach(() => mock.mockReset())` без фигурных скобок возвращает функцию, и Vitest вызывает её как очистку после теста (пишите `beforeEach(() => { ... })`); счётчик вызова подмены при загрузке модуля к началу теста уже обнулён (для такой проверки перезагружайте модуль в отдельном файле, `push-setup.test.ts`).
- Ключи VAPID на время прогона генерируются в `vitest.config.ts`.
- Проверка, что тесты ловят ошибки: вносите в код осознанную поломку (например, уберите проверку автора в `tasks/routes.ts`) и убедитесь, что тест краснеет.
- CI (`.github/workflows/ci.yml`, GitHub Actions): на каждый пуш в `main` и pull request три задания: сервер (`npm ci`, `npm run typecheck`, `npm test` с сервисом Postgres 17; адрес задаёт `DATABASE_URL`, тестовую базу тесты создают сами), фронтенд (`npx tsc -b`, `npm run lint`, `npm run build`) и конфигурация (`bash -n update.sh`, `docker compose config` для обычного и продакшен-режима, валидация `Caddyfile`). Любое изменение, которое надо проверять в CI, сначала воспроизводите локально теми же командами в чистой копии без `.env`. Названия заданий с двоеточием в YAML берите в кавычки.
- Фронтенд автотестов не имеет, проверяется вручную и скилом `seed-demo-family`.

Обновление на сервере: `./update.sh` (подробнее в разделе «Деплой и эксплуатация»).

## Миграции БД

`node-pg-migrate`, SQL-файлы в `server/migrations/` с маркерами `-- Up Migration` / `-- Down Migration`. Сервер применяет их сам при старте (`server/src/migrate.ts`), поэтому в Docker отдельного шага нет. Применённые миграции не редактируем, любое изменение схемы — новый файл:

```bash
cd server && npm run migrate:create -- имя   # migrate:up / migrate:down — вручную
```

Откат кода не откатывает схему, поэтому перед обновлением с миграциями `update.sh` делает копию БД.

## Сервер: архитектура и правила

- **Вход по email + одноразовому коду** (`server/src/auth.ts`, таблица `email_codes`, purpose `signup`/`login`). Код 6 цифр, 10 минут, 5 попыток, повторная отправка раз в 60 с. Ответ на `POST /api/email-codes` одинаков для известного и неизвестного email (при `login` письмо уходит только известным; строка с кодом пишется всегда, чтобы cooldown не выдавал существование адреса). Не меняйте это поведение, не проверив, что оно не начало раскрывать email.
- **Участник** = имя + email (оба уникальны в рамках семьи, email хранится в нижнем регистре) + роль (`mama`/`papa`/`child`). Один email может быть в нескольких семьях: `POST /api/auth/login` отвечает `409 choose_member` с вариантами, код при этом не сжигается и используется повторно со `memberId`. Создатель семьи — только мама или папа, получает `is_owner`; присоединиться по приглашению могут все три роли.
- **Сессии** (`sessions`): по одной на устройство, клиент хранит токен в IndexedDB, в БД SHA-256 хэш, `Authorization: Bearer`. `DELETE /api/session` отзывает только текущую.
- **Приглашения** (`invites`): многоразовые, 7 дней. Новое приглашение удаляет старые (так можно отозвать утёкшую ссылку). Ссылка вида `/join?code=...`. Владелец видит и перевыпускает его на странице семьи.
- **Профиль и фото.** `PATCH /api/me` меняет имя (уникально в семье, иначе `409 name_taken`), фото и дату рождения; email и роль менять нельзя. Дата рождения (`members.birth_date`, тип `date`) ходит строкой `YYYY-MM-DD`: на сервере её всегда читают через `to_char(...)`, на клиенте разбирают вручную (`web/src/lib/date.ts`), потому что `new Date('YYYY-MM-DD')` и драйвер `pg` сдвигают день по часовому поясу. Проверка: реальная дата, не раньше 1900 и не в будущем (запас сутки на пояса), `null` очищает; ошибка `invalid_birth_date`. Фото хранится прямо в `members.avatar` как data URL (jpeg/png/webp, не больше 70 000 символов, ограничено схемой и `check` в БД). Клиент перед отправкой обрезает его до квадрата 128×128 JPEG (`web/src/lib/image.ts`, около 3–10 КБ), поэтому сервер ничего не ресайзит и не должен принимать оригиналы. Фото и дата рождения приходят в `/api/me` для всех участников семьи. Fastify вырезает неизвестные поля (`removeAdditional`) уже после `minProperties`, так что пустой итоговый патч проверяется вручную.
- **Расписание уроков** (`schedule_lessons`, `server/src/schedule.ts`): только у участников с ролью `child`, дни 1–6 (Пн–Сб), у урока предмет и необязательные время начала и конца (окончание строго позже начала), не больше 12 уроков в день. Сохраняется целиком через `PUT /api/members/:id/schedule`; порядок уроков в дне равен порядку в массиве.
- **Расписание тренировок** (`training_sessions`, `server/src/trainings.ts`) устроено так же, но дни 1–7 (Пн–Вс, ISO: воскресенье = 7, в отличие от `Date.getDay()`; помощники в `web/src/lib/weekdays.ts`), у тренировки название, необязательные место и время, не больше 8 в день. `GET/PUT /api/members/:id/trainings`.
- **Доступ к расписаниям** (`server/src/access.ts`, `authorizeChild`): читать и менять может сам ребёнок и любой родитель (мама/папа) его семьи, другие дети получают 403, чужая семья 404, не-ребёнок 400.
- **Задания** (`tasks`, `task_completions`, `server/src/tasks/`). Любой член семьи создаёт задание себе или другому; видят все задания семьи все. Менять и удалять (`PUT/DELETE /api/tasks/:id`) может только автор (иначе 403), отмечать выполненным и снимать отметку (`POST /api/tasks/:id/complete|uncomplete`, тело `{date}`) — любой в семье. Срок необязателен: без даты это «без срока»; время допустимо только с датой. Повтор `none|daily|weekly|monthly` (`weekly` с днями 1–7, `monthly` на то же число, в коротком месяце на последний день), необязательное `until`. Расписание повторов считает только сервер (`tasks/recurrence.ts`, чистые функции с проверкой на граничных случаях); клиент получает готовые вхождения: `GET /api/tasks?from&to` (не больше 62 дней) отдаёт `{tasks, occurrences}`: вхождения периода, невыполненные просроченные разовые и задания без срока; `GET /api/tasks/done` — недавно выполненное. Выполнение хранится по каждому вхождению (`task_completions`, для задания без даты дата-заглушка `1970-01-01`), поэтому повторяющееся задание отмечается отдельно в каждый день; при смене графика отметки сбрасываются, при смене названия сохраняются. Уведомления (`notifyMember` в `push.ts`, тексты в `tasks/text.ts`): исполнителю при создании и изменении (если задание дал не он сам), автору при первой отметке выполнения (если выполнил не он сам). Напоминаний «в срок» нет.
- **Push-уведомления** (`server/src/push.ts`, `server/src/notifications/`, таблицы `push_subscriptions` и `notification_log`). Web Push через `web-push` и ключи VAPID из `.env` (без них функция выключена, `/api/push/*` отвечают 503). Планировщик (`scheduler.ts`) раз в минуту просматривает подписки и для каждой считает местное время по её `time_zone` (`Intl`, `time.ts`): в 10:00 день рождения (именинника поздравляем отдельным текстом, остальным «исполняется N»), в 17:00 для детей уроки следующего учебного дня (воскресенье и суббота без уроков пропускаются, как на «Моём дне»; нет уроков — ничего не шлём). Опоздавшее уведомление уходит в течение двух часов после назначенного времени, дальше нет. Тренировки: ребёнку за 2 часа до `starts_at` (`trainingMessages`; без времени начала напоминаний нет; окно отправки 15 минут без догона, потому что «за 2 часа» теряет смысл; тренировка в первые часы после полуночи анонсируется накануне вечером, поэтому у `PlannedMessage` есть `day` — дата самой тренировки для журнала). Дубли исключает `notification_log` (запись пишется до отправки: на одну подписку, вид и локальную дату). Подписка с ответом 404/410 удаляется. Тексты и выбор дня — чистые функции в `messages.ts`. Адрес подписки принимается только у известных push-сервисов (`ALLOWED_SUFFIXES` в `push.ts`, для тестов `PUSH_ALLOWED_HOSTS`): сервер сам обращается по этому адресу, иначе это SSRF. Подписка привязывается к устройству (`endpoint`) и переходит к тому, кто вошёл на нём последним. Принудительный проход для проверки: `npm run notify:tick -- HH:MM [--reset]` в `server/` (`server/scripts/tick.ts`).
- **Прокси и лимиты.** Сервер за nginx (и Caddy в проде): `trustProxy: true` для `X-Forwarded-For`. Rate limit — общий 120/мин и строгий 10/мин (`strictLimit` в `server/src/routes.ts`) на эндпоинты, где можно подбирать коды; строгий счётчик общий для этих маршрутов по IP. Сервер не должен торчать наружу в обход nginx.

## Клиент: экраны и данные

**Маршруты.** Публичные: `/`, `/create`, `/created`, `/join`, `/login`. Остальные лежат под `AppShell` (проверка входа, значок профиля справа сверху и нижняя панель табов `TabBar`): `/tasks`, `/tasks/new`, `/tasks/:taskId`, `/chat`, `/my-day`, `/family`, `/family/:memberId`, `/profile`, `/settings`, `/settings/schedule`, `/settings/trainings`, `/family/:memberId/schedule`, `/family/:memberId/trainings`. Вошедшего `Welcome` отправляет на `/tasks`. Новый раздел: страница в `pages/`, роут внутри `AppShell` в `App/index.tsx` и запись в `TABS` (`components/TabBar/utils.ts`). В таб-баре раздел назван «Задачи», заголовок страницы «Задания». «Чат» — заглушка (`components/Placeholder`).

**Семья и профиль.**
- «Моя семья» (`/family`): приглашение для владельца, список участников. Карточка ведёт на `/profile`, если это вы, иначе на превью `/family/:memberId` (фото, имя, роль, дата рождения и возраст; email не показываем; у ребёнка для родителя пункты расписаний).
- `/profile`: имя, дата рождения, фото; email и роль только для чтения.
- Значок профиля (`Avatar`: фото, а без него круг стабильного цвета из `memberId` и первая буква имени) ведёт на `/profile`.
- `/api/me` запрашивается один раз для всех разделов (`web/src/profile`: `ProfileProvider` внутри `AppShell`, хук `useProfile`, `refresh()` после изменений); при 401 он очищает вход. Данные перезапрашиваются при каждом переходе и при возврате на вкладку, чтобы правки других участников (фото, имя, дата) были видны без перезагрузки. После смены имени обновляйте и `Identity` на устройстве (`save`).
- Состояние входа: `web/src/identity/` (провайдер читает IndexedDB, хук `useIdentity` в `context.ts`, `toIdentity` превращает ответ сервера в `Identity`).
- Регистрация и присоединение — общий `components/RoleForm` (шаг `DetailsStep`, затем `CodeStep`): сам показывает ошибки, страницы только вызывают API и бросают `ApiError`.

**Задания.**
- `/tasks`: вкладки «Предстоящие» (7 дней вперёд, просроченное сверху, «без срока» внизу) и «Выполненные» (за месяц, с отметкой, кто выполнил), фильтр по человеку («Все», «Мои», каждый член семьи).
- `/tasks/new`, `/tasks/:taskId` (`pages/TaskForm`): автору форма с удалением, остальным только просмотр (отметить выполненным можно в списке).
- Отметка с мгновенным откликом и откатом при ошибке — хук `lib/useToggleOccurrence`, общая строка — `components/TaskItem`, склейка вхождений и сортировка — `lib/occurrences.ts`.

**Расписания.**
- Ребёнок правит своё из «Настроек» (`/settings/schedule`, `/settings/trainings`), родитель — с превью ребёнка (`/family/:memberId/...`). Страницы `pages/Schedule` и `pages/Trainings` — зеркальные редакторы: по умолчанию просмотр (`LessonViewList`, `TrainingViewList`), «Изменить» открывает редактор с черновиком (`saved` — серверное состояние, `draft` — правки), «Отмена» с несохранёнными правками просит подтверждение, пустые строки при сохранении отбрасываются.
- Общие `components/DayTabs` (дни передаются пропом) и `components/SortableList` (перетаскивание `@dnd-kit`, ручка слева, есть клавиатура; строки сами вызывают `useSortable`).

**«Мой день».** Приветствие по времени суток и блоки (`pages/MyDay`):
- «Задания на сегодня» (`TodayTasks`): мои на сегодня и просроченные, без «без срока», отметка прямо в списке.
- Ребёнку «Уроки сегодня/завтра/в понедельник» (`TodayLessons`) и «Тренировки сегодня/завтра/в среду» (`TodayTrainings`).
- Родителю «Уроки и тренировки детей» (`FamilyLessons`): компактная карточка на каждого ребёнка со ссылкой в его расписание; расписания грузятся параллельно по одному запросу на ребёнка, день для каждого выбирается отдельно.
- Выбор дня (`pages/MyDay/utils.ts`): уроки (`pickLessonDay`) — до 18:00 сегодняшний, с 18:00 завтрашний, воскресенье и суббота без уроков пропускаются до понедельника; тренировки (`pickTrainingDay`) — с сегодняшнего (с 18:00 с завтрашнего) берётся ближайший день с тренировками, нет тренировок совсем — блока нет.

**«Настройки».** Для детей пункты расписаний, блок «Уведомления» (`NotificationsSetting`, хук `lib/usePushSubscription`: включение, проверка, выключение на этом устройстве), тема оформления внизу.

## PWA, кэширование, тема

- Service worker свой, `web/src/sw.ts` (стратегия `injectManifest`): кэш приложения (`/api/` в кэш не попадает) и обработчики `push` и `notificationclick`. Он собирается отдельным tsconfig (`tsconfig.sw.json`, lib `WebWorker`) и исключён из `tsconfig.app.json`. Иконки генерируются из `web/public/icon.svg` командой `npm run generate-pwa-assets` (в `web/`).
- Кэширование (`web/nginx.conf`): `index.html` (включая `/` и все маршруты SPA, их отдаёт SPA fallback), `sw.js`, `registerSW.js` и `manifest.webmanifest` отдаются с `Cache-Control: no-cache` (браузер каждый раз сверяется по ETag, 304 если не менялись), файлы с хэшем в `/assets/` с `public, max-age=31536000, immutable`; манифест отдаётся с типом `application/manifest+json`. Если добавите файл, который меняется между сборками без хэша в имени, добавьте его в `no-cache`-правило, иначе пользователи будут видеть старую версию.
- Тема: по умолчанию следует `prefers-color-scheme`, явный выбор (`pages/Settings/components/ThemeSetting`: как в системе / светлая / тёмная) хранится в `localStorage['theme']` и применяется атрибутом `data-theme` на `<html>`. Скрипт в `web/index.html` ставит его до первого рендера (без вспышки) и синхронизирует `<meta name="theme-color">`; логика дублирует `lib/theme.ts`, при изменении правьте оба места. Слушатель смены системной темы (`lib/useThemeSync`) подключён один раз в `App`.

## Структура `web/src`

Каждый компонент — папка с `index.tsx`. Рядом по необходимости: `styles.ts` (styled-components), `types.ts` (пропсы и типы), `utils.ts` (чистые функции). Вложенные компоненты, которые нужны только этому компоненту, лежат в его `components/` и устроены так же, на любую глубину.

- `App/`, `main.tsx` — корень, роуты.
- `pages/<Page>/` — страницы (default export), у них свои `components/`.
- `components/` — общие компоненты. Базовые примитивы (`Button`, `Chip`, `IconButton`, `Input`, `Notice`, `Page`, `Select`, `Stack`, `BackLink`) объявлены как styled-компоненты прямо в `index.tsx`; варианты задаются transient-пропсами (`$variant`, `$tone`, `$inline`, `$active`), ссылки получаются через `as={Link}`. Остальное: `AppShell`, `Avatar`, `CodeStep`, `DayTabs`, `Field`, `LessonViewList`, `LinkBox`, `MenuLink`, `Placeholder`, `ReplaceGuard`, `RoleForm`, `SortableList`, `TabBar`, `TaskItem`, `TrainingViewList`.
- `GlobalStyle/` (в `components/`) — глобальные стили. Цвета заданы CSS-переменными, в styled-компонентах используйте `var(--...)`, а не жёсткие цвета. Новый цвет добавляйте в обе палитры (`lightColors`/`darkColors`).
- `api/` — клиент API по доменам: `client.ts` (`request`, `ApiError`), `auth/`, `families/`, `invites/`, `profile/`, `push/`, `schedule/`, `tasks/`, `trainings/` (в каждом `index.ts` с функциями и `types.ts`), наружу всё реэкспортирует `api/index.ts`, поэтому импортируем из `@/api`. Новый эндпоинт кладём в свой домен.
- `identity/`, `profile/` — провайдеры состояния (не UI): `context.ts` с хуком вынесен из `index.tsx` ради fast refresh.
- `lib/` — общие модули без UI: `date`, `errors`, `image`, `links`, `occurrences`, `roles`, `taskText`, `theme`, `validation`, `weekdays` и хуки `useNow`, `usePushSubscription`, `useThemeSync`, `useToggleOccurrence`.

## Соглашения

- В `web/` включён `erasableSyntaxOnly`: никаких `enum` и parameter properties в конструкторах.
- API-запросы фронтенда только через `web/src/api` (общий `request`, ошибки как `ApiError` с `status` и `code`). Коды ошибок сервера — snake_case (`invite_expired`, `name_taken`), UI мапит их на тексты.
- Валидация входных данных на сервере через JSON-схемы Fastify; запросы к БД — параметризованный SQL через `pg`, без ORM. Даты и время отдаём строками через `to_char`.
- Секреты и `.env` не коммитим (`.env` и `backups/` в `.gitignore`, шаблон — `.env.example`).
- Коммиты на русском или английском без требований к формату; в `main` пушим только по просьбе пользователя.

## Деплой и эксплуатация

- **Прод:** на сервере в `.env` задано `COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml` и `DOMAIN`, тогда обычный `docker compose up -d --build` поднимает ещё и Caddy (`Caddyfile`, сертификат Let's Encrypt для `DOMAIN`, том `caddy_data` не удалять); веб-контейнер снаружи не публикуется (`ports: !reset []`). Первый запуск по шагам и повседневные команды описаны в README, раздел «Деплой на сервер».
- **Обновление:** `./update.sh` на сервере: `git pull --ff-only`, копия БД в `backups/` (последние 14, `--no-backup` пропускает), `docker compose up -d --build`, проверка здоровья сервера изнутри (до минуты) и, если задан `DOMAIN`, снаружи по HTTPS, `docker image prune`. При неудаче показывает лог сервера и команду отката (`git checkout <прежний коммит>`); миграции при откате кода не откатываются. Скрипт предупреждает, если изменился `.env.example` или появились миграции.
- **IP клиента.** Цепочка Caddy → nginx (`web`) → Fastify. Caddy ставит `X-Forwarded-For`, nginx принимает его через `real_ip` только от внутренних сетей Docker и передаёт серверу `X-Forwarded-For $remote_addr`, поэтому rate limit работает на каждого посетителя и заголовок подделать нельзя. Если поменять эту цепочку (например, добавить ещё прокси), проверьте, что IP клиента по-прежнему доходит до API (в логах сервера `remoteAddress`), иначе лимиты станут общими на всех.
- **Почта обязательна.** Без настоящего SMTP войти нельзя (только код из письма). DigitalOcean блокирует исходящие порты 25, 465 и 587, поэтому нужен сервис с портом 2525. Сервисы рассылок не разрешают отправлять «от имени» `@gmail.com` и подобных (DMARC), нужен адрес на **своём домене**, подтверждённом через DKIM и SPF; на бесплатных поддоменах (DuckDNS) этих DNS-записей не добавить. Mailpit (`COMPOSE_PROFILES=dev-mail`) в проде не включать.
- **Ключи VAPID** создаются один раз (`npx web-push generate-vapid-keys`) и больше не меняются: после смены все push-подписки перестают работать. `VAPID_SUBJECT` — настоящий контакт (для iPhone важно). Пароль БД в `.env` без символов `/ + = @ :` (ломают строку подключения), лучше hex.
- **Адрес и данные браузера.** Вход, подписки и приглашения привязаны к адресу сайта: при смене домена всё придётся делать заново.
- **Тома.** `pgdata` (БД) и `caddy_data` (сертификаты) не удалять: `docker compose down -v` стирает их.

## Известные ограничения и идеи

- «Чат» — заглушка; напоминаний о заданиях «в срок» нет; у фронтенда нет автотестов.
- Во встроенной панели Browser (инструменты агента) service worker и уведомления не работают: настоящую доставку push проверять в обычном Chrome на собранной версии (README, раздел про push). На iPhone уведомления есть только у приложения, добавленного на экран «Домой» (iOS 16.4+), и нужен HTTPS.
- Название таба «Задачи» и страницы «Задания» разное, при желании унифицировать в `TABS`.
