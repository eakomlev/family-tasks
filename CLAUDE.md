# Family Tasks

PWA для семейных задач. Монорепозиторий без workspaces: у `web/` и `server/` свои `package.json` и `node_modules`. Язык интерфейса и сообщений об ошибках для пользователя — русский, комментарии в коде тоже на русском.

- `web/` — React 19 + Vite 8 + TypeScript, стили на `styled-components`, PWA через `vite-plugin-pwa`, роутинг `react-router-dom`, данные на устройстве в IndexedDB (`idb-keyval`). Алиас `@/` → `web/src` (vite + `paths` в tsconfig).
- `server/` — Node 22 + Fastify 5 + `pg`, TypeScript (ESM, `NodeNext`, импорты с суффиксом `.js`).
- PostgreSQL 17, всё упаковано в Docker: nginx (раздаёт `web/dist`, проксирует `/api/` на `server:3000`) + server + db. Письма: `nodemailer` по SMTP, в dev Mailpit (профиль compose `dev-mail`, UI на :8025).

## Команды

Полный стек как в проде (http://localhost:8080):

```bash
cp .env.example .env
docker compose up --build -d
docker compose down
```

Локальная разработка одной командой (БД и Mailpit в Docker, сервер через tsx watch, Vite с HMR; скрипты в корневом `package.json`, зависимость только `concurrently`):

```bash
npm run setup   # один раз
npm run dev     # npm run dev:stop выключает БД и Mailpit
```

Service worker в dev выключен (в `vite.config.ts` нет `devOptions`), PWA и push проверяйте на сборке.

Проверки (тестов пока нет):

```bash
cd web && npx tsc -b && npm run lint && npm run build
cd server && npx tsc --noEmit
```

Если порт 5173 занят, Vite молча берёт следующий, смотрите адрес в выводе. Порт 8025 (Mailpit) занят и в полном Docker-стеке, поэтому одновременно запускать оба режима нельзя.

## Миграции БД

`node-pg-migrate`, SQL-файлы в `server/migrations/` с маркерами `-- Up Migration` / `-- Down Migration`. Сервер применяет их сам при старте (`server/src/migrate.ts`), поэтому в Docker отдельного шага нет. Применённые миграции не редактируем, любое изменение схемы — новый файл:

```bash
cd server && npm run migrate:create -- имя   # migrate:up / migrate:down — вручную
```

## Архитектура и важные решения

- **Вход по email + одноразовому коду** (`server/src/auth.ts`, таблица `email_codes`, purpose `signup`/`login`). Код 6 цифр, 10 минут, 5 попыток, повторная отправка раз в 60 с. Ответ на `POST /api/email-codes` одинаков для известного и неизвестного email (при `login` письмо уходит только известным; строка с кодом пишется всегда, чтобы cooldown не выдавал существование адреса). Не меняйте это поведение, не проверив, что оно не начало раскрывать email.
- **Участник** = имя + email (оба уникальны в рамках семьи, email хранится в нижнем регистре) + роль (`mama`/`papa`/`child`). Один email может быть в нескольких семьях: `POST /api/auth/login` отвечает `409 choose_member` с вариантами, код при этом не сжигается и используется повторно со `memberId`.
- **Сессии** (`sessions`): по одной на устройство, клиент хранит токен в IndexedDB, в БД SHA-256 хэш, `Authorization: Bearer`. `DELETE /api/session` отзывает только текущую.
- **Профиль и фото.** `PATCH /api/me` меняет имя (уникально в семье, иначе `409 name_taken`), фото и дату рождения; email и роль менять нельзя. Дата рождения (`members.birth_date`, тип `date`) ходит строкой `YYYY-MM-DD`: на сервере её всегда читают через `to_char(...)`, на клиенте разбирают вручную (`web/src/lib/date.ts`), потому что `new Date('YYYY-MM-DD')` и драйвер `pg` сдвигают день по часовому поясу. Проверка: реальная дата, не раньше 1900 и не в будущем (запас сутки на пояса), `null` очищает; ошибка `invalid_birth_date`. Дата и возраст видны в превью участника семьи. Фото хранится прямо в `members.avatar` как data URL (jpeg/png/webp, не больше 70 000 символов, ограничено схемой и `check` в БД). Клиент перед отправкой обрезает его до квадрата 128×128 JPEG (`web/src/lib/image.ts`, около 3–10 КБ), поэтому сервер ничего не ресайзит и не должен принимать оригиналы. Фото приходят в `/api/me` для всех участников семьи. Fastify вырезает неизвестные поля (`removeAdditional`) уже после `minProperties`, так что пустой итоговый патч проверяется вручную.
- На клиенте `/api/me` запрашивается один раз для всех разделов в `web/src/profile` (`ProfileProvider` внутри `AppShell`, хук `useProfile`, `refresh()` после изменений); при 401 он очищает вход. Данные перезапрашиваются при каждом переходе между страницами и при возврате на вкладку, чтобы правки других участников (фото, имя, дата рождения) были видны без перезагрузки; без этого родитель видел устаревший профиль ребёнка. После смены имени обновляйте и `Identity` на устройстве (`save`).
- **Расписание уроков** (`schedule_lessons`, `server/src/schedule.ts`): только у участников с ролью `child`, дни 1–6 (Пн–Сб), у урока предмет и необязательные время начала и конца (окончание строго позже начала), не больше 12 уроков в день. Сохраняется целиком через `PUT /api/members/:id/schedule`; порядок уроков в дне равен порядку в массиве. Читать и менять может сам ребёнок и любой родитель (мама/папа) его семьи, другие дети получают 403, чужая семья 404. Вкладки дней (`components/DayTabs`, дни передаются пропом) и перетаскиваемый список (`components/SortableList`, строки сами вызывают `useSortable`) общие для уроков и тренировок. Страница `pages/Schedule` по умолчанию в режиме просмотра (`LessonViewList`, только чтение), кнопка «Изменить» открывает редактор с черновиком (`saved` — серверное состояние, `draft` — правки), «Отмена» с несохранёнными правками просит подтверждение. Порядок на клиенте меняется перетаскиванием (`@dnd-kit`, ручка слева, есть клавиатура); пустые строки без предмета при сохранении отбрасываются.
- **Расписание тренировок** (`training_sessions`, `server/src/trainings.ts`) устроено как расписание уроков, но дни 1–7 (Пн–Вс, ISO: воскресенье = 7, в отличие от `Date.getDay()`; помощники в `web/src/lib/weekdays.ts`), у тренировки название, необязательные место и время, не больше 8 в день. Эндпоинты `GET/PUT /api/members/:id/trainings`. Проверка прав (ребёнок сам и родители семьи, остальные дети 403) общая для уроков и тренировок: `server/src/access.ts` (`authorizeChild`).
- **Задания** (`tasks`, `task_completions`, `server/src/tasks/`). Любой член семьи создаёт задание себе или другому; видят все задания семьи все. Менять и удалять (`PUT/DELETE /api/tasks/:id`) может только автор (иначе 403), отмечать выполненным и снимать отметку (`POST /api/tasks/:id/complete|uncomplete`, тело `{date}`) — любой в семье. Срок необязателен: без даты это «без срока»; время допустимо только с датой. Повтор `none|daily|weekly|monthly` (`weekly` с днями 1–7, `monthly` на то же число, в коротком месяце на последний день), необязательное `until`. Расписание повторов считает только сервер (`tasks/recurrence.ts`, чистые функции с проверкой на граничных случаях); клиент получает готовые вхождения: `GET /api/tasks?from&to` (не больше 62 дней) отдаёт `{tasks, occurrences}`: вхождения периода, невыполненные просроченные разовые и задания без срока; `GET /api/tasks/done` — недавно выполненное. Выполнение хранится по каждому вхождению (`task_completions`, для задания без даты дата-заглушка `1970-01-01`), поэтому повторяющееся задание отмечается отдельно в каждый день; при смене графика отметки сбрасываются, при смене названия сохраняются. Уведомления (`notifyMember` в `push.ts`, тексты в `tasks/text.ts`): исполнителю при создании и изменении (если задание дал не он сам), автору при первой отметке выполнения (если выполнил не он сам). Напоминаний «в срок» нет.
- **Push-уведомления** (`server/src/push.ts`, `server/src/notifications/`, таблицы `push_subscriptions` и `notification_log`). Web Push через `web-push` и ключи VAPID из `.env` (без них функция выключена, `/api/push/*` отвечают 503). Планировщик (`scheduler.ts`) раз в минуту просматривает подписки и для каждой считает местное время по её `time_zone` (`Intl`, `time.ts`): в 10:00 день рождения (именинника поздравляем отдельным текстом, остальным «исполняется N»), в 17:00 для детей уроки следующего учебного дня (воскресенье и суббота без уроков пропускаются, как на «Моём дне»; нет уроков — ничего не шлём). Опоздавшее уведомление уходит в течение двух часов после назначенного времени, дальше нет. Дубли исключает `notification_log` (запись пишется до отправки: на одну подписку, вид и локальную дату). Подписка с ответом 404/410 удаляется. Тренировки: ребёнку за 2 часа до `starts_at` (`trainingMessages`; без времени начала напоминаний нет; окно отправки 15 минут, без догона, потому что «за 2 часа» теряет смысл; тренировка в первые часы после полуночи анонсируется накануне вечером, поэтому у `PlannedMessage` есть `day` — дата самой тренировки для журнала). Тексты и выбор дня — чистые функции в `messages.ts`. Адрес подписки принимается только у известных push-сервисов (`ALLOWED_SUFFIXES` в `push.ts`, для тестов `PUSH_ALLOWED_HOSTS`): сервер сам обращается по этому адресу, иначе это SSRF. Подписка привязывается к устройству (`endpoint`) и переходит к тому, кто вошёл на нём последним. Принудительный проход для проверки: `npm run notify:tick -- HH:MM [--reset]` в `server/` (`server/scripts/tick.ts`).
- Создатель семьи — только мама или папа, получает `is_owner`. Присоединиться по приглашению могут все три роли.
- **Приглашения** (`invites`): многоразовые, 7 дней. Новое приглашение удаляет старые (так можно отозвать утёкшую ссылку). Ссылка вида `/join?code=...`. Владелец видит и перевыпускает его на странице семьи.
- Сервер за nginx: `trustProxy: true` для `X-Forwarded-For`. Rate limit — общий 120/мин и строгий 10/мин (`strictLimit` в `server/src/routes.ts`) на эндпоинты, где можно подбирать коды; строгий счётчик общий для этих маршрутов по IP. Сервер не должен торчать наружу в обход nginx.
- Состояние идентичности: `web/src/identity/` (провайдер читает IndexedDB, хук `useIdentity` в `context.ts`, `toIdentity` превращает ответ сервера в `Identity`). Если API отвечает 401, страница семьи очищает идентичность и возвращает на приветствие.
- Маршруты фронтенда: публичные `/`, `/create`, `/created`, `/join`, `/login` и разделы под `AppShell` (общий каркас: проверка входа и нижняя панель табов `TabBar`): `/tasks`, `/chat`, `/my-day`, `/family` («Моя семья»), `/family/:memberId` (превью другого участника, только просмотр: фото, имя, роль; email не показываем), `/profile`, `/settings`. Карточка участника в «Моей семье» ведёт на `/profile`, если это вы, иначе на превью. Задания: `/tasks` (список: вкладки «Предстоящие» на 7 дней вперёд с просроченным и «без срока» и «Выполненные», фильтр по человеку), `/tasks/new` и `/tasks/:taskId` (`pages/TaskForm`: автору форма с удалением, остальным только просмотр); на «Моём дне» блок «Задания на сегодня» (`TodayTasks`: мои на сегодня и просроченные). Отметка с мгновенным откликом и откатом при ошибке — хук `lib/useToggleOccurrence`, общая строка — `components/TaskItem`. В таб-баре раздел назван «Задачи», заголовок страницы «Задания». Расписание тренировок: `/settings/trainings` и `/family/:memberId/trainings` (страница `pages/Trainings`, зеркало расписания уроков). Расписание уроков: `/settings/schedule` (ребёнок правит своё, пункт есть только в его настройках) и `/family/:memberId/schedule` (родитель, пункт на превью ребёнка); это один компонент `pages/Schedule`. В «Настройках» блок «Уведомления» (`NotificationsSetting`, хук `lib/usePushSubscription`) включает и выключает push на этом устройстве; тема оформления стоит в самом низу. Значок профиля (`Avatar`: фото, а без него круг стабильного цвета из `memberId` и первая буква имени) лежит в `AppShell` справа сверху и ведёт на `/profile` (имя, фото, email и роль только для чтения; в таб-баре страницы нет). Чат пока заглушка (`components/Placeholder`), «Мой день» показывает приветствие и (только у детей) блок «Уроки сегодня» из расписания (`pages/MyDay/components/TodayLessons`; какой день показывать, решает `pickLessonDay`: до 18:00 сегодняшний, с 18:00 завтрашний, а воскресенье и суббота без уроков пропускаются до понедельника; заголовок «Уроки сегодня/завтра/в понедельник»), «Настройки» — выбор темы (и пункт расписания у детей). Тренировки: ребёнку блок «Тренировки сегодня/завтра/в среду» (`TodayTrainings`, `pickTrainingDay` в `pages/MyDay/utils.ts`: до 18:00 с сегодняшнего дня, с 18:00 с завтрашнего, берётся ближайший день с тренировками, нет тренировок совсем — блока нет), родителям строка «Тренировка завтра: Футбол 10:00» в карточке ребёнка. Родителям вместо блока уроков показывается «Уроки и тренировки детей» (`pages/MyDay/components/FamilyLessons`: компактная карточка на каждого ребёнка со ссылкой в его расписание; расписания всех детей грузятся параллельно по одному запросу на ребёнка, день для каждого выбирается отдельно). Логика выбора дня (`pickLessonDay`, `lessonsForDay`) лежит в `pages/MyDay/utils.ts`. Список уроков только для чтения — общий `components/LessonViewList`. Новый раздел: страница в `pages/`, роут внутри `AppShell` в `App/index.tsx` и запись в `TABS` (`components/TabBar/utils.ts`). Вошедшего пользователя `Welcome` отправляет на `/tasks`. nginx отдаёт `index.html` для любого пути (SPA fallback). Кэширование (`web/nginx.conf`): `index.html` (включая `/` и все маршруты SPA), `sw.js`, `registerSW.js` и `manifest.webmanifest` отдаются с `Cache-Control: no-cache` (браузер каждый раз сверяется по ETag, 304 если не менялись), файлы с хэшем в `/assets/` с `public, max-age=31536000, immutable`; манифест отдаётся с типом `application/manifest+json`. Если добавите новый файл, который меняется между сборками без хэша в имени, добавьте его в `no-cache`-правило, иначе пользователи будут видеть старую версию.
- PWA: service worker свой, `web/src/sw.ts` (стратегия `injectManifest`): кэш приложения (`/api/` в кэш не попадает) и обработчики `push` и `notificationclick`. Он собирается отдельным tsconfig (`tsconfig.sw.json`, lib `WebWorker`) и исключён из `tsconfig.app.json`. Иконки генерируются из `web/public/icon.svg` командой `npm run generate-pwa-assets` (в `web/`).

## Структура `web/src`

Каждый компонент — папка с `index.tsx`. Рядом по необходимости: `styles.ts` (styled-components), `types.ts` (пропсы и типы), `utils.ts` (чистые функции). Вложенные компоненты, которые нужны только этому компоненту, лежат в его `components/` и устроены так же, на любую глубину.

- `App/`, `main.tsx` — корень, роуты.
- `pages/<Page>/` — страницы (default export), у них свои `components/`.
- `components/` — общие компоненты. Базовые примитивы (`Button`, `Input`, `Notice`, `Page`, `Stack`, `BackLink`) объявлены как styled-компоненты прямо в `index.tsx`; варианты задаются transient-пропсами (`$variant`, `$tone`), ссылки получаются через `as={Link}`.
- `GlobalStyle/` — глобальные стили. Цвета заданы CSS-переменными, в styled-компонентах используйте `var(--...)`, а не жёсткие цвета. Тема: по умолчанию следует `prefers-color-scheme`, явный выбор пользователя (`pages/Settings/components/ThemeSetting`: как в системе / светлая / тёмная) хранится в `localStorage['theme']` и применяется атрибутом `data-theme` на `<html>`. Скрипт в `web/index.html` ставит его до первого рендера (без вспышки) и синхронизирует `<meta name="theme-color">`; логика дублирует `lib/theme.ts`, при изменении правьте оба места. Новый цвет добавляйте в обе палитры (`lightColors`/`darkColors`). Слушатель смены системной темы (`lib/useThemeSync`) подключён один раз в `App`.
- `api/` — клиент API по доменам: `client.ts` (`request`, `ApiError`), `auth/`, `families/`, `invites/` (в каждом `index.ts` с функциями и `types.ts`), наружу всё реэкспортирует `api/index.ts`, поэтому импортируем из `@/api`. Новый эндпоинт кладём в свой домен. `identity/` (провайдер, `context.ts` с хуком `useIdentity`, `utils.ts`) — не UI. Хук вынесен из `index.tsx` ради fast refresh.
- `lib/` — мелкие общие модули без UI (`roles`, `links`, `errors`, `validation`).

## Соглашения

- В `web/` включён `erasableSyntaxOnly`: никаких `enum` и parameter properties в конструкторах.
- API-запросы фронтенда только через `web/src/api` (общий `request`, ошибки как `ApiError` с `status` и `code`). Коды ошибок сервера — snake_case (`invite_expired`, `name_taken`), UI мапит их на тексты.
- Валидация входных данных на сервере через JSON-схемы Fastify; запросы к БД — параметризованный SQL через `pg`, без ORM.
- Регистрация/присоединение — общий компонент `web/src/components/RoleForm` (шаг `DetailsStep`, затем `CodeStep` с кодом). Он сам показывает ошибки; страницы только вызывают API и бросают `ApiError`.
- Секреты и `.env` не коммитим (`.env` в `.gitignore`, шаблон — `.env.example`).
- Коммиты на русском или английском без требований к формату; в `main` пушим только по просьбе пользователя.

## Деплой

Прод: `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build` (подробно в README, раздел про сервер). Добавляет Caddy (`Caddyfile`, сертификат Let's Encrypt для `DOMAIN`, том `caddy_data` не удалять), веб-контейнер снаружи не публикуется (`ports: !reset []`). Цепочка: Caddy → nginx (`web`) → Fastify. Реальный IP клиента: Caddy ставит `X-Forwarded-For`, nginx принимает его через `real_ip` только от внутренних сетей Docker и передаёт серверу `X-Forwarded-For $remote_addr`, поэтому rate limit работает на каждого посетителя и заголовок подделать нельзя. Если поменять эту цепочку (например, добавить ещё прокси), проверьте, что IP клиента по-прежнему доходит до API (в логах сервера `remoteAddress`), иначе лимиты станут общими на всех. В проде нужны настоящие SMTP (иначе не войти) и ключи VAPID, Mailpit (`COMPOSE_PROFILES=dev-mail`) не включать.
